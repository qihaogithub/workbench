# 元素自由定位（`$demo.positionable`）优化方案

## 背景

`$demo.positionable` 允许用户在 Schema 中声明可定位子组件列表，通过配置面板中的缩略画布拖拽或输入坐标来调整元素在容器中的 X/Y 位置。当前实现的核心流程：

1. Schema 声明 `$demo.positionable`（items / defaults / size）
2. `__positions` 以隐藏 prop 注入组件代码，组件代码需在 DOM 上添加 `data-pos-key` 属性
3. 配置面板渲染 280×200px 缩略画布，等比缩放容器，在画布上拖拽方块
4. 元素尺寸通过 postMessage 协议从 iframe 收集（`COLLECT_POSITIONABLE_SIZES` → `POSITIONABLE_SIZES_RESULT`）
5. 坐标变更写入 `formData.__positions`

## 当前问题

### 1. 缩略画布与真实预览脱节

- 用户在 280×200px 的迷你画布上拖拽缩放后的方块，无法看到实际渲染效果
- 小尺寸元素在缩放后几乎不可见（例如 40×40px 元素缩放后仅 ~14×14px），难以精确操作
- 网格线基于 100px 间距，与元素实际尺寸无关联

### 2. 鼠标事件边界问题

- 使用 `onMouseDown` / `onMouseMove` / `onMouseUp`（`ConfigForm.tsx` 513-540 行）
- 鼠标拖拽到画布外时丢失 `mousemove`，依赖 `onMouseLeave` 兜底结束拖拽
- 不支持触摸设备（平板/手机）

### 3. `data-pos-key` + postMessage 尺寸收集协议脆弱

- 组件代码必须手动添加 `data-pos-key` 属性，增加创作端用户的心智负担
- 尺寸收集依赖 500ms 图片加载超时兜底（`iframe-template.ts` 2099-2119 行），时序不确定
- 仅在父窗口主动发送 `COLLECT_POSITIONABLE_SIZES` 时才回传，不是实时推送
- 找不到元素或尺寸为 0 时回退到无尺寸的标签方块

### 4. 每次拖拽触发 React re-render

- 每个 `mousemove` 调用 `onPositionsChange({ ...positions, [key]: { x, y } })`（533 行）
- 导致整个 `PositionControl` 组件在每次鼠标移动时重新渲染，画布 60fps 拖拽下产生大量不必要的渲染开销

### 5. 缩放比例失真

- 容器尺寸通过 `positionable.size` → `previewSize` → 800×600 回退链计算
- 缩略画布固定最大 280×200，极端长宽比（如移动端 375×812）下画布非常窄小
- 缩放后的方块位置与实际 DOM 渲染位置可能有亚像素误差

## 优化方案

### 方案 A：Pointer Events + CSS Transform（低成本、立即见效）

**改动范围**：仅 `ConfigForm.tsx` 的 `PositionControl` 组件

1. 将 `onMouseDown/Move/Up` 替换为 `onPointerDown/Move/Up`
2. 使用 `setPointerCapture(pointerId)` 解决边界外事件丢失
3. 拖拽过程中使用 ref 直接操作 `style.transform` 代替 React state 更新触发重渲染
4. 仅在 `pointerUp` 时提交最终位置到 `onPositionsChange`

```tsx
const handlePointerDown = (key: string, e: React.PointerEvent) => {
  (e.target as HTMLElement).setPointerCapture(e.pointerId);
  setDraggingKey(key);
  startPosRef.current = { x: e.clientX, y: e.clientY };
  origPosRef.current = { ...positions[key] };
};

const handlePointerMove = (e: React.PointerEvent) => {
  if (!draggingKey) return;
  const dx = (e.clientX - startPosRef.current.x) / scaleFactor;
  const dy = (e.clientY - startPosRef.current.y) / scaleFactor;
  // 直接操作 DOM 的 transform
  dragElRef.current.style.transform = `translate(${origPosRef.current.x + dx}px, ${origPosRef.current.y + dy}px)`;
};

const handlePointerUp = (e: React.PointerEvent) => {
  // 最终提交
  onPositionsChange({ ...positions, [draggingKey]: { x: snappedX, y: snappedY } });
  setDraggingKey(null);
};
```

**收益**：
- 触摸设备支持
- 拖拽不再丢失事件
- 60fps 拖拽零 React re-render

### 方案 B：ResizeObserver 推模式替代 postMessage 轮询

**改动范围**：`iframe-template.ts`、`PreviewPanel.tsx`

当前流程（拉模式）：
```
父窗口 → COLLECT_POSITIONABLE_SIZES → iframe → requestAnimationFrame → 等图片 → measureAndReport → POSITIONABLE_SIZES_RESULT → 父窗口
```

优化后（推模式）：
```
iframe → ResizeObserver on [data-pos-key] 元素 → 变化时主动 postMessage → 父窗口缓存 sizes
```

1. 在 iframe 初始化时为每个 `[data-pos-key]` 元素挂载 `ResizeObserver`
2. 元素挂载/卸载/尺寸变化时自动推送 `POSITIONABLE_SIZES_UPDATE`
3. 父窗口维护一个尺寸缓存 Map，不再需要主动发起 `COLLECT_POSITIONABLE_SIZES`
4. `PositionControl` 需要尺寸时直接从缓存读取

**收益**：
- 消除 500ms 超时兜底和图片加载等待逻辑
- 尺寸始终是最新的，无需轮询
- 减少 postMessage 往返次数

### 方案 C：预览直拖手柄层（体验最优、重构较大）

**核心思路**：废弃缩略画布，在预览 iframe 上方渲染透明的拖拽手柄叠加层，用户直接在真实预览上拖拽。

```
┌──────────────────────────────────────────────┐
│  PositionOverlay (与 iframe 等大，绝对定位)    │
│                                              │
│  ┌──────────────────────────┐                │
│  │  preview iframe          │                │
│  │  ┌────────┐              │                │
│  │  │ Header │ ← 真实渲染   │                │
│  │  └────────┘              │                │
│  └──────────────────────────┘                │
│  ┌────────┐  ← 拖拽手柄（与 Header 位置对齐） │
│  │ ╋════╋ │     半透明边框 + 中心拖拽点       │
│  └────────┘                                  │
└──────────────────────────────────────────────┘
```

**实现要点**：

1. **新增 `PositionOverlay` 组件**：在 `PreviewPanel` 中渲染，与 iframe 等大，`pointer-events: none` 容器内手柄元素 `pointer-events: auto`
2. **手柄位置同步**：接收 iframe 推送的 `POSITIONABLE_SIZES_UPDATE`（来自方案 B），将每个手柄对齐到对应元素的 iframe 内坐标
3. **坐标转换**：拖拽手柄时，将父窗口像素坐标转换为 iframe 内容坐标（考虑 iframe 缩放、滚动偏移）
4. **拖拽反馈**：手柄使用 Pointer Events + `setPointerCapture`，拖拽时实时更新位置
5. **保留坐标输入框**：在配置面板中保留精确 X/Y 输入（可选）

**UI 设计**：
- 默认模式：预览正常显示，不可拖拽
- 进入"定位编辑模式"（配置面板点击"编辑位置"按钮或直接在预览上双击手柄）：手柄层激活，显示半透明边框
- 支持吸附对齐：拖拽时计算与其他元素的边缘/中心对齐线
- 键盘微调：选中手柄后方向键 ±1px，Shift+方向键 ±10px

**收益**：
- 所见即所得，100% 准确的视觉反馈
- 不再需要缩略画布和缩放计算
- 可扩展吸附对齐、键盘微调等高级功能

### 方案 D：消除 `data-pos-key` 手动标记

**思路**：在 iframe 模板中自动为 positionable 元素包裹定位容器，无需用户手动添加属性。

当前：用户代码必须写 `<div data-pos-key="header">`  
优化后：模板自动在渲染时注入 `<div class="pos-wrapper" data-pos-key="header">` 包裹 positionable items 对应的根元素

具体做法：
1. 在 `renderComponent()` 之前，用正则或 Babel 在组件 JSX 根元素上注入 `data-pos-key`
2. 或者修改 demo 编译模板，在 iframe 沙箱中渲染时自动识别 positionable items 对应的组件并包裹

**风险**：自动注入可能误伤复杂组件结构，建议作为后续优化，不优先实施。

## 实施优先级

| 优先级 | 方案 | 工作量 | 收益 |
|--------|------|--------|------|
| P0 | 方案 A：Pointer Events + CSS Transform | 小（仅 PositionControl） | 解决拖拽性能、触摸支持、事件丢失 |
| P1 | 方案 B：ResizeObserver 推模式 | 中（iframe 模板 + 消息处理） | 消除尺寸收集时序问题和图片等待 |
| P2 | 方案 C：预览直拖手柄层 | 大（新增组件 + 坐标转换） | 体验质变，所见即所得 |
| P3 | 方案 D：自动注入 data-pos-key | 中（编译模板改造） | 降低用户使用门槛 |

建议按 P0 → P1 → P2 → P3 顺序逐步实施，每步可独立验证和上线。

## 风险与待确认

- 方案 C 的坐标转换需处理 iframe 缩放（`scale` 参数）和滚动偏移，边界情况较多
- 方案 B 的 ResizeObserver 在 iframe 内大量元素时可能有性能影响，需要评估元素数量上限
- 方案 C 若与已有视觉编辑模式（visualEditMode）、评论模式等 iframe 覆盖层冲突，需统一管理层级
- 当前缩略画布的网格和坐标输入仍需保留作为精确数值编辑入口（或作为方案 C 的降级方案）
