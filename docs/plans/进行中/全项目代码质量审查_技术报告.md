## 1. 执行摘要

项目可以完成生产构建，多个核心包的类型检查和单元测试也通过；但在 Web API、Agent 服务、截图服务和多用户工作空间之间，存在几条需要先处理的安全边界：

- Agent 服务的路由注册没有统一认证层；服务端还接受客户端传入的 `workingDir`，而 `X-API-Key` 只在客户端发送，服务端没有对应校验。
- 创作端的旧项目/模板管理接口没有在路由中验证登录身份，部分操作会以默认 `admin` Actor 执行。
- 知识库和工作区上下文接口允许请求方直接提交服务器路径；Live Workspace 的校验只把 session、项目和路径对上，没有把 session 与当前登录用户对上。
- JWT、管理员密钥和 Docker 配置仍存在可直接使用的默认/占位秘密；管理员密钥还通过 URL 参数传递并留在地址栏。
- Session 列表与工作区文件预览的用户隔离不完整，旧 Session 的 `userId` 可以为空并触发“有值才校验”的放行逻辑。
- 截图服务可以接收较大的页面源码和未限制数量的批量任务，且服务端没有认证；在端口可达时存在资源耗尽风险。

这些问题不是单纯的 UI 缺陷，而是可能影响项目数据、用户文件、模型费用和服务可用性的边界问题。未做破坏性动态利用验证，因此报告将“代码路径已确认”和“部署条件下的实际可利用性”分开表述。

### F-01 Agent 服务缺少统一认证，且接受客户端工作区路径（Blocker）

**证据**

- Fastify 启动代码只配置 CORS、WebSocket 和 multipart，没有认证 hook：[packages/agent-service/src/server.ts:48]`/Users/surainchang/Projects/OneFlow/packages/agent-service/src/server.ts`（第48行）。
- 所有 Agent、项目、协同、附件和 Workspace Authority 路由直接注册，没有统一鉴权包装：[packages/agent-service/src/routes/index.ts:14]`/Users/surainchang/Projects/OneFlow/packages/agent-service/src/routes/index.ts`（第14行）。
- 消息接口直接读取请求体里的 `workingDir`、`customWorkspace`、`projectId` 和 `mode`，非 `viewer-readonly` 模式下将路径交给工作区管理器：[packages/agent-service/src/routes/agent.ts:123]`/Users/surainchang/Projects/OneFlow/packages/agent-service/src/routes/agent.ts`（第123行）、[packages/agent-service/src/routes/agent.ts:169]`/Users/surainchang/Projects/OneFlow/packages/agent-service/src/routes/agent.ts`（第169行）。
- Docker 将服务端口映射到宿主机，并绑定 `0.0.0.0`：[docker-compose.yml:28]`/Users/surainchang/Projects/OneFlow/docker-compose.yml`（第28行）、[docker-compose.yml:35]`/Users/surainchang/Projects/OneFlow/docker-compose.yml`（第35行）。
- `agent-client` 会发送 `X-API-Key`，但在 `packages/agent-service/src` 中没有发现对应的 API key 校验；允许的 CORS header 不是认证。

**最小复现思路（未执行有副作用请求）**

1. 让 3201 端口对请求方可达。
2. 不携带 `X-API-Key`、JWT 或内部 token，向 `/api/agent/<任意 sessionId>/message` 发送普通 `workbench` 模式请求，并提供 `workingDir`。
3. 代码路径会进入 `manager.getOrCreate` 和 Agent 执行流程；预期应该在进入业务逻辑前返回 401/403。

**影响**

一旦端口可被不可信请求方访问，攻击者可能创建、读取、销毁 Agent Session，选择服务进程可访问的工作区，并触发具备写文件/命令能力的工作流。项目目录、用户文件、模型凭据和外部服务调用都可能被连带影响。

**建议方向**

在 Agent 服务入口建立不可绕过的服务认证；真正校验 `X-API-Key` 或短期签名，而不是只在客户端发送；将用户身份、项目、Session、workspace 绑定在服务端解析，禁止请求体自行决定任意绝对路径；Agent 服务默认只走内网，公开访问必须经过带用户身份的网关。`viewer-readonly` 的只读约束不应被视为通用 Agent 接口的安全边界。
