## 1. Review Session：独立于项目体系

Review Session 是一个全新的轻量概念，与现有 `Project`、`EditTransaction` 完全解耦。不修改 `project-core`，不扩展 `ProjectConfig`。Session 直接持有项目路径，不引入独立的项目注册抽象。

Session 没有固定有效期——只要 dev server 存活，session 就可用。dev server 由 agent-service 管理，Session 空闲（无 WebSocket 连接）超过 30 分钟后自动 kill。用户再次访问时自动重新 spawn dev server。链接可分享，多人同时打开、标注、对话，标注和消息各自携带操作者标识。

```typescript
// packages/shared/src/review.ts (新建)

interface ReviewSession {
  sessionId: string;
  /** Codex 项目根路径（绝对路径）*/
  projectPath: string;
  /** 项目显示名称，从 package.json 提取 */
  projectLabel: string;
  /** 项目框架类型 */
  framework?: "vite" | "next" | "custom";
  /** dev server URL（Session 生命周期内持续有效）*/
  devServerUrl: string;
  /** Codex 自动分析生成的页面清单 */
  manifest: ReviewManifest;
  /** session 创建者 */
  createdBy: string;
  createdAt: number;
  /** 构建快照版本链，每次编辑完成后自动追加 */
  snapshotVersions: SnapshotVersion[];
}

interface SnapshotVersion {
  /** 版本序号，从 1 开始递增 */
  version: number;
  /** 构建产物目录 */
  distPath: string;
  /** 对应的截图缓存 */
  screenshotCache?: Record<string, string>;
  /** 关联的任务 ID（哪个任务完成后触发的），初始版本为 null */
  taskId?: string | null;
  createdAt: number;
}

interface ReviewManifest {
  /** 项目名称 */
  projectName: string;
  /** 框架类型，用于 iframe 注入策略调整 */
  framework?: "vite" | "next" | "custom";
  pages: ReviewPage[];
  /** 标识 manifest 来源 */
  source: "codex-auto" | "manual" | "hybrid";
  /** 开发者手动编辑时间（详见 Manifest 开发者补充入口章节） */
  lastManualEditAt?: number;
}

interface ReviewPage {
  id: string;
  name: string;
  order: number;
  /** 页面预览尺寸，移动端活动通常 375 宽 */
  size: { width: number; height: number };
  states: ReviewPageState[];
}

interface ReviewPageState {
  id: string;
  label: string;
  /** 路由路径 */
  route: string;
  /** Mock 数据覆盖，通过 URL 参数或注入脚本传递 */
  mockOverrides?: Record<string, string | number | boolean>;
  /**
   * Codex 分析出的复现提示，纯文本展示给协作者。
   * 例如："点击'立即抽奖'按钮，等待弹窗出现"
   * 不做自动触发，协作者切换到单页模式后手动操作。
   */
  triggerHint?: string;
}
```

## 2. 统一入口：创作端首页项目列表

Codex 项目和创作端项目从**同一个入口**进入——创作端首页项目列表。不设独立入口页面。

```
创作端首页项目列表
┌──────────────────────────────────────────────────┐
│ 项目列表                                          │
│                                                  │
│ ┌──────────────────────────────────────────────┐ │
│ │ 🎨 新年活动页                   创作端项目     │ │  ← /demo/[id]/edit
│ │   修改于 2 小时前                             │ │
│ ├──────────────────────────────────────────────┤ │
│ │ 🔧 新年活动页 (业务代码)         Codex 项目    │ │  ← /review/[sessionId]
│ │   vite · 已连接 · v3                          │ │
│ ├──────────────────────────────────────────────┤ │
│ │ 🎨 暑期促销页                   创作端项目     │ │
│ │   修改于 3 天前                               │ │
│ └──────────────────────────────────────────────┘ │
│                                                  │
│  [+ 新建创作端项目]    [+ 新建 Codex 项目]         │
└──────────────────────────────────────────────────┘
```

**实现方式**：

- 前端并行请求两路数据源：
  - 创作端项目：来自 `project-core` API
  - Codex 项目：来自 agent-service `GET /api/review-sessions`（返回活跃的 Codex 项目会话列表）
- 两种项目通过列表项标签区分（`创作端项目` / `Codex 项目`）
- 点击 Codex 项目 → 路由到 `/review/[sessionId]`
- 点击创作端项目 → 路由到 `/demo/[id]/edit`（现有行为）

**创建入口**：

| 入口 | 操作者 | 实现方式 |
|------|--------|---------|
| **Codex IDE → MCP** | 开发者 | 在 Codex 中说"创建 Codex 项目" → Codex 检测项目路径 → 通过 MCP 工具调用 agent-service API |
| **创作端项目列表** | PM/设计师 | 点击「新建 Codex 项目」→ 弹出项目路径选择对话框 → agent-service spawn dev server + 生成 Manifest → 列表刷新，点击进入 |

两条路径最终都走到 agent-service 的同一套 API。agent-service 收到项目路径后：

1. spawn dev server（2-3s）→ Session 立即可用
2. 注册代理路由 → 项目就绪
3. 后台并行：`codex exec` 分析源码生成 Manifest
4. 后台并行：`npm run build` → 截图 → 画布渐进就绪
5. 编辑完成后：自动 `npm run build` → 新快照加入版本链
6. Session 销毁时清理所有 dist_v{N}/ 目录

## 3. Manifest 自动生成：全委托 Codex

开发者不需要手写 manifest。agent-service 调用 Codex CLI 分析项目：

```bash
codex exec \
  --json \
  --sandbox read-only \
  --cd /path/to/project \
  --ephemeral \
  "分析这个项目的所有页面路由和UI状态变体，输出 JSON manifest。
   识别内容：
   - 路由页面（routes.tsx、pages/、App Router 等）
   - 条件渲染分支（if/else、三元、&&短路）
   - API 数据状态（loading/error/empty/data）
   - 弹窗/模态框（Modal、Dialog、Drawer、visible={}）
   - 时间/用户状态（isExpired、isLoggedIn、vipLevel 等）
   - 每个状态需包含 route、mockOverrides、triggerHint（如何复现）

   输出格式：
   {
     \"projectName\": \"...\",
     \"framework\": \"vite|next|custom\",
     \"pages\": [{
       \"id\": \"...\",
       \"name\": \"...\",
       \"order\": 0,
       \"size\": { \"width\": 375, \"height\": 812 },
       \"states\": [{
         \"id\": \"...\",
         \"label\": \"...\",
         \"route\": \"/path\",
         \"mockOverrides\": { \"key\": \"value\" },
         \"triggerHint\": \"点击XXX按钮\"
       }]
     }]
   }"
```

**agent-service 的 Manifest 生成器只做：**

1. 调用 `codex exec`
2. JSON Schema 校验输出
3. 格式错误时重试一次（不同的 prompt 措辞）
4. 仍然失败则降级为最小 manifest（仅路由页面列表，无状态分支）
5. 结果缓存，session 有效期内复用

**不做任何自己的静态分析或 AST 遍历。**

### Manifest 开发者补充入口

Codex 自动分析可能不完整（遗漏某些状态变体、弹窗或边界情况）。开发者可通过以下方式补充：

Codex 项目页面左侧面板提供「编辑页面清单」按钮（仅创建者可见），点击后弹出结构化编辑器：

```
┌─────────────────────────────────────────┐

│                                         │
│  📄 首页                     [删除]      │
│    └ 默认状态                            │
│                                         │
│  📄 抽奖页                   [删除]      │
│    ├ 有抽奖次数               [删除]      │
│    ├ 次数=0                  [删除]      │
│    ├ 已结束                  [删除]      │

**2. 数据模型预留**

`ReviewManifest` 的 `source` 和 `lastManualEditAt` 字段已包含在共享类型定义中（见 §1 数据结构），开发者手动编辑时自动更新。无额外数据模型变更。

## 4. HTTP 代理层：始终代理 dev server

Session 创建时 spawn dev server，代理层始终激活。去掉了原方案的双模式（browsing/editing）切换，简化架构。**依赖**：`@fastify/http-proxy`（需新增），在 `registerRoutes()` 中注册代理路由。

```typescript
// packages/agent-service/src/review/proxy.ts (新建)

import fastifyHttpProxy from "@fastify/http-proxy";

export async function createSessionProxy(server: FastifyInstance, session: ReviewSession) {
  // 注册代理
  server.register(fastifyHttpProxy, {
    upstream: session.devServerUrl,
    prefix: `/review/${session.sessionId}/preview`,
    rewritePrefix: "/",
    websocket: true,  // HMR WS 自动升级透传
    replyOptions: {
      onResponse: (req, reply, res) => {
        if (isHtmlContent(res)) {
          injectAnnotationScript(reply, session.sessionId);
        }
      },
    },
  });
}
```

**历史版本浏览**：前端切换版本选择器后，请求 `/review/:sessionId/snapshot/:version/`，走静态文件服务直接 serve `dist_v{N}/` 目录。与代理路由互不影响。

## 5. 页面标注：代理注入 + 复用现有可视化编辑基础设施

### 与现有系统的关系

创作端现有的 iframe 预览系统（`@workbench/demo-ui`）已有完善的可视化编辑基础设施：

| 已有能力 | 位置 | 可用于 Review 标注 |
|---------|------|-------------------|
| iframe 同域通信（postMessage） | `PreviewPanel.tsx` | ✅ 同域，sandbox 含 `allow-same-origin` |
| 元素选择和 hover 高亮 | `iframe-template.ts` `__VISUAL_EDIT__` | ✅ 可复用选择器提取逻辑 |
| 标注覆盖层（annotation layer） | `iframe-template.ts` | ✅ 已有 DOM 结构可参考 |
| 脚本注入机制 | `iframe-template.ts` import map + 自执行脚本 | ✅ 模式可直接借鉴 |

**关键差异**：现有创作端预览走「编译 → postMessage 发送代码 → iframe 动态 import」路径，Codex 项目走「HTTP 代理 → dev server 直接渲染」路径。前者的脚本注入在 `iframe-template.ts` 构建 HTML 时完成；后者需要在代理层注入。

### Codex 项目标注实现

由于代理层确保了同域，标注脚本可以直接访问 iframe 内的 DOM。注入方式：代理层在 HTML 响应中注入 `annotation.js`，或复用在 iframe 初始化时注入脚本的模式。

```
协作者操作                        系统行为
───────────────────────────────────────────────────
在画布某页上点击元素              → annotation.js 提取
                                    { selector, boundingRect, textContent, tagName }
                                  → 在元素上画高亮边框（复用现有 hover box 模式）
                                  → 弹出标注气泡输入框

输入修改意见并提交                → 标注数据通过 postMessage 发送到 author-site
                                  → 挂载到当前 AI Chat 消息上下文
                                  → Pi Agent 看到带标注的指令

任务执行完成 / HMR 更新            → iframe 刷新
                                  → 已解决的标注自动移除
```

### 标注脚本隔离策略

Codex 项目的 iframe 使用 `sandbox="allow-scripts allow-same-origin"`（与现有预览一致），iframe 本身提供天然隔离边界，不需要 Shadow DOM 做样式隔离。标注脚本通过 IIFE 封装，挂载到 `window.__REVIEW_ANNOTATION__` 命名空间下，避免与目标页面 JS 冲突。

```typescript
// 注入的标注脚本结构（参考现有 iframe-template.ts 模式）
window.__REVIEW_ANNOTATION__ = (function() {
  // 高亮框、标注气泡、元素选择器提取
  // 与父窗口通信: postMessage({ type: "REVIEW_ANNOTATION_CREATE", ... }, "*")
})();
```

```typescript
// 标注数据结构（多人标注，各自携带用户标识）

## 6. 画布多 iframe 预览

两种互补的渲染模式，不是二选一：

| | 画布网格 | 单页模式 |
|------|------|------|
| **用途** | 快速浏览所有页面和状态变体 | 精确标注、手动交互触发弹窗 |
| **渲染方式** | Session 创建后后台生成的截图（渐进就绪） | 实时 iframe（通过代理层） |
| **支持点击标注？** | 不支持（截图没有 DOM） | 支持 |

**核心原则：标注必须基于实时 iframe 的 DOM。** 截图只能加速浏览，不能替代交互式标注。

```
画布视图 (manifest pages × states)
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 首页 /       │ 抽奖-有次数   │ 结果-中奖     │ 抽奖弹窗      │
│              │ /lottery     │ /result      │ triggerHint:  │
│  [截图]      │  [截图]      │  [截图]      │ 点击抽奖按钮   │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 抽奖-次数=0  │ 抽奖-已结束   │ 结果-未中奖   │ (空)          │
│ /lottery     │ /lottery     │ /result      │              │
│  [截图]      │  [截图]      │  [截图]      │              │
└──────────────┴──────────────┴──────────────┴──────────────┘

画布网格：截图占位，快速加载，不需要 dev server 持续运行
单页模式：点击某页 → 加载实时 iframe → 可点击元素标注、手动触发弹窗
```

**MVP 阶段策略**：

- Session 创建时：spawn dev server（2-3s）→ 代理立即可用 → 单页预览就绪
- 后台并行：`npm run build` → 依次截图各页面状态 → 画布网格渐进填充
- 用户打开画布：有截图就展示截图，没有就显示加载占位符
- 点击进入单页模式：实时 iframe 预览，允许标注和交互

## 7. Pi Agent 翻译官模式

Pi Agent 仅做需求澄清和 Task 组装。**实现方式**：新增 `reviewer-codex` 模式，复用现有 `AgentMode` 体系（参考 [viewer-readonly-mode.ts](file:///e:/重要文件/Programming/1_Work/opencode-workbench/packages/agent-service/src/services/viewer-readonly-mode.ts)），在 `normalizeAgentMode()` 和 `createWorkbenchTools()` 中追加。

```
你是「页面修改请求协调员」。你的唯一职责是确保用户对页面的修改需求明确无歧义，然后转交给 Codex 执行引擎处理。

【你可以做的事】
1. 理解用户描述的页面修改需求。如果消息附带标注数据

   - 有没有参考？
3. 需求确认后，将用户意图翻译为清晰的技术执行指令，
   附上标注上下文（选择器、路由）
4. 告知用户任务已提交、排队中、已完成等状态

【你绝对不能做的事】
- 编写任何代码
- 修改任何文件
- 提出自己的设计方案
- 绕过任务队列直接操作工作空间

【你的工具限制】
仅对话工具，无文件读写、bash、工具执行权限

【需求分类规则 — 你必须遵守】
在确认需求后，你必须判断该需求属于以下哪一类：

📌 第一类：纯 UI 修改（可以直接提交任务）
- 颜色、尺寸、间距、圆角、阴影等视觉样式
- 文案/文本内容修改
- 静态布局调整（flex/grid 排列）
- 图标、图片替换
- 动画/过渡效果调整
→ 判断标准：不涉及分支逻辑、数据流、API 调用、状态管理
→ 动作：确认需求后直接提交 Task 到执行队列

🔒 第二类：功能逻辑修改（必须留存待开发者处理）
- 交互行为/事件处理逻辑变更
- 条件判断/分支逻辑（if/else、权限判断等）
- API 调用、数据获取/提交逻辑
- 状态管理（useState、Redux、Zustand 等）
- 表单校验规则
- 路由跳转逻辑
- 新增/删除功能模块
→ 判断标准：涉及任何代码逻辑、数据流、API 或状态变更
→ 动作：明确告知用户"该需求涉及功能逻辑，已保存为待处理任务，开发者会跟进处理"

⚠️ 边界情况：如果无法明确判断属于哪一类，默认归为第二类（留存）。

## 10. 版本链：快速查看 + 历史回看

每次编辑完成后自动触发 `npm run build`，产物存为 `dist_v{N}/` 并追加到 `snapshotVersions` 数组。创建时的初始 build（后台异步）形成 `v1`。

**前端版本选择器**，位于页面顶部工具栏：

```
[版本: v3（当前）▾] [已连接] 🔗
 ├── v3  2026-07-25 15:32  任务#2 完成后（当前）
 ├── v2  2026-07-25 15:10  任务#1 完成后
 └── v1  2026-07-25 14:50  初始版本
```

- **当前版本（最新）**：始终走 HTTP 代理 → dev server 实时预览，支持标注和交互
- **历史版本**：静态文件服务 serve `dist_v{N}/`，iframe DOM 完整，标注脚本也正常工作
- 切换版本时 iframe 重新加载，标注按 `pageStateId` + `pageRoute` 匹配，自动过滤不适用当前版本的标注

**路由设计**：

| 路由 | 渲染方式 | 用途 |
|------|---------|------|
| `/review/:sessionId/preview/` | HTTP 代理 → dev server | 当前版本实时预览 |
| `/review/:sessionId/snapshot/:version/` | 静态文件 serve dist_v{N}/ | 历史版本回看 |

## 11. 修改回退

对 Codex 修改结果不满意时，不需要专门的回滚功能——**回退就是再提一个任务**。

```
协作者发现修改不符合预期：
1. 在 AI Chat 中描述回退需求：
   "把提交按钮改回原来的样式"
   "撤销上一次对抽奖页面的修改"
2. Pi Agent 将其作为新任务（category: "ui"）提交到队列
3. Codex 执行 → HMR 实时刷新 → 协作者确认
```

**设计理由**：
- 所有项目仓库均有 git 管理，极端情况下开发者随时可手动处理
- 不在 agent-service 中引入 git stash/pop 操作，避免状态管理的复杂度
- 用户体验与提新任务完全一致，无需额外学习成本
- 旧版本的历史 build 快照（dist_v{N}/）和版本链仍可用于对照和参考

## 12. 与创作端编辑页的组件复用

开发项目页面与创作端编辑页共享同一套骨架，组件复用度约 70%。

### 三栏骨架对比

```
创作端编辑页                           开发项目页
┌────────┬──────────┬────────┐        ┌────────┬──────────┬────────┐
│ 左侧   │  预览区   │  右侧   │        │ 左侧   │  预览区   │  右侧   │
│        │          │        │        │        │          │        │
│ Tabs:  │ Canvas/  │ Tabs:  │        │ Tabs:  │ Canvas/  │ Tabs:  │
│  AI    │ Single   │  编辑   │        │  AI    │ Single   │  编辑   │
│  页面  │          │  配置   │        │  页面  │ (代理    │  任务   │
│  文件  │          │        │        │        │  模式)   │        │
│  版本  │          │        │        │        │          │        │
└────────┴──────────┴────────┘        └────────┴──────────┴────────┘
```

### Tab 级对比

| 区域 | 创作端编辑页 Tab | Codex 项目页 Tab | 复用方式 |
|------|-----------------|-----------------|---------|
| **左侧栏** | `AI` — `<AIChat>` | `AI` — `<AIChat>` | ✅ **完全复用** |
| | `页面` — `<DemoPageTree>` (数据源: project-core) | `页面` — 复用 Tree 组件 (数据源: Manifest) | 复用组件，替换数据源 |
| | `文件` — `<KnowledgePanel>` / `<WorkspaceFileTree>` | — 不需要 | 隐藏此 Tab |
| | `版本` — 内联版本历史 | — 不需要（顶栏有版本选择器） | 隐藏此 Tab |
| **右侧栏** | `编辑` — `<VisualPropertyPanel>`（直接修改项目数据） | `编辑` — `<VisualPropertyPanel>`（仅预览生效，不写代码） | 复用组件，修改落点为本地预览状态 |
| | `配置` — `<PageConfigPanel>` | `任务` — `<TaskPanel>` (新建) | 配置 Tab 替换为任务列表 |
| **预览区** | Canvas: `<PreviewCanvas>` | Canvas: `<PreviewCanvas>` (截图网格) | ✅ **完全复用** |
| | Single: `<PreviewPanel>` (编译沙箱) | Single: `<PreviewPanel>` (代理模式, 新增 renderMode) | 复用外壳，扩展渲染模式 |
| **顶栏** | 项目名称 | 项目名称 + `[版本: v3 ▾] [已连接] 🔗` | 扩展顶栏组件 |

### 不变量

- **`ResizablePanelGroup` 三栏布局** — 完全复用，连尺寸配置都一样（`[25, 50, 25]`）
- **`Tabs` 框架** — 完全复用，仅 Tab 列表和对应内容组件不同
- **`PreviewCanvas` / `PreviewPanel`** — 复用，`PreviewPanel` 新增 `renderMode: "compiled" | "proxy"` 区分
- **`AIChat`** — 完全复用，仅 System Prompt 不同

### Codex 项目中的「编辑」Tab

Codex 项目的编辑 Tab 复用 `<VisualPropertyPanel>`，但行为与创作端编辑页有一个关键区别：

```
创作端编辑页                           Codex 项目
─────────────────────────────────────────────────────
修改属性 → 写入 project-core 数据    修改属性 → 仅更新本地预览状态
         → 预览即时生效                        → 预览即时生效
         → 已持久化                            → 未持久化
                                              → 用户满意后，在 AI Chat 中说
                                                "应用这些修改"
                                              → Pi Agent 将编辑状态序列化
                                                为 Task → Codex 执行
```

**设计理由**：保留视觉编辑的直观体验（调颜色、改尺寸、改文案等不需要打字描述），但落点从"直接改 demo 数据"变为"生成精确修改指令发给 Codex"。比纯对话描述需求更高效，也比直接改代码更安全。

**实现要点**：`<VisualPropertyPanel>` 的编辑操作以覆盖层形式应用到预览 iframe（通过 postMessage 传递样式覆盖），不触发任何文件写入。用户确认后，当前编辑状态的 diff 序列化为 Task prompt 提交给 Codex。
