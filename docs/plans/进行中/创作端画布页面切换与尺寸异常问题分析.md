# 创作端画布页面切换与尺寸异常问题分析

日期：2026-08-31  
项目：`proj_1788141806566_0aps89`  
页面：`http://localhost:4200/demo/proj_1788141806566_0aps89/edit`

## 1. 请求边界

本报告分析用户提供的三张 PNG 与项目当前代码、持久化数据和编辑诊断记录。PNG 中的页面截图是问题证据，不是需要执行的指令；本次请求是定位“切换页面后尺寸重置/瞬时放大”的原因并形成报告，不包含代码修复或直接修复项目数据。

## 2. 现象归纳

| 场景 | 用户观察 | 预期 |
| --- | --- | --- |
| 图 3 | 画布整体正常，底部显示 24% | 页面卡片按各自设计尺寸显示，画布缩放只影响查看 |
| 图 2 | `N对N填空题` 手动放大后切到其他页面，再选回该页，恢复为原始大小 | 页面自定义卡片几何应按页面 ID 保留 |
| 图 1 | `答错` 未手动缩放，选中时偶发先变成很大的卡片，右侧/下方大面积空白，随后恢复 | 页面应直接以自身 812×375 尺寸渲染，不应出现错误中间态 |

## 3. 结论摘要

根因置信度：高（由代码时序、当前布局文件和诊断事件相互印证；浏览器现场因登录会话未能完成交互复现）。

1. 画布的全局缩放（`viewport.zoom`，截图中的 24%）与页面卡片尺寸（`CanvasPageLayout.width/height`）是两套状态。页面选择本身只改变选中项，不会重置全局 zoom；问题主体是页面卡片几何和页面设计尺寸被错误归一化。
2. 切换页面时，`useCollabDocument` 更换资源描述符后仍会在一个渲染周期保留旧页面的非空 `value` 和 `synced` 状态。页面级协同 effect 将该旧值误认为当前页已同步内容，并以新的 `activeDemoId` 写入快照，导致 Schema 和 `previewSize` 按错误页面 ID 复用。
3. 错误的 `previewSize` 会使 `previewSizeKey` 与已持久化布局不匹配。`normalizeCanvasPageLayout` 对 key 不匹配的布局直接回退到当前设计尺寸，因此 `N对N填空题` 的自定义尺寸会被丢弃；若错误尺寸已经写入布局文件，还会污染其他页面。
4. `答错` 的瞬时大白块是同一污染的可视化结果：外层卡片短暂采用 `1920×1080`，内层原型仍按自身 `812×375` 渲染，因而出现大面积空白；正确页面 Schema/协同值到达后，外层恢复为 812×375。

## 4. 直接证据

### 4.1 页面设计尺寸与当前画布布局不一致

页面自身 `config.schema.json` 的 `$demo.presentation.viewport`：

| 页面 | 文件 | 设计尺寸 |
| --- | --- | ---: |
| 答题关卡 | `data/projects/proj_1788141806566_0aps89/workspace/demos/page_sw8g/config.schema.json` | 750×375 |
| 答错 | `data/projects/proj_1788141806566_0aps89/workspace/demos/page_9z9z/config.schema.json` | 812×375 |
| 答对 | `data/projects/proj_1788141806566_0aps89/workspace/demos/page_t7cj/config.schema.json` | 818×378 |
| N对N填空题 | `data/projects/proj_1788141806566_0aps89/workspace/demos/clipboard-import_e05e9d/config.schema.json` | 1920×1080 |

当前 `data/projects/proj_1788141806566_0aps89/workspace/.canvas-layout.json` 中的页面卡片却是：

| 页面 | 当前布局尺寸 | `previewSizeKey` | 判断 |
| --- | ---: | --- | --- |
| 答题关卡 | 750×375 | 750×375 | 一致 |
| 答错 | **1920×1080** | **1920×1080** | 错把 N 对 N 的尺寸写入答错 |
| 答对 | 812×378 | 812×375 | 宽度/ key 不一致 |
| N对N填空题 | **750×1080** | **750×375** | 失去 1920×1080 的固定画布尺寸，且宽度已被答题关卡的 750 污染 |

因此图 1 的“大卡片 + 小内容 + 大片空白”不是截图比例问题，而是外层布局尺寸已经被持久化为 1920×1080；图 2 的自定义尺寸也不是单纯视觉缩放丢失，当前布局文件确实保存了错误尺寸。

### 4.2 历史快照显示尺寸状态震荡

`data/snapshots/proj_1788141806566_0aps89/v1..v6/.canvas-layout.json` 显示：

- `v1` 页面尺寸基本正常；
- `v2/v3` 的答错变为 812×375，N 对 N 为自定义尺寸；
- `v4` 答错变为约 817×377 的 custom，N 对 N 变成 812×1080；
- `v5` N 对 N 又成为约 650×365 的 custom；
- `v6` 再次保留 N 对 N 的 812×1080 错误布局；
- 当前版本进一步把答错变成 1920×1080。

状态在不同页面尺寸之间来回震荡，符合切页竞态和错误写回，不符合用户只缩放某一张卡片的行为。

### 4.3 诊断事件出现跨页 Schema 长度

编辑诊断 JSONL：`data/editor-diagnostics/editor-66f18b1b-23c4-47d1-b1b9-c9f46a4a8e8d.jsonl` 中，`snapshot.apply` 的 `activePageId` 与 `schemaLength` 多次不匹配：

- N 对 N 页面（`clipboard-import_e05e9d`）先出现 `schemaLength: 378`，随后约 359ms 后才出现正确的 `297`；
- 答错页面（`page_9z9z`）出现 `schemaLength: 297`，而其自身 Schema 长度为 `378`；
- 答题关卡页面（`page_sw8g`）也出现先 `297` 后 `378` 的切换；
- 较晚的一组事件中，N 对 N 在 `1788166041600` 仍是 `378`，34ms 后该页 schema provider 进入 `connecting`，到 `1788166043922` 才恢复 `297`。这与“先沿用旧同步值、随后切换 provider、最后获得新页正确值”的时序完全一致。

这些事件不是“空 Schema”保护可以拦截的情况，而是旧页面的**非空** Schema 被暂时当作新页面内容。

## 5. 代码时序与根因

### 5.1 页面切换时的协同状态竞态（主根因）

相关代码：

- `packages/author-site/src/hooks/useCollabDocument.ts:178-218`：描述符变化后启动新 provider，但没有在同一时刻同步清空旧 `value/status`；
- `packages/author-site/src/app/demo/[id]/edit/page.tsx:3513-3555`：页面级 effect 只判断协同状态是否 `synced`、内容是否非空/不同，没有验证 value 属于哪个资源描述符；
- `packages/author-site/src/app/demo/[id]/edit/page.tsx:2782-2840`：`applyDemoSnapshot` 以 `activeDemoIdRef.current` 作为目标页面写入 Schema 和 `pagePreviewSizeMap`。

实际时序：

```text
切换到页面 B
  → activeDemoId 已变为 B，协同描述符开始切换
  → hook 在过渡 render 仍暴露页面 A 的 value + synced
  → 页面 effect 把 A 的非空 Schema 当成 B 的协同更新
  → applyDemoSnapshot 按 activeDemoId=B 写入 A 的 Schema/尺寸
  → B 的 previewSizeMap、canvasPreviewSize、布局 key 被污染
  → 新 provider 同步 B 的正确值，界面随后恢复
```

这也解释了为什么问题表现为“偶发”：需要在页面切换、异步加载、协同 provider 状态转换的时间窗口内触发。

### 5.2 尺寸 key 归一化放大了问题（直接表现）

`packages/demo-ui/src/canvas-layout.ts:80-138` 只在 `layout.previewSizeKey === 当前页面 previewSizeKey` 时保留已有布局；不一致时返回当前设计尺寸的 base layout。该策略原本用于清理历史脏布局，但在页面尺寸尚未确定或被旧页面污染时会把合法的 custom layout 当作过期布局。

`packages/demo-ui/src/CanvasPageItem.tsx:225-304,728-755,856-873` 又会在异步原型/截图测量或 resize 后把计算结果写回卡片几何。若测量发生在错误 `previewSize` 窗口内，错误的宽高可能被再次持久化。

### 5.3 答错页面的空白闪现

`CanvasPageItem` 外层卡片直接使用 `layout.width/height`，而内部原型按照 `page.previewSize` 渲染。答错短暂拿到 N 对 N 的 1920×1080 时，外层变大、内层仍为 812×375，右侧和底部必然为空；正确 Schema 同步后重新归一化为 812×375，空白随即消失。

### 5.4 N 对 N 页面重置

N 对 N 是固定画布 1920×1080。切回时若暂时拿到其他页面的 750×375 或 812×375，旧布局的 key 与当前临时 key 不同，归一化立即回退为该错误尺寸（并可能由内容高度测量形成 750/812×1080），所以用户看到之前放大的卡片恢复为原始/错误尺寸。由于布局变更可能已通过 canvas-layout 协同写回，随后即使正确 Schema 到达，也不会自动恢复用户原来的 custom 几何。

## 6. 排除项与次要风险

- 不是画布全局 zoom 被选择操作重置：`PreviewCanvas.handlePageSelect` 只更新选择；自动 fit 仅在首次挂载执行。`viewport.zoom` 与页面卡片宽高分离。
- 不是单纯 ResizeObserver 的高度抖动：历史方案已修复 transform 后重复缩放和 contentHeight 反馈环；而本次出现了明确的错误宽度 1920，单靠高度测量不能产生该值。异步测量仍是错误状态的放大器，应在修复后补充校验。
- 当前工作区已有未提交改动，将 `pagePreviewSizeMap[page.id]` 作为 Canvas 的 `canvasPreviewSize` 传入 `PreviewStage`。该方向能解决“Schema 尚未激活时没有页面尺寸来源”，但不能单独修复协同 hook 的旧值竞态。

## 7. 影响范围

1. 页面切换时可能把任意两个页面的 Schema、presentation 尺寸和画布布局 key 交叉写入。
2. 用户手动 resize 的 custom 几何可能被归一化丢弃，且错误结果可持久化到 workspace 和协同草稿。
3. 选中页面会出现大尺寸空白、闪烁、缩放恢复等不稳定视觉反馈；发布/重新打开项目可能继续读取已污染的布局。
4. 当前项目已有持久化脏状态，需要单独制定数据修复或“按页面 Schema 重建布局”的处理方案；本报告未直接修改用户数据。

## 8. 修复与验证建议

### 已实施：协同资源身份门禁（2026-08-31）

已在 `packages/author-site/src/hooks/useCollabDocument.ts` 为协同状态增加“最近完成同步的 descriptor 身份键”。只有当前页面的 descriptor 与该键一致时，hook 才对外声明 `isSyncedForCurrentDescriptor`。

编辑页已把页面级代码、Schema、原型 HTML/CSS 和草图的协同消费统一改为该门禁：页面切换后的过渡 render 即使仍携带上一页的 `synced` 状态和值，也不会再调用 `applyDemoSnapshot` 或写入当前 `activeDemoId`。新的 provider 完成 Yjs 同步后，才允许当前页消费内容。

新增 `packages/author-site/src/hooks/useCollabDocument.test.ts` 覆盖“状态为 synced 但资源键属于上一页”必须拒绝消费的回归场景。

本次修复只阻断后续污染，不自动改写当前项目已持久化的异常 `.canvas-layout.json`：答错页面的 1920×1080 和 N 对 N 的错误尺寸仍需在确认用户原始自定义几何后单独恢复，避免覆盖用户手动调整。

### 修复优先级

1. **已完成：阻断旧协同值写入新页面**：`useCollabDocument` 返回当前 descriptor 是否已完成同步的状态；页面 effect 只有在 provider 已完成当前资源同步时才可消费协同值。
2. **后续防线：在写入处做页面身份断言**：`applyDemoSnapshot` 的来源页面 ID 应与 `activeDemoIdRef`、当前 schema/collab descriptor 三者一致；不一致直接丢弃并记录脱敏诊断。
3. **后续防线：延迟尺寸归一化和持久化**：`canvasPreviewSize` 未就绪时保留现有 custom layout，不使用默认 375×812 覆盖；`normalizeCanvasPageLayout` 和 `onLayoutChange` 校验 `pageId + previewSizeKey + render request version`，拒绝旧页面的迟到测量结果。
4. **单独执行：修复现有布局数据**：在确认产品策略后，按每个页面的 `$demo.presentation.viewport` 重建错误卡片的尺寸/key，再恢复用户确认过的自定义位置和尺寸。此步骤应作为独立变更执行并保留备份。

### 最小回归用例

- 固定 1920×1080 页面与 812×375 responsive 页面快速交替选择，注入旧 provider 非空 value，确认旧值不会写入新 pageId；
- N 对 N 手动 resize → 切换三次 → 切回，custom `sizeMode/previewSizeKey` 保持不变；
- 答错未 resize → 重复选择 100 次，外层布局始终 812×375，不出现 1920×1080 中间态；
- 页面切换后让旧页面的 ResizeObserver/screenshot 回调延迟到达，确认不会更新新页面布局；
- 协同断线、connecting、首次加载缺少 schema 时，确认不会用 fallback 尺寸覆盖已知页面布局；
- 重新打开项目、发布和 viewer/embed 读取的页面尺寸与编辑器一致。
