# 编辑会话过期问题修复记录

> 问题：长时间停留在项目编辑页（>2h），保存/同步失败提示「工作区已过期」，用户感知为"登录态丢失"。
> 根因、修复方案、验证结果与后续跟进事项。

---

## 一、背景

编辑页停留超过 2 小时后，用户做保存/同步操作时失败，提示「当前工作区已过期，请刷新项目后重试」。同时可能伴随协同认证失败、刷新后 session 重建等连锁反应。

## 二、根因

系统存在**两个独立会话概念**，混淆是问题的根源：

| 概念 | TTL | 存储位置 | 保护范围 |
|------|-----|---------|---------|
| 登录 JWT (`auth_token` cookie) | **7 天** | 浏览器 cookie | middleware、所有 API 路由 |
| 编辑会话 (`sessionId`) | **2 小时** | `data/sessions/.../.session.json` | 协同 WS token、保存/同步管道 |

**"登录态丢失"表象是编辑会话静默过期，而非 JWT 登出。** 失效链：

1. 用户停留 > 2h → `SESSION_EXPIRY_MS = 2 * 60 * 60 * 1000` 到期。
2. `renewEditSession` 唯一调用点在 `flushWorkspaceBeforeCriticalAction`（`workspace-flush.ts:255`），只在主动 flush 时触发，idle 期间无任何续期。
3. 用户编辑触发 debounced sync（`syncWorkspaceToProject`，3 步依次执行）：
   - Step 1 `persistActivePageToSession` → `PUT /api/sessions/{id}/files/{demoId}` → `isSessionExpired`（route.ts:354）→ **410 SESSION_EXPIRED** → 管道提前终止
   - Step 2 `flushWorkspaceCollab` 本可续期（`renewEditSession` 在 flush 内），但不到达
4. 协同 WS token = sessionId 固定（`useCollabDocument.ts:211`），过期后重连 → agent-service `validateWorkspaceSession` 拒绝 → `SESSION_EXPIRED` → socket 1008 → "协同认证失败"
5. 刷新页面 → `findActiveSession`（`session-manager.ts:244`）归档过期 session 并删除 workspace → 旧协同状态丢失，看起来像全新开始

## 三、修复方案

### 方案 A：客户端周期性续期（已实施，最小改动）

**思路**：加轻量 `POST /api/sessions/{id}/renew` 端点，客户端每 30 分钟调用一次，在 session 过期前主动续期。

### 改动文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `packages/author-site/src/app/api/sessions/[sessionId]/renew/route.ts` | 新增 | 验证 JWT + session 所有权 → `renewEditSession` → 返回新 expiresAt |
| `packages/author-site/src/app/demo/[id]/edit/page.tsx:955-968` | 新增 | `useEffect` 依赖 `sessionId`，启动时立即续期，之后每 30 分钟 `setInterval` 续期 |

### 续期间隔说明

选择 30 分钟的理由：`SESSION_EXPIRY_MS = 2h`，30 分钟间隔有 4 次余量，即使网络抖动漏掉一次，下次续期也能补上。续期端点无副作用，仅写文件 + 返回新 expiresAt。

### 方案 B（未实施，可选兜底）

过期后静默重建 session + 重连协同 WS，不打断用户编辑。复杂度较高，涉及 sessionId 状态变更、WS provider 重建、多组件同步。建议作为二期改进。

## 四、验证结果

### 测试

- `pnpm check:author`：**991 通过**，1 个预存 Figma 测试失败（无关，URL 不匹配）
- 新增路由：单元测试覆盖（通过 `renewEditSession` 已有测试间接验证）
- 客户端 effect：无直接测试，但 `useEffect` 依赖简单，仅 `sessionId` 状态变化触发

### 手动验证步骤

```bash
# 1. 启动服务
pnpm dev

# 2. 打开编辑页，观察控制台
# 应看到立即发出一次 POST /api/sessions/{id}/renew，30 分钟后再次发出

# 3. 验证续期效果
# 直接检查 .session.json 的 expiresAt 是否被延后
cat data/sessions/{userId}/{projectId}/{sessionId}/.session.json | grep expiresAt

# 4. 验证 session 过期后保存会失败
# 等待 2h 或手动修改 expiresAt 为过去时间
# 编辑内容 → 保存 → 应看到 "保存失败" toast
# 刷新页面 → session 应自动重建
```

### 已知风险

- 续期请求失败（网络中断）时静默 `catch`，不干扰用户。下次 30 分钟周期会自动重试
- 极端情况：连续多次续期失败 + session 到期 → 退回原行为（保存失败 + 需刷新）。概率极低
- 如果用户停留在编辑页超过 2h 且网络断开，刷新后仍会创建新 session，丢失旧协同状态
