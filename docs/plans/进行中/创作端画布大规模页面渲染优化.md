# 创作端画布大规模页面渲染优化

## 背景

创作端画布浏览模式当前最多处理几十页级别的场景，调度策略围绕 iframe 池和截图降级设计。用户实际场景需要支持 **50-100 个页面** 在画布中流畅展示，现有方案存在架构瓶颈。

实际场景中大部分页面为原型页（Shadow DOM），React 页占少数。`50-100 个 React 页`是极端情况，不作为主要优化目标。

## 目标

支持画布中展示 50-100 个页面依然流畅，包括：

- 画布加载、缩放、平移不卡顿
- 页面选中、拖拽、切换编辑态响应及时
- 截图服务不成为瓶颈（减少不必要的截图请求）

## 现状

### 页面类型

三种运行时类型，渲染方式不同：

| 类型 | 渲染方式 | 复杂度 |
| --- | --- | --- |
| `prototype-html-css` | Shadow DOM，内联 HTML+CSS，无 iframe | **低** — 无 JS 执行、无网络请求、直接 mount DOM |
| `sketch-scene` | 基于 sketch-core 的 Canvas/SVG 渲染 | 中 — 需要 sketch-core 渲染引擎 |
| `high-fidelity-react` | iframe + 编译代码（PreviewPanel） | **高** — iframe 创建开销、编译、JS 执行、内存占用 |

### 当前画布渲染调度

入口：`canvas-render-scheduler.ts` → `computeCanvasRenderModes`

**页面数 < 6 时**：全部实时渲染

- 原型/草图页 → `"prototype"`
- React 页 → `"iframe"`

**页面数 >= 6 时**（已修改）：

- **原型/草图页**：始终 `"prototype"`，不再使用截图降级
- **React 页**：按距视口中心距离排序，前 12 个 `"iframe"`，其次 12 个 `"sleeping-iframe"`，其余有截图 `"screenshot"`、无截图 `"loading"`（第 122-154 行）

### 关键问题

1. ~~**原型页截图是不必要的复杂度**~~ ✅ 已解决：原型/草图页始终返回 `"prototype"`，不再检查 `screenshotUrls` 降级。同时 `buildScreenshotBatchPages` 和 `scheduleScreenshotRegenerate` 已过滤原型/草图页，不再为其生成截图。

2. **原型页大规模 mount 影响滚动帧率**：虽已有 `getVisiblePageIds` 视口裁剪（200px 缓冲区）和 `visible` prop 控制，但 100 个原型页的可见集合内可能仍有数十个页面挂载完整 Shadow DOM，累积 layout/paint 开销影响滚动性能。不能用 JS 条件渲染做回收——缩放/平移时频繁 mount/unmount 会更加卡顿。

3. **缩放/平移期间 iframe 回收会加剧卡顿**：当前 iframe 池在每次调度重算时都可能回收/重建 iframe。用户缩放/平移过程中应避免销毁已激活的 iframe，只在不活跃期执行回收。

## 关键约束

- **不要为无需截图的页面类型生成截图**：原型页是 Shadow DOM，不经过 iframe 编译流水线，截图完全没有性能收益，纯属额外开销。
- **截图只保留给 React 页的 iframe 降级**：React 页有 iframe 创建/编译/内存开销，截图降级有意义。
- **缩放/平移过程中禁止回收 DOM 或 iframe**：任何在用户交互期间触发的大规模 mount/unmount 或 iframe 销毁重建都会加剧卡顿。回收逻辑应在用户停止操作后（约 500ms 空闲）执行。
- **不要增加截图服务的负载**：去掉原型页截图需求后，截图服务只需为 React 页生成，负载下降。

## 当前结论

原型页的截图降级是不必要的架构复杂度。画布大规模渲染的核心方向应该是：

- **原型页**：始终 `"prototype"`（Shadow DOM），通过 CSS `content-visibility: auto` + `contain-intrinsic-size` 减少离屏 layout/paint 开销，不回收 DOM。缩放/平移期间无 JS 层 mount/unmount，保持流畅。
- **React 页**：保留 screenshot/iframe/sleeping-iframe 池。用户交互期间（缩放/平移）不回收已激活 iframe，仅在不活跃期（停止操作约 500ms）执行 LRU 回收。
- **所有页面**：在用户可见交互期间避免任何 DOM 销毁或 iframe 重建，防止加剧卡顿。
