# 创作端画布 - 页面完整内容高度测量根治方案

> 模块：创作端画布 / 预览测量
> 日期：2026-08-06
> 状态：进行中
> 方案性质：架构级根治（测量统一 + 视口锁定），非单点补丁

---

## 一、背景与问题

创作端画布按"页面完整内容高度"显示每个页面卡片，让用户一眼看到整页。这个设计对普通网页正确（内容多高卡片多高），但**对"占满一屏"的页面（如 PPT 幻灯片、`100vh` 整屏页）会出问题**：页面被画布拉成异常高的长条（以「OneFlow 介绍」项目为实例，16:9 幻灯片被拉到约 4157px，约为设计高度 1080 的 3.85 倍）。

### 根因（架构级）

测量链路上 `contentHeight`（内容高度）与 `renderViewport`（渲染视口）被耦合：

1. 画布量出页面内容高度；
2. 通过 `effectiveHeight` 把该高度**回填进渲染视口**（`computePreviewScale` 的 `useEffectiveHeight` 分支：渲染容器/iframe 高度 = contentHeight）；
3. **关键缺陷**：`PrototypePagePreview` 把 `computePreviewScale` 返回的 `designHeight`（在 `useEffectiveHeight` 场景下被抬升为 contentHeight）直接当作"设计基准"传入 `buildPrototypePreviewHtmlFragment`，用于 `normalizePrototypeViewportUnits` 归一化 `100vh`；
4. 于是 `100vh` 被归一化成"contentHeight 对应的像素"（如 4157px），整屏幻灯片被撑成异常高度；
5. 该高度又回填进 `effectiveHeight`，形成正反馈，直到被 `MAX_PAGE_HEIGHT=50000` 兜底。

即：**页面里任何用 `100vh`/`min-h-screen` 的元素，其归一化基准被画布自身的测量高度污染。**

同时测量函数 `measureFullContentHeight` 用 `max(body, children.bottom, scrollHeight)`，把"视口固定区域"与"内蕴内容"混在一起计算，进一步加剧。

## 二、会一起出错的机制

不只 `100vh`，同一"测量内容高度"机制下确认存在以下失败模式：

| # | 机制 | 失败表现 | 位置 |
|---|------|---------|------|
| A | 视口耦合反馈（`100vh`/`min-h-screen`/`100%` 链→屏幕祖先） | 整屏页被撑成异常高度 | `preview-scale.ts` `effectiveHeight` |
| B | 视口单位覆盖不全（原型只归一化 `vw/vh/vmin/vmax`，缺 `svh/dvh/lvh/dvw/svw`） | 用 `100dvh` 等新单位的页面不被锁定，仍可能膨胀 | `prototype-preview.ts` `normalizePrototypeViewportUnits` |
| C | `position:fixed` 不入 scrollHeight | 固定页脚/头部导致的真实内容被低估，卡片太矮、内容被裁 | `iframe-template.ts` `measureFullContentHeight` |
| D | 根 `overflow:hidden` 裁剪 | 长页面被裁成视口高（对幻灯片是预期，对长页是错的） | 同上 |
| E | Chrome `scrollHeight` clamp 到 2^24 | 天文数字高度 | 同上（原型路径无此兜底） |
| F | 截图 `renderBox` 与实时测量口径不一致 | 卡片在截图态与 live 态之间跳高 | `useScreenshotGeneration` / `CanvasPageItem` |
| G | 异步内容/字体换行后不重测 | 图片/富文本加载后卡片高度过期 | `iframe-template.ts` |

## 三、根治原则

> **渲染视口永远是 previewSize（设计尺寸），`vh` 族永远等于 designHeight；画布卡片高度 = max(一屏, 页面的内蕴内容跨度)，且该值绝不回喂渲染视口。**

即"先量身高，再定床长"，而非"床变长→人变高→床再变长"。

落地的三个可维护支柱：

- **支柱 1 · 视口锁定**：保证 `vh/svh/dvh/lvh/vmin/vmax` 及 `min-h-screen`/`h-screen` 全部解析为 designHeight/designWidth。
- **支柱 2 · 统一内容度量**：测量"内蕴内容跨度"（含 in-flow 下边缘、纳入 `position:fixed`、下落一屏、上设合理 cap 绕过 2^24 clamp），并在字体/图片 ready 后重测。
- **支柱 3 · 度量与显示解耦**：先在设计视口下测得 `contentHeight`，再据此渲染卡片；卡片高度不回喂测量视口；截图走同一套口径。

## 四、实施方案与进度

### 阶段 1+2（本次）：测量统一 + 视口锁定

- [x] 撰写本文档
- [x] **真实根因修复（设计基准锁定）**：`packages/demo-ui/src/PrototypePagePreview.tsx` 不再把 `computePreviewScale` 返回的 `designHeight`（`useEffectiveHeight` 场景下被抬升为 contentHeight）作为归一化基准，改用 `previewSize` 的真实设计宽高（`fragmentDesignWidth/Height`）传入 `buildPrototypePreviewHtmlFragment`。这切断了"测量高度污染 `100vh` 归一化基准"的正反馈。已用 headless 浏览器复现：旧行为 slide=4157px，新行为 slide=1080px。
- [x] **画布测量兜底（初始上报）**：`PrototypePagePreview` 在渲染后 `requestAnimationFrame` 上报一次初始内容高度（`root.scrollHeight`，元素自身坐标、不受画布 transform 缩放影响），避免 `ResizeObserver` 首帧回调不触发时页面永远停留在历史持久化高度。
- [x] **视口单位归一化补全**：`packages/shared/src/demo/prototype-preview.ts` 的 `normalizePrototypeViewportUnits` 扩展覆盖 `svw/svh`、`dvw/dvh`、`lvw/lvh`（basis：vw 族→designWidth，vh 族→designHeight，vmin→min，vmax→max）。已用独立脚本验证 14/14 用例通过。
- [x] **iframe 内容度量加固**：`packages/demo-ui/src/iframe-template.ts` 的 `measureFullContentHeight` 引入 `MAX_CONTENT_HEIGHT = 50000`（与画布 `MAX_PAGE_HEIGHT` 一致）钳制，防止异常测量值（2^24 clamp）反向撑爆渲染视口；新增 `document.fonts.ready` 后重测。
- [x] **存量数据修正**：`OneFlow介绍` 项目 live 工作区 `.canvas-layout.json` 中 7 个被错误持久化的 4157px 高度修正为设计高度 1080px（`sizeMode: preview` 的页面），画布卡片恢复 16:9。已在浏览器验证卡片 aspect=1.78。
- [x] **可滚动长页在画布展示完整内容（本次新增）**：修复"作者用固定高度 + `overflow:hidden` 裁剪容器装起可滚动内容"的页面（如 `伴读首页` 手机页）在画布卡片里只显示一屏的问题。根因：`.prototype-root` 的 `scrollHeight` 被页面自身固定高度的裁剪容器钳制在设计高，看不到内层可滚动容器的完整内容。`PrototypePagePreview` 在上报内容高度前，自底向上解除"纵向裁剪且内容确实溢出"的容器（`overflow:visible` + `height:auto`），让 `.prototype-root` 长到完整内容高度，再由 ResizeObserver/fonts.ready 重测上报。已用真实页面兜底验证：修复前 root=812px（一屏），修复后 root=1034px（完整内容）。
- [~] **测试**：新增 `packages/demo-ui/src/prototype-preview.test.ts`（`normalizePrototypeViewportUnits` 全单位快照）。注：demo-ui vitest 环境 `vitest@1.6.1 + @testing-library/jest-dom@6.9.1 + jsdom@26` 存在既有兼容问题，测试无法运行，改用独立脚本验证。另：headless 浏览器环境（ego-browser）的 `ResizeObserver` 不触发，无法直接验证 ResizeObserver 驱动的画布再测量，改用 `scrollHeight` 兜底并靠真实浏览器确认。
- [x] **消除"实际高度/一屏高度"反复闪烁（修复 `PrototypePagePreview` 测量 feedback loop）**：`PrototypePagePreview` 的测量 effect 依赖了 `designHeight`/`designWidth`（`computePreviewScale` 在 `useEffectiveHeight` 场景下返回的即是内容高度）与 `onContentHeightChange`（其身份随 `contentHeight` 状态变化）。当上报内容高度后，这两个依赖变化 → effect 重建 shadow DOM（`shadow.innerHTML = ...`）→ root 瞬时回到一屏高度 → 裁解除失效 → 重新上报一屏高度 → 卡片又缩回一屏，形成"实际高度 ↔ 一屏高度"正反馈闪烁。修复：`onContentHeightChange` 改存 ref（`onContentHeightChangeRef`），effect 只依赖真正决定 shadow DOM 内容的 `html/css/configData/allowScroll/fillContainer/visualPropertyChanges/sessionId/demoId`，移除 `designHeight`/`designWidth`/`onContentHeightChange`。shadow DOM 内容本就不依赖 `effectiveHeight`（归一化基准已用 `fragmentDesignWidth/Height` 即真实设计尺寸），故可安全移除。已通过 `tsc`（非测试文件无错）验证。

> 说明：`position:fixed` 属视口覆盖元素，不参与"内容高度"（不推高卡片），故未纳入测量；`overflow:hidden` 裁剪分两类处理——**幻灯片等平铺正好一屏的固定页**（contentHeight == clientHeight）是页面作者意图，由视口归一化保证 16:9，不做画布侧处理；**可滚动长页**（内容确实溢出、有内层滚动容器）则通过 `expandVerticalClippedElements` 在画布中解除裁剪、展示完整内容。解除裁剪只作用于"纵向裁剪且 `scrollHeight > clientHeight`"的容器，一屏固定页不会被误展开。

### 阶段 3（后续）：截图口径一致

**目标**：让截图 `renderBox` 上报的内容高度与 live 实时测量采用同一套"内容跨度"语义，避免画布卡片在"截图占位态"与"live iframe 态"之间跳高。

**现状数据流**：
- 截图服务按 `getScreenshotRequestSize`（designWidth × designHeight）作为视口截图，`renderBox` 记录当时的 `documentHeight/bodyHeight/scrollHeight`（见 `screenshot-service/src/utils/screenshot-store.ts`）。
- 画布 `CanvasPageItem` 把 `screenshotRenderBox.height` 走与 live 测量相同的 `handleContentHeightChange` → `resolveCanvasContentHeightLayout`（`resolveCanvasContentHeightLayout` 已按 `MAX_PAGE_HEIGHT` 兜底）。
- 阶段 1+2 后：原型页截图经 `/api/compile` 已做视口归一化，React 页截图视口即 designHeight，故整屏页截图天然测得"一屏"；与 live 测量（也因归一化/钳制稳定）基本一致。**残余不一致主要来自：live 测量若被 `effectiveHeight` 短暂拉高、或截图与 live 的 documentHeight 判定口径不同。**

**实施步骤**：
- [ ] **统一内容跨度判定**：抽取一个共享的"内容跨度"计算约定（`documentHeight` 主、`bodyHeight` 兜底、`scrollHeight` 仅在溢出视口时采用、统一上限 `MAX_CONTENT_HEIGHT`），在 `iframe-template.ts` `measureFullContentHeight` 与截图服务 `renderBox` 计算处共用同一套规则，保证两者数值口径一致。
- [ ] **截图侧对齐**：`screenshot-service` 计算 `renderBox` 时应用与 live 相同的上限钳制；视口固定为 designHeight，天然让 `100vh` 页测得"一屏"。
- [ ] **画布侧应用对齐**：`CanvasPageItem` 应用 `screenshotRenderBox.height` 时，与 live 一样做下限（<50 忽略）与上限（`MAX_PAGE_HEIGHT`）处理，避免截图态把卡片撑得偏离 live 态。
- [ ] **测试**：新增/扩展截图 renderBox 与 live 内容跨度在"整屏页"与"长页面"两类下取值一致的用例（`useScreenshotGeneration.test.tsx`、screenshot-service 测试）。

**涉及文件**：`screenshot-service/src/routes/screenshots.ts`、`screenshot-service/src/utils/screenshot-store.ts`、`demo-ui/src/iframe-template.ts`、`demo-ui/src/CanvasPageItem.tsx`、`shared`（共享内容跨度约定）。

### 阶段 4（后续，独立专项）：React 长页 + 100vh 区块（源级视口单位归一化）

**目标**：解决唯一无法靠"测量"根治的残余——">1 屏长 React 高保真页 + `100vh` hero 区块"。要显示全部内容必须把 iframe 拉高到 contentHeight，而拉高会让 hero 的 `100vh` 跟着膨胀。

**根因**：原型页有 `normalizePrototypeViewportUnits` 把 `100vh`→designHeight；React 高保真页无此归一化，其 `100vh` 直接等于 iframe 视口高度（= 被拉高的 contentHeight）。

**前置准备（本次文档已确认）**：
- React 高保真页编译管线：`author-site/src/lib/compiler.ts` → `@workbench/preview-contract/compiler` 的 `compilePreviewPageSource`，产物含 `compiledCode` 与 `cssImports`（CSS 文件导入）。
- 页面设计尺寸来源：`previewSize`（`$demo.previewSize` / `prototype.meta.json` / fallback），编译/服务时按页面可取得。

**候选方案（按侵入度排序，需决策）**：

- [ ] **方案 4-A · 源级视口单位归一化（彻底，推荐主体）**：复用/泛化 `normalizePrototypeViewportUnits` 成共享的 `normalizeViewportUnits`，对 React 高保真页产物做归一化：
  - 对 `cssImports` 引用的 CSS 文件：在服务时按页面设计尺寸重写 `100vh`/`min-h-screen`/`100dvh` 等；
  - 对编译后 JS 中的视口单位字符串字面量（`style={{ height: '100vh' }}`、`minHeight: '100vh'` 等）：在编译后模块字符串上做字面量替换。
  - 需要 designSize 参与归一化：要么把 designSize 并入编译缓存 key，要么在服务路由层按页面归一化（推荐后者，避免缓存膨胀）。
  - **局限**：对编译后 JS 字符串做正则替换是"尽力而为"，可能误伤变量名/注释/字符串拼接；需用白名单字面量模式（`<number>(vh|svh|dvh|lvh|vw|svw|dvw|lvw|vmin|vmax)`、`min-h-screen`/`h-screen`）控制风险。
- [ ] **方案 4-B · 整屏检测 + 一屏钳制（窄、先做）**：对 React 页在 designHeight 视口下测量，若 `documentHeight ≈ designHeight`（整屏固定页），直接把卡片钳制为 designHeight，不拉高 iframe，避免膨胀。覆盖最常见的"单屏 100vh 页"；对真正的"长页 + 100vh hero"仍需 4-A。

**建议路径**：先 4-B（低风险、覆盖多数场景），再按需评估 4-A 的归一化（重写管线，需充分测试与回归）。

**涉及文件**：`packages/preview-contract/src/compiler.ts`、`author-site/src/lib/compiler.ts`、`author-site/src/app/api/compile/route.ts`、`demo-ui/src`（整屏检测）、`shared/src/demo/prototype-preview.ts`（泛化 normalize）。

## 六、风险与待确认

- `position:fixed` 计入内容高度会略高估少数页面（权衡：更符合"完整内容"语义）。
- React 长页 + `100vh` 区块的视觉膨胀属残余问题（阶段 4）。
- 阶段 4 方案 4-A 对编译后 JS 字符串做视口单位替换是"尽力而为"（白名单字面量），可能误伤部分写法，需充分测试；4-B 更保守但只覆盖单屏页。
- 阶段 3 需确认截图服务与 live 测量共用同一"内容跨度"约定后，是否会影响既有截图 renderBox 的历史读取（`readScreenshotRenderBox` 兼容性）。
