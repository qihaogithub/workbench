## 第四轮修复（2026-07-31）

### 根因确认

**CSS 置灰规则存在致命缺陷**，并非 `injectPosKey` 失败。

`iframe-template.ts` 中的 CSS 规则：

```css
body.position-editing.position-editing-dimming :not([data-pos-key]),
body.position-editing.position-editing-dimming :not([data-pos-key]) * {
  opacity: 0.3 !important;
}
```

- 第二条规则 `:not([data-pos-key]) *` 匹配所有不含 `data-pos-key` 的元素的所有后代
- `#root` 不含 `data-pos-key` → 所有 `#root *` 被命中 → 可定位元素（logo/title/subtitle）虽自身有 `data-pos-key`，但规则将其作为 `#root` 的后代也置为 `opacity: 0.3`
- **即使 `injectPosKey` 完全成功**，可定位元素仍因 `#root` 的 0.3 opacity 而不可见

步骤 3 中"鼠标悬停变抓手"证明 `injectPosKey` 实际是成功的 —— 元素 DOM 存在且有 `data-pos-key`，只是 CSS 置灰规则让它们在白底上彻底隐形。

### 修复内容

`packages/demo-ui/src/iframe-template.ts`：

1. **移除** `<style>` 中的 CSS 置灰规则（原 2115-2118 行）
2. **`setDimCSS` 改为 JS 逐元素置灰**：
   - `applyElementDimming()`：遍历 `body.querySelectorAll('*')`，只对**不含 `data-pos-key` 且不含 `[data-pos-key]` 后代**的元素设置 `el.style.setProperty('opacity', '0.3', 'important')`，并标记 `pos-dimmed` class
   - `clearElementDimming()`：移除所有 `.pos-dimmed` 元素的 `opacity` inline style
   - 可定位元素自身（有 `data-pos-key`）和包含可定位元素的祖先容器（含 `[data-pos-key]` 后代）均保持完整不透明度

效果：
- logo/title/subtitle 等 → 完整显示（有 `data-pos-key`）
- `#root` 等祖先容器 → 完整显示（含 `[data-pos-key]` 后代）
- 其他非定位元素 → 置灰 opacity 0.3

## 推测根因

核心问题链：**`injectPosKey` 未能成功注入 `data-pos-key`** → 后续所有依赖 `[data-pos-key]` 选择器的操作失效 → 置灰 CSS 将所有元素 opacity 降为 0.3（因为没有任何元素有 `data-pos-key`）→ 视觉上呈现"白色无内容"。

### injectPosKey 可能仍失败的猜测

1. **`getComputedStyle` 时机问题**：`injectPosKey` 在 `enter()` 中调用，此时 DOM 可能刚渲染完成但 computed style 尚未稳定（如 Tailwind 的 JIT 样式注入延迟、图片未加载导致布局不稳定）
2. **`#root.querySelectorAll('*')` 返回的 NodeList 为空**：如果 `#root` 不存在或内容尚未挂载
3. **页面组件的 offsetParent 层次**：`cs.left` 返回的是相对于最近的 `position` 祖先的值。如果页面 DOM 结构中有一个中间层设置了 `position: relative`，`cs.left` 的值可能不等于 `__positions` 中的坐标
4. **`position: absolute` 元素的渲染异常**：如果组件渲染时 `__positions` 未传入（configData 不包含该字段），元素可能使用默认值渲染，但 `cs.left`/`cs.top` 的值与传入 `enter()` 的 positions 不匹配

### 辅助问题猜测

- **`APPLY_POSITIONS` 不生效**：因为 `applyPosition` 依赖 `[data-pos-key]` 选择器找元素，而注入失败时找不到任何元素
- **退出后白屏持续**：退出时发送的 `UPDATE_CONFIG` → `renderComponent()` 能正确渲染，但渲染结果可能受 dimming CSS 残留影响（`exit()` 中 `setDimCSS(false)` 移除了 class，但可能存在时序问题）
- **切换模式恢复**：iframe 完全重建（src 重置），所有状态清零

## 下一步排查建议

### 优先验证项

1. **在浏览器控制台中手动验证 `injectPosKey`**：
   - 打开 iframe 控制台
   - 手动调用 `injectPosKey(["logo", "title", "subtitle"], { logo: {x:20,y:20}, title: {x:100,y:24}, subtitle: {x:100,y:64} })`
   - 检查 `document.querySelectorAll('[data-pos-key]')` 是否有结果
   - 检查 `document.querySelectorAll('#root *')` 中有多少 `position: absolute` 元素，它们的 `cs.left`/`cs.top` 值是多少

2. **检查 `__positions` 何时进入 configData**：
   - 在 ConfigForm 中打日志，看 `formData.__positions` 何时被设置
   - 在 `handleEnterPositionEdit` 中打日志，看传入的 `positions` 参数值
   - 确认 `configData` prop 在 PreviewPanel 中是否已包含 `__positions`

3. **检查 dimming CSS 是否生效**：
   - 进入编辑模式后，在 iframe 控制台检查 `document.body.classList` 是否包含 `position-editing-dimming`
   - 检查 `.position-editing-dimming` CSS 规则是否正确注入

### 备选方案

如果 `injectPosKey` 的 `getComputedStyle` 方式仍不可靠，可考虑：

1. **在编译阶段注入 `data-pos-key`**：修改 `/api/compile` 或页面编译管线，在生成的 React 代码中自动为 `$demo.positionable.items` 对应的 JSX 元素添加 `data-pos-key` 属性
2. **放弃自动注入，使用文档约定**：要求用户在页面代码中手动添加 `data-pos-key="keyName"` 属性（当前 `index.tsx` 已使用了 `__positions` 但未加 `data-pos-key`）
3. **放弃 DOM 属性匹配，改用位置推断**：不依赖 `data-pos-key`，而是在 `pointerdown` 时通过 `elementsFromPoint` + 位置/尺寸匹配找到对应的可定位元素
