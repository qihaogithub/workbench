# 创作端配置图片白板：可插拔编辑器引擎方案

> 状态：方案设计中
> 创建日期：2026-08-29
> 适用范围：创作端配置图片白板、白板草稿、PNG 回填与二次编辑
> 关联方案：[创作端配置图片白板-产品与实现方案](./创作端配置图片白板-产品与实现方案.md)

## 一、背景

创作端的图片配置项可以打开白板，用户在白板中绘制内容，导出 PNG 后回填为配置项的图片值，并在后续再次打开原始白板继续编辑。该流程同时包含编辑器交互、白板文档保存、图片资产生成、配置值更新、绑定关系、权限和冲突处理。

当前 `WhiteboardDialog`、`WhiteboardDocument` 和提交接口直接使用 `SketchSceneDocument` 与 `sketch-react`。这使自研编辑器能够快速复用现有能力，但业务提交链路与编辑器数据模型存在强耦合：如果短期引入 Excalidraw，或未来替换为成熟的第三方/自研引擎，就需要同时修改存储校验、二次编辑、导出和提交逻辑。

本方案将“业务提交协议”作为稳定边界，将 Excalidraw、`sketch` 或其他实现收敛为可插拔的编辑器引擎。编辑器只负责编辑私有文档和导出图片；创作端业务层继续负责目标解析、权限、草稿、原子提交和配置回填。

## 二、目标

- 稳定 `WhiteboardCommit` 业务协议，不让配置系统依赖某个编辑器的 scene 格式。
- 支持 Excalidraw 作为第一阶段编辑器，也支持后续切换到 `sketch`。
- 保留白板二次编辑能力，二次打开时使用创建该文档时的兼容引擎。
- PNG 仍作为图片配置项的最终值；白板原始文档、绑定和图片资产保持独立职责。
- 保留取消不回填、冲突检测、权限校验、原子提交、失败重试和延迟 GC。
- 让 `WhiteboardDialog`、配置入口和服务端提交接口不感知具体编辑器 UI。
- 允许新白板默认使用新引擎，同时不破坏历史白板。

## 三、非目标与边界

- 不把 Excalidraw JSON 或 `SketchSceneDocument` 直接定义为跨引擎业务协议。
- 不在配置值中保存白板 JSON；配置值仍然是 PNG 资产路径或现有图片值结构。
- 不要求 Excalidraw 与 `sketch` 之间实现百分之百可逆转换。
- 不在本方案中扩展图片字段识别范围、页面 runtime 或普通图片资产协议。
- 不把编辑器视口、选区和撤销栈写入图片配置值。
- 不因更换编辑器而复制一套权限、Authority 或 Workspace 提交流程。

## 四、总体方案

### 4.1 分层

```text
图片配置字段
  → ImageConfigTarget
  → WhiteboardDialog（草稿、关闭保护、状态展示）
  → WhiteboardEditorEngine（可插拔编辑器）
  → WhiteboardDocument（版本化引擎文档）
  → PNG 导出
  → WhiteboardCommit（统一业务提交）
  → 图片资产 + 配置值 + binding + Authority revision
```

分层职责如下：

| 层 | 职责 | 不负责的内容 |
|:---|:---|:---|
| `demo-ui` | 识别图片字段并发出 `ImageConfigTarget` | 不持有项目状态、编辑器状态或网络 IO |
| `WhiteboardDialog` | 草稿生命周期、加载/关闭、错误、提交触发 | 不解析 Excalidraw 或 `sketch` 的内部节点 |
| `WhiteboardEditorEngine` | 编辑、撤销重做、视口、变更通知、PNG 导出 | 不更新配置值，不写项目文件 |
| `WhiteboardDocument` | 保存引擎标识、引擎文档和编辑视口 | 不承载图片字段所有权 |
| `WhiteboardCommit` | 校验、权限、冲突、资产、binding、配置值的一次提交 | 不依赖具体编辑器组件 |

### 4.2 引擎可插拔接口

建议在 author-site 或独立白板适配层定义稳定接口，避免 `WhiteboardDialog` 直接导入 `SketchPageEditor` 或 Excalidraw 组件：

```ts
export interface WhiteboardEditorEngine {
  mount(container: HTMLElement, options: WhiteboardEditorEngineOptions): void;
  load(document: WhiteboardDocument): void;
  onChange(listener: (document: WhiteboardDocument) => void): () => void;
  exportPng(options?: WhiteboardExportOptions): Promise<Blob>;
  focus(): void;
  dispose(): void;
}

export interface WhiteboardEditorEngineOptions {
  readOnly?: boolean;
  backgroundImage?: string | null;
}
```

实际实现：

```text
ExcalidrawEngine  → Excalidraw API、原始 elements/appState/files、PNG 导出
SketchEngine      → SketchSceneDocument、sketch-react、PNG 导出
```

`WhiteboardDialog` 只依赖工厂：

```ts
createWhiteboardEditorEngine(document.engine): WhiteboardEditorEngine
```

引擎必须在 `dispose` 时移除事件监听、快捷键和临时 URL，避免 Dialog 关闭后继续修改草稿或拦截宿主快捷键。

## 五、文档与提交协议

### 5.1 版本化 `WhiteboardDocument`

将当前固定的 `scene: SketchSceneDocument` 改为引擎 envelope：

```ts
interface WhiteboardDocument {
  id: string;
  version: 2;
  engine: "excalidraw" | "sketch";
  engineVersion: string;
  engineDocument: unknown;
  editorView: {
    zoom: number;
    offsetX: number;
    offsetY: number;
  };
  updatedAt: number;
}
```

约束：

- `engine` 是持久化兼容性选择，不是当前 UI 选择状态。
- `engineDocument` 只由对应引擎校验；服务端不得假设其内部字段。
- `editorView` 使用统一的最小视口结构，便于引擎之间迁移；无法恢复时使用安全默认值。
- 每个引擎注册 `validate`、`normalize` 和 `migrate`，未知引擎或版本必须 fail-closed。
- 文档大小上限、路径规则、权限和脱敏诊断继续由白板资源层统一控制。

历史 `version: 1` 文档（`scene: SketchSceneDocument`）保留读取兼容，读取时包装为 `engine: "sketch"`；新提交统一写入 `version: 2`。是否批量迁移历史文件不属于首期必需项。

### 5.2 `WhiteboardBinding` 不绑定具体引擎

`WhiteboardBinding` 继续只记录配置目标、白板 ID、scene revision 和输出 PNG hash：

```text
binding
  → whiteboardId
  → target
  → sceneRevision
  → outputAssetHash
```

binding 不保存引擎内部节点 ID，也不把 Excalidraw 元素或 `SketchSceneNode` 写入图片资产元数据。

### 5.3 统一 `WhiteboardCommit`

提交输入保持业务语义稳定：

```text
sessionId
target
document（已校验的 WhiteboardDocument）
pngBase64 / staged binary
```

提交流程：

```text
引擎草稿
  → exportPng
  → PNG 头、大小、内容 hash 校验
  → 检查 target 与当前配置值的冲突
  → 写入 whiteboard document
  → 写入 PNG 资产
  → 更新 binding
  → 更新配置值
  → Authority receipt / revision
```

上述操作必须继续属于同一个 Authority mutation。编辑器替换不能改变提交顺序、权限边界或失败后的重试语义。

## 六、二次编辑与迁移策略

### 6.1 二次编辑

- 根据 `WhiteboardDocument.engine` 选择引擎，而不是根据当前默认配置选择。
- Excalidraw 文档由 `ExcalidrawEngine` 原样加载，避免先转换成 `sketch` 导致信息丢失。
- `sketch` 文档由 `SketchEngine` 加载并继续使用现有协议校验。
- 只有用户明确执行“转换为自研白板”时，才调用显式转换器并展示可能丢失的能力。

### 6.2 新旧引擎共存

```text
历史文档：engine = excalidraw → ExcalidrawEngine
新建文档：默认 engine = sketch（或灰度阶段指定 excalidraw）
业务回填：两者均使用同一 WhiteboardCommit
```

默认引擎应通过 feature flag 或项目级策略控制，但不能覆盖已保存文档的 `engine`。

### 6.3 转换原则

- 转换器是单独模块，不放入通用提交接口。
- 转换前保留源文档，转换失败不能覆盖原白板。
- 转换结果生成新的白板文档 ID 或新的 revision，并重新导出 PNG。
- 不承诺所有元素、字体、库资源、手绘效果和文本样式可逆转换。
- 转换结果必须经过目标引擎校验和只读渲染回归。

## 七、Excalidraw 接入评估

### 7.1 可复用部分

如果按本方案实施，以下内容无需因接入 Excalidraw 重写：

- 图片字段入口与 `ImageConfigTarget`；
- `WhiteboardDialog` 的关闭确认、草稿状态和错误展示；
- 白板读取接口、权限校验和资源路径；
- PNG staging、哈希去重和配置值冲突检测；
- `WhiteboardBinding`、延迟 GC 和 Authority 原子提交；
- 图片配置面板和页面预览。

### 7.2 需要新增的适配工作

- Excalidraw 动态加载、容器挂载和主题样式适配；
- Excalidraw 文档与 `WhiteboardDocument` envelope 的序列化/校验；
- Excalidraw 的图片文件、字体、资源大小和临时 URL 管理；
- PNG 导出参数、透明背景和画布边界处理；
- Dialog 快捷键、Escape、焦点和未保存修改状态桥接；
- Excalidraw 引擎的单测、浏览器回归和性能基线。

因此，接入 Excalidraw 的主要成本是引擎适配，而不是重做图片配置业务链路。若不先增加 envelope 和 engine interface，短期成本较低，但将来切换自研引擎会产生数据迁移和双协议维护成本。

## 八、实施阶段

### 阶段一：稳定业务边界

- [ ] 抽出 `WhiteboardEditorEngine` 与工厂。
- [ ] 将 `WhiteboardDocument` 升级为 `version: 2` envelope。
- [ ] 为旧 `version: 1` sketch 文档增加读取包装。
- [ ] 让 `WhiteboardDialog` 不再直接依赖 `SketchPageEditor`。
- [ ] 保持现有 `WhiteboardCommit` 请求结构和配置回填行为不变。

### 阶段二：完成 Excalidraw 引擎

- [ ] 实现 `ExcalidrawEngine` 的加载、变更、视口和 PNG 导出。
- [ ] 增加 Excalidraw 文档大小、图片资源和临时 URL 清理策略。
- [ ] 增加新建白板的引擎灰度开关。
- [ ] 验证取消、刷新、冲突、提交失败和二次编辑。

### 阶段三：接回自研 `sketch`

- [ ] 实现 `SketchEngine`，复用现有 `sketch-react` 能力。
- [ ] 新白板按灰度策略切换默认引擎。
- [ ] 历史 Excalidraw 文档继续由原引擎打开。
- [ ] 单独评估 Excalidraw → sketch 转换，不把转换作为提交前置步骤。

## 九、验证计划

- 协议：引擎未知、版本未知、文档损坏和超限时 fail-closed。
- 业务：PNG 回填成功时配置值、binding、白板文档和资产属于同一 revision。
- 二次编辑：Excalidraw 与 sketch 文档分别恢复原始内容和视口。
- 取消与失败：取消、Escape、权限拒绝、冲突、导出失败和上传失败均不修改原配置。
- 互操作：引擎更换不影响 `ImageConfigTarget`、`WhiteboardBinding` 和配置值读取。
- 安全：远程图片本地化、canvas taint、data URL 大小和临时 Blob URL 清理。
- 性能：首开、200 节点拖拽、PNG 导出、二次加载和 Dialog 销毁后的资源释放。
- 回归：`sketch-react`、author-site 白板 Dialog、whiteboard API、配置图片字段和 Playground。

## 十、风险与决策

| 风险 | 影响 | 应对 |
|:---|:---|:---|
| Excalidraw 文档体积大 | 白板资源和请求变慢 | 独立大小上限、压缩/分块评估、图片资产外置 |
| 两种引擎能力不一致 | 切换后视觉或编辑能力变化 | 不做隐式转换，按 engine 恢复并明确转换提示 |
| 编辑器快捷键与 Dialog 冲突 | Escape、复制粘贴或撤销行为异常 | 引擎生命周期内统一注册和清理快捷键作用域 |
| 视口模型不同 | 二次编辑位置变化 | 统一保存最小视口，无法映射时安全回退并记录诊断 |
| 上游版本变化 | Excalidraw 适配失效 | 锁定依赖版本、引擎版本字段和适配层回归 |
| 双引擎长期维护 | 测试和包体成本增加 | 新建默认逐步收敛到自研引擎，旧引擎只保留读取/编辑维护 |

最终决策：**稳定业务提交协议，编辑器引擎可插拔；不稳定业务协议去迁就任何单一编辑器。**
