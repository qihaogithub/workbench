# 创作端文档编辑与保存可靠性治理方案

## 背景

创作端 Markdown 编辑器原先由宿主组件各自维护 800ms 定时器和保存 Promise。Authority 拒绝写入时，部分路径只静默吞掉异常，导致编辑器中的内容仍在内存里，但重新打开文档后无法恢复。诊断证据表明，当前问题不是编辑器 `onChange` 没有触发，而是保存提交在 Authority 备份校验阶段失败后没有可靠的本地保留和可见状态。

## 目标与范围

- 统一普通文档视图、设计规范说明和项目模式知识文档弹窗的保存状态与提交队列。
- 保存成功得到明确 API/Authority 成功响应后才清理草稿；失败保留最新编辑值并暂停自动提交。
- 为具备 `projectId + workspaceId` 身份的编辑资源提供基于服务端基准指纹的 IndexedDB 草稿恢复；基准变化进入冲突状态，不覆盖服务端内容。
- Authority 备份缺失、外部漂移、网络、权限、校验和资源冲突使用不同状态提示；不在前端自动 reconcile-adopt 或无限重试。
- 不修改项目数据，不增加按页面或具体错误文本分支，不绕过 Authority 写入。

## 方案

`DocumentSaveCoordinator` 负责脏值、800ms 防抖、3 秒最大等待、单请求在途、最新值合并、显式 retry 和 dispose flush。`workspace-offline-drafts` 只负责浏览器本地草稿；其内容指纹不是 Authority 的 revision、rootHash 或服务端哈希替代物。`DocumentSaveStatusBar` 统一展示保存状态、重试和放弃本地草稿操作。

宿主只提供资源读取和提交函数：普通文档视图提交知识文档或 workspace 文件，设计规范提交整份文档，项目模式知识文档弹窗使用自动保存并保留显式保存立即冲刷；旧版 Yjs 协同文档继续由协同通道负责 flush，避免双重写入。

## 风险与边界

- IndexedDB 不可用时只能降级为服务端编辑，不得把内存值宣称为“已保存草稿”。
- 本地草稿基准变化时只进入冲突状态，当前实现不自动合并；后续如需合并应单独定义用户确认和 Authority 版本契约。
- Authority 备份缺失的恢复动作属于运维/管理员流程，本次只提供前端可见状态和显式重试，不自动修复工作区。
- 设计规范 API 的成功响应增加 Authority receipt 元数据，但保留原 `data.entries` 等既有数据形状。
