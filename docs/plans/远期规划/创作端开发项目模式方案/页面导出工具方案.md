# 页面快照导入与评审工具方案

> 创建日期：2026-07-26
> 最近校正：2026-08-20
> 当前状态：评审闭环已实现；CLI 采集与转换已有原型，但可靠批量导入、稳定重复更新和失败安全尚未完成
> 原名称：页面导出工具方案
> 定位：把开发项目的页面运行态快照转换为创作端 `prototype-html-css` 原型页，用于视觉评审、批注和意见回流；不是源码同步或双向同步系统

## 一、结论与方向校正

方案的基本方向成立：复用 SingleFile 获取浏览器运行态页面，复用创作端 Project Admin CLI 导入原型页，复用现有批注和 AI 修改链路完成评审闭环。

原方案对能力边界有三处表述过度，现统一校正：

1. “同步所有页面”改为“导入明确路由与页面状态的静态快照”。自动发现只能生成候选路由，不能枚举动态参数、权限身份、弹窗、展开态等运行状态。
2. “可重复同步”改为目标能力。当前 manifest 没有稳定 `pageId`，CLI 只按 `pageId` 更新，实际尚不能可靠覆盖已有页面。
3. “dry-run 校验”改为“dry-run 仅展示计划”。当前 `ow project import-prototype --dry-run` 不执行页面写入和 `prototypeGate`；真正的无提交预检需要单独补齐。

校正后的产品定义：

> 页面快照导入工具负责生成受 prototypeGate 约束的静态 Import Bundle。CLI 可以直接批量抓取并转换；浏览器插件则负责生成保留脚本、事件和 iframe 的高保真 Editable Snapshot Bundle。只有用户明确需要创作端原型评审时，才由独立派生器从高保真 bundle 生成静态副本。

## 二、目标与非目标

### 2.1 目标

- 将 Next.js、React、Vue、Vite 等应用的已渲染页面保存为静态、可读、可导入的 HTML/CSS 原型。
- 保留足够的 DOM 结构、文字、布局和图片，支持创作端画布评审。
- 支持批注、评论和 AI 修改原型页，意见按稳定路由身份回流开发项目。
- 同一路由再次导出时，在映射明确的前提下更新已有原型页。
- 所有导入均先完成本地转换报告和创作端事务预检，只有显式确认才提交。

### 2.2 非目标

- 不恢复 React/Vue 组件、源码文件边界、变量名或路由实现。
- 不保留 JavaScript 交互；轮播、地图、表单提交等动态行为不属于原型页能力。
- 不自动枚举所有动态路由实例、用户权限和页面状态。
- 不自动合并创作端原型改动与开发项目源码。
- 不替代 WARC 等专业网页归档工具。

### 3.3 尚未完成或需要修正

以下均为进入“可靠内部工具”前的阻断项：

1. **稳定页面身份缺失**：normalize 只生成 routeKey；`page update-prototypes` 只按 pageId 查找已有页面。
2. **嵌套路由输出目录缺失**：`demo/[id]/edit` 等文件名含目录分隔符，写文件前未创建父目录。
3. **跨页面图片名冲突**：每页图片编号都从 `img-001` 开始，却写入同一个 images 目录。
4. **dry-run 不做内容预检**：当前只返回计划，不能据此判断 `prototypeGate.decision`。
5. **提交参数语义相反**：skill 要求显式 `--commit`，但 export.mjs 当前在非 dry-run 且未传 `--no-commit` 时默认提交。
6. **部分失败仍继续**：单页渲染失败后默认继续 normalize 和导入，可能提交不完整页面集合。
7. **Cookie 文件残留**：JWT 写入输出目录后没有自动清理和权限收紧。
8. **normalize 仍主要依赖正则**：尚未实现原方案描述的 DOM/CSS AST 级解析兜底。
9. **Project Admin skill 衔接未固化**：export-pages skill 尚未完整承接 doctor、事务检查、验证和提交规范。

## 四、校正后的目标架构

```text
CLI / agent 批量抓取
      │
      ▼
静态 page-export normalize
      │
      ▼
Import Bundle v1 → preflight → 显式 commit → 创作端原型评审

浏览器当前标签
      │
      ▼
高保真 Editable Snapshot Bundle
  保留 script / event / iframe / 原始资源
      │
      ├── Agent 阅读、修改、隔离预览
      │
      └── 可选静态原型派生器
              │
              ▼
        Import Bundle v1 → 创作端原型评审
```

### 4.1 两个采集前端

| 入口 | 主产物 | 适用场景 | 限制 |
|---|---|---|---|
| CLI | 静态 Import Bundle | agent 批量导出显式路由清单 | 登录和复杂页面状态准备成本高 |
| 浏览器插件 | 高保真 Editable Snapshot Bundle | 当前标签、真实登录态、Agent 阅读与修改 | 默认单页；当前不能直接导入 prototype-html-css |
| 静态原型派生器 | 从高保真 bundle 生成的 Import Bundle | 需要把插件产物送入现有原型评审 | 会显式移除或降级脚本、事件和 iframe |

浏览器插件另见《高保真网页工程导出浏览器插件开发方案》。插件与静态导出工具可以共享 parser、资产哈希和报告等底层能力，但必须使用不同的保留策略和产物协议：插件以保真为先，静态原型派生器才执行 prototypeGate 所需净化。

### 4.2 Import Bundle v1

建议目录：

```text
page-export-bundle/
  manifest.json
  state.json
  pages/
    <route-slug>/prototype.html
    <route-slug>/prototype.css
  assets/
    images/<content-hash>.<ext>
    fonts/<content-hash>.<ext>
  reports/
    capture-report.json
    normalize-report.json
    preflight-report.json
```

manifest 每页至少包含：

- `sourceKey`：源项目稳定标识与 routeKey 组合，例如 `<sourceProjectKey>:<routeKey>`。
- `pageId`：首次导入后写入映射；后续导入必须携带。
- `routeKey`：开发项目路由主键，不因创作端页面重命名而变化。
- `name`、`prototypeHtml`、`prototypeCss`、`order`、`parentId`。
- `capture`：URL、标题、时间、viewport、采集前端、页面状态备注。

`state.json` 保存目标 projectId、sourceKey→pageId 映射和上次导出摘要。CLI 或静态原型派生器负责维护该映射；高保真插件使用自己的 Editable Snapshot 契约。映射冲突时停止，不根据名称猜测页面。

### 4.3 静态原型派生的可读性与视觉保真原则

- HTML 使用 DOM parser 解析、语义净化和稳定格式化，不用正则承担结构解析。
- CSS 使用 CSS AST 解析；只做安全的作用域改写与格式化，不排序声明，不进行可能改变 fallback/cascade 的激进合并。
- 保留原有 id、class、ARIA 和 `data-*` 中有定位价值的属性；移除 React/Vue 运行时噪声和 SingleFile 内部标记前必须有 allowlist。
- 图片与字体按内容哈希命名，跨页去重，避免序号冲突。
- 可读性优化不能恢复源组件语义；产物是“可读的运行态 HTML/CSS”，不是“还原的项目源码”。
- 默认保留原始 SingleFile HTML 作为可选诊断工件，但不导入创作端。

## 五、可靠导入与失败安全

### 5.1 三阶段命令语义

1. `capture/normalize`：只生成 bundle，不修改创作端。
2. `preflight`：在临时事务中写入、执行 prototypeGate、edit validate、runtime validate 和 diff，随后放弃事务，不提交。
3. `import --commit`：复用已确认 bundle，显式提交。

`--dry-run` 只允许表示“打印执行计划”；若保留该名称，输出必须明确 `validationPerformed: false`。内容验证统一使用 `--preflight`，避免混淆。

### 5.2 默认行为

- 默认只生成 bundle 或 preflight，不提交。
- 只有显式 `--commit` 才能提交。
- 任一请求页面失败时整体失败；只有显式 `--allow-partial` 才生成部分 bundle。
- 部分 bundle 必须在 manifest 和报告中列出缺失 routeKey，导入时再次确认。
- Cookie 文件写入系统临时目录，权限为当前用户可读，finally 中删除；bundle 中禁止包含 Cookie、JWT 和密码。

## 六、评审与意见回流契约

已实现的批注→AI 路径继续保留。意见回流以持久化评论线程为事实来源：

```json
{
  "contractVersion": 1,
  "sourceKey": "web-app:/settings",
  "pageId": "page_xxx",
  "routeKey": "/settings",
  "threadId": "thread_xxx",
  "anchor": {
    "domPath": "...",
    "pin": { "xRatio": 0.4, "yRatio": 0.3 },
    "textSnippet": "..."
  },
  "text": "调整标题与按钮间距",
  "createdAt": "...",
  "resolved": false,
  "status": "open"
}
```

约束：

- routeKey/sourceKey 用于定位源码路由；DOM path 只作快照内视觉参考。
- screenshot 为可选扩展字段，只有真实截图工件存在时输出，不再写成必有字段。
- 临时 visual annotations 不属于 comments store；若未来需要回流，必须先定义持久化语义，不能让 exporter 猜测内存状态。
- 回写 resolved/status 应通过正式 API 或 CLI，不直接编辑 `comments.json`。

## 八、验收标准

### 8.1 CLI 导出

- 至少覆盖根路由、三级嵌套路由、动态路由样例和失败路由。
- 多页重复图片正确去重，不发生跨页覆盖。
- 单页失败时默认不生成可提交结果。
- 报告按 routeKey 给出 capture、normalize、size、asset、prototypeGate 状态。

### 8.2 重复导入

- 首次导入记录 pageId。
- 相同 sourceKey 第二次导入更新同一 pageId，页面数量不增加。
- routeKey、页面名称或映射发生冲突时停止并提供人工选择，不静默创建后缀页面。

### 8.3 安全与提交

- bundle 不含 Cookie、JWT、密码或浏览器存储内容。
- preflight 不改变当前项目版本。
- 不传 `--commit` 时不得提交。
- prototypeGate、事务校验和 runtime 校验均通过后才允许 commit。

### 8.4 评审闭环

- 原型页创建批注并发送 AI 后，修改落入 prototype.html/css。
- 评论导出包含稳定 sourceKey、routeKey、pageId 和 threadId。
- agent 能按 routeKey 定位源码并通过正式接口回写状态。

## 九、风险与决策记录

| 风险 | 当前决策 |
|---|---|
| SingleFile 产物不是源码 | 接受；定位为可读运行态快照，不承诺组件恢复 |
| 原型页无交互 | 接受；需要交互的页面升级高保真页 |
| 动态路由无法穷举 | 显式 route/scenario manifest 为主，自动发现只生成候选 |
| 高保真与静态产物策略混淆 | 使用两个独立契约；只共享底层 parser/asset 工具，净化仅发生在静态派生器 |
| SingleFile AGPL | 内部使用仍需完成合规确认；分发插件前必须确认 AGPL 开源义务或取得商业许可 |
| DOM/CSS 净化改变视觉 | AST 转换、原始快照保留、截图 diff 和 prototypeGate 联合验证 |
| 凭证泄漏 | Cookie 只进临时目录，finally 清理，bundle 敏感信息扫描 |
