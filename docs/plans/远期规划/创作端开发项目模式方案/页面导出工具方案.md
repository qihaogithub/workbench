# 页面导出工具方案

> 创建日期：2026-07-26
> 更新日期：2026-07-26（评估后接入创作端批注→AI 评审闭环与意见回流）
> 状态：方案设计中（P0 未实现）
> 定位：让 Codex 等 agent 把开发项目所有页面同步到创作端，接通创作端「批注→AI 修改」评审闭环，评审意见回流开发项目

## 一、方案概览

**一句话**：Codex 等 agent 在开发项目目录运行 `export-pages` skill → 把项目中**所有页面**批量导出为静态 HTML（SPA 渲染快照或源码净化）→ normalize 脚本转换（含 routeKey 锚点注入）→ 调用创作端已有 CLI（`ow project import-prototype`）导入为**原型页** → 评审者在创作端画布中批注/评论，AI 直接修改原型页 → 意见按 routeKey 导出回流，agent 在开发项目消费并落到源码。

**目标**：让开发项目页面融入创作端现有评审工作流——评审者在创作端画布中查看项目全部页面，用批注/评论提出意见，AI 负责修改；意见以结构化契约回流开发项目，由 agent 按路由定位源码逐条落地。页面更新后可重复同步（重新导出 + 按页面 ID 更新已有原型页），保持两侧一致。

**关键结论**：

- 创作端已有完整原型导入链路与静态安全红线校验，**导出通道零修改成立**
- 创作端「批注→AI 修改」评审闭环对原型页存在**半成品缺口**（批注交互缺失、AI prompt 写死 `index.tsx`），需三处局部接线补齐——属补既有欠账，非新增模块
- `single-file-cli`（CDP 驱动系统 Chrome）是现成渲染/资源内联引擎，无需自研；唯一自研部分是 normalize 转换脚本（含 routeKey 锚点注入）
- 评审意见回流以 **routeKey 契约**为主键；该契约是评审闭环的公因子，后续换同步通道（如双向 diff）契约不变

## 二、背景

开发项目（代码在外部 Git 仓库，由 Codex 等 agent 工具负责编码）与创作端（可视化编辑、画布预览、评审与发布）目前是两个割裂的环境：页面评审需要切换到开发项目的 dev server 逐个查看，修改意见通过口头或文字转达给开发者，无法复用创作端已有的画布查看、批注和评审工作流。

创作端现有的评审工作流载体是「可视化批注与编辑」：单页预览点击元素 → 批注浮层（文字/临时样式）→ 批注、属性变更、选区组装成限定范围的 AI prompt → 自动发送到 AI 对话 → AI 修改页面文件 → 用户回到对话区审阅。**只有接入这条链，「把页面迁入创作端」才等于「融入评审工作流」**；否则评审体验退化为「查看 + 评论级标注」，意见仍需人工转达。

同步是可重复的：页面更新后 agent 重新导出，并按页面 ID 更新已有原型页（`page update-prototypes`），保持创作端与开发项目一致。

## 三、可行性结论

**可行**，依据四条已核实的既有事实：

### 1. 创作端已有完整原型导入链路（导出通道零修改成立）

- `ow project import-prototype --manifest <json>`：批量导入外部 HTML/CSS 原型项目，事务工作流 = doctor → project create → edit begin → `asset upload-dir` → `page update-prototypes` → edit validate → edit diff → `project validate-runtime` → 可选 `--commit`（`packages/project-cli/src/index.ts`）。
- Manifest 格式：`pages[]`，每页支持 `pageId` / `name` / `routeKey` / `prototypeHtml`(或 `html`) / `prototypeCss`(或 `css`) / `prototypeMeta` / `schema` / `order` / `parentId`；字符串支持 `@./file.html` 文件引用（`parsePrototypeManifest` / `readTextValue`）。
- 资产目录通过 `--assets <from>:<to>` 上传，创作端登记到 `assets/images/` 并自动改写页面相对引用。
- 远程图片 URL 在导入时自动下载本地化（见 `docs/项目文档/创作端/10-CLI/技术/02_本地项目包与脚手架同步.md`、`03-项目管理/技术/12_发布资源本地化.md`）。

### 2. 原型页有明确的静态安全红线（导出产物必须满足）

`packages/project-core/src/service.ts` 的 `prototypeGate` 校验：

| 红线 | 结果 |
|---|---|
| `<script>` 标签 | upgrade_to_high_fidelity（不可自动修复） |
| 内联事件属性 `on*` | upgrade_to_high_fidelity |
| `javascript:` URL（HTML 或 CSS） | upgrade_to_high_fidelity |
| `iframe` / `embed` / `object` | upgrade_to_high_fidelity |
| 带 `action` 的 `form` | upgrade_to_high_fidelity |
| CSS `@import` | repair_prototype（可自动修复） |
| CSS 直接选择 `html` / `body` / `:root` | repair_prototype |
| HTML 空 / HTML > 2MB / CSS 过大 | repair_prototype |

即：导出工具必须产出「无脚本、无事件、无内嵌运行时、无远程 CSS 导入、CSS 局部化」的静态 HTML+CSS，才能以 `accept_prototype` 通过校验。

### 3. SingleFile CLI 是现成渲染/内联引擎

- npm 包 `single-file-cli@2.0.83`，依赖 `simple-cdp` + `ws`，通过 Chrome DevTools Protocol 驱动**系统已安装的 Chrome**（无需内置 Puppeteer）。
- 支持批量 URL 导出为单个自包含 HTML：CSS `@import` 展开、字体/图片内联、canvas 序列化、Shadow DOM、iframe 递归处理。
- 输出为渲染后 DOM 快照，默认移除脚本执行环境。
- 我们不需要维护渲染与资源内联这一层（这是 SingleFile 的价值所在），只在其输出上做转换。

### 4. 评审闭环现状：创作端「批注→AI 修改」对原型页有半成品缺口，补全成本低

创作端评审工作流 = 可视化批注（`VISUAL_ANNOTATION_CREATE`）→ 组装限定范围 AI prompt → AI 修改页面文件 → 用户审阅（见 `docs/项目文档/创作端/04-配置与预览/技术/06_可视化批注与编辑机制.md`）。

现状：原型页（`prototype-html-css`，Shadow DOM 渲染）上该闭环**四环全断**：

1. **无批注交互**：`PrototypePagePreview.tsx:19-44` 的 props 无 `visualAnnotations` / `onVisualAnnotationCreate` / 批注模式；批注脚本（`iframe-template.ts:63-198`）只注入 iframe document，对 Shadow DOM 无效。
2. **批注 UI 未接线**：编辑页 `page.tsx:8059` 硬编码 `visualAnnotationMode: false`，`handleStartVisualAnnotation` / `handleSendVisualAnnotationsToAI` 未被任何组件使用。
3. **AI 修改目标写死**：批注→AI 的 prompt 固定指向 `demos/<id>/index.tsx`（`useVisualEditState.ts:1423`），原型页只有 `prototype.html` / `prototype.css`，AI 无从修改。
4. 评论锚点已支持原型页（`CommentLayer.tsx` 的 `composedPath` + `prototype-root`），但评论不驱动代码修改——可作 P0 期评审兜底。

**补全 = 三处局部接线（均既有半成品欠账，非新增模块）**：原型页 renderer 补批注交互（复用 iframe 批注逻辑或直接接 `onVisualAnnotationCreate`）、接通批注 UI 与状态、AI prompt 按 `runtimeType` 分流到 `prototype.html/css`。

## 四、核心设计

### 4.1 两条路径（先做 SPA 路径）

| 路径 | 适用项目 | 引擎 | 产物 |
|---|---|---|---|
| **A. SPA 渲染抓取** | Next.js / Vite / React / Vue 等，源码 HTML 只有挂载点 | `single-file-cli <urls> --output-directory out/` | 渲染后自包含 HTML |
| **B. 静态源码净化** | 纯静态 HTML/CSS 项目 | 直接读取源码 HTML + 净化脚本 | 源码级 HTML（可读性最好） |

纯静态项目**不需要引入 SingleFile 与 headless Chrome 依赖**，直接净化源码；SPA 项目必须渲染抓取。首批先做 A 路径，B 路径作为同一 normalize 脚本的简化分支（净化规则复用）。

### 4.2 数据流（含评审与回流）

```
开发项目 dev server（已启动）
        │ 路由清单（agent 提供，或脚本扫描 pages/app/routes）
        ▼
single-file-cli <urls> --output-directory out/    （仅 SPA 路径）
        │  渲染后单文件 HTML（图片 base64 内联、样式 <style> 内联、无脚本）
        ▼
normalize 脚本（唯一需要自研的部分）
  1. 提取 <style> 内容 → prototypeCss（HTML 与 CSS 分离，符合 manifest 字段）
  2. base64 图片 → 落地 out/images/，改写 <img>/CSS url() 为相对路径
  3. 红线净化：删内联事件属性、javascript: URL、iframe/embed/object、form action
  4. CSS 局部化：html/body/:root 选择器改写为 .prototype-root 容器内局部选择器
  5. 锚点注入：页面根元素加 data-route="<routeKey>"（评审意见可映射回路由）
  6. 生成 manifest.json（prototypeHtml 用 @./out/<page>.html 文件引用）
        │
        ▼
ow project import-prototype --source . --manifest @./manifest.json \
     --assets out/images:assets/images --dry-run   （先 dry-run 校验）
        │
        ▼
ow project import-prototype ... --commit --json     （确认后提交）
        │
        ▼
创作端原型页（prototype-html-css），可直接预览/编辑/发布
        │ 评审：画布批注/评论（P1 接通批注→AI 修改，改动落回 prototype.html/css）
        ▼
意见回流：{ routeKey, anchor, 正文, 截图 } → JSON 导出
        │
        ▼
agent 在开发项目按 routeKey 定位对应路由源码 → 消费意见落地修改
```

### 4.3 normalize 脚本职责（几十行级）

- **样式分离**：SingleFile 输出全部样式在 `<style>` 中；取 `document.head` 内 `<style>` 文本合并为 `prototypeCss`，HTML 中移除（保留内联 `style` 属性）。
- **锚点注入**：页面根元素加 `data-route="<routeKey>"`；manifest 的 `routeKey` 与开发项目路由一一对应，作为评审意见回流的主键。
- **图片策略**：
  - 推荐：base64 提取为独立文件 + 语义化命名（`img-001.png`），HTML/CSS 改写相对路径，走 `--assets` 上传资产化。不依赖 dev server 存活，且不撑爆 2MB HTML 上限。
  - 备选（更轻）：SingleFile 配置大图不内联，保留 dev server 上的资源 URL，由创作端导入时自动下载本地化。依赖导入时 dev server 存活，若失败则保留外链 + 导入警告。
  - 落地实现时做成可选项，默认走推荐策略。
- **红线净化**：按 4.2 节步骤 3/4 的正则 + DOM 级处理兜底（HTML 解析后再序列化，避免正则误伤文本节点）。
- **体积控制**：HTML 超 2MB 时逐页报告并提示压缩/拆页（Figma 大导出已有同款约束处理）。

### 4.4 路由清单来源

- 显式提供（agent 在开发项目里列出要导出的路由）；
- 自动发现：Next.js 扫 `app/**/page.tsx` / `pages/**`，Vite 扫 `src/router` 配置（P0，「所有页面」是核心诉求，手动列路由违背自动化初衷）。

### 4.5 评审闭环与意见回流（本方案的闭环核心）

**创作端接线（P1，三处局部改动，补既有半成品欠账）**：

1. 原型页 renderer（`PrototypePagePreview`）补批注交互：批注模式、pin、`onVisualAnnotationCreate` 回调——复用 iframe 批注逻辑或直接接创作端批注状态。
2. 接通批注 UI 与状态：去掉 `visualAnnotationMode: false` 硬编码，挂载批注入口，打通 `handleStartVisualAnnotation` / `handleSendVisualAnnotationsToAI`。
3. AI prompt 按 `runtimeType` 分流：原型页指向 `prototype.html` / `prototype.css`（替换写死的 `demos/<id>/index.tsx`）。

**意见回流契约（评审闭环公因子）**：

- 意见 JSON 单条格式：`{ pageId, routeKey, anchor: { domPath, pin }, text, screenshot, status }`；`routeKey` 来自 normalize 注入的 `data-route`（或 manifest），`anchor` 为创作端批注/评论既有锚点。
- 导出方式：读创作端评论/批注数据（已有 API）生成回流 JSON，不新增创作端存储。
- 消费侧：`export-pages` skill 文档固化「导入意见 JSON → 按 routeKey 定位开发项目对应路由源码 → 逐条处理 → 回写状态」，与下一次导出形成循环。
- 契约与通道解耦：后续若从「快照导入」升级为「本地项目包双向同步」，该契约不变。

## 五、工具形态：独立目录 + 项目级 skill

- 在 opencode-workbench 仓库内建独立工具目录（如 `tools/page-export/`，与 `OPS/`、`packages/` 平级或归入 OPS 下，落地时定），包含：
  - `export.mjs`：编排（起 dev server 检查 → 路由发现 → 批量导出 → normalize → manifest 生成 → 调用 CLI）
  - `normalize.mjs`：净化/转换脚本（4.3 节）
  - `export-opinions.mjs`：读创作端评论/批注数据 → 生成回流 JSON（4.5 节契约）
  - `README.md`：使用说明
- 在 `.reasonix/skills/` 注册项目级 skill（如 `export-pages`）：skill 文档描述「何时用、前置条件、步骤、常见失败与修复、评审意见回流消费流程」，运行时让 agent 按文档调用上述脚本。
- 与 `opencode-project-admin` skill 的关系：导出工具负责「从开发项目产出可导入目录 + 回流意见消费」，导入动作复用现有 project-cli（`ow project import-prototype`），不重复造导入轮子。
- 运行环境：开发项目目录（导出端）+ 已配置的 project-cli（导入端）；需要系统 Chrome（SPA 路径，CI/容器需预先安装）。
- 创作端改动范围：仅 4.5 节三处接线，无新页面类型、无新数据模型（意见复用既有评论/批注数据）。

## 六、边界与风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 渲染后 DOM 非源码 | SPA 导出是运行态快照，CSS Modules/Tailwind 类名为哈希，HTML 可读性低于 Figma 导出 | 属预期；评审/归档场景可接受；静态项目走 B 路径保留源码可读性 |
| 原型页无交互 | 导入后是静态原型页，按钮点击等行为不可用（创作端原型页不执行 JS，产品语义） | 明确告知用户；需要交互的页面升级高保真页 |
| 评审闭环依赖创作端接线 | 原型页批注→AI 修改是创作端既有半成品，未接线前评审=评论级 | P1 补三处接线（改动局部，复用既有能力） |
| 意见回流锚点只到路由级 | 快照 DOM 锚点（哈希类名）对开发项目源码无意义 | 意见契约以 routeKey 为主键，锚点仅作创作端内定位；agent 按路由定位源码 |
| 依赖渲染状态 | 登录态/点击后才渲染的内容抓不到 | SingleFile 支持 cookies 复用；复杂交互场景先预置状态再导出 |
| 2MB HTML 上限 | base64 大图易超限 | 图片落地 + 资产化（推荐策略）后 HTML 保持小体积 |
| 跨域资源 | 第三方 CDN 资源可能内联失败或体积膨胀 | 净化时报告未内联资源；必要时 allowlist |
| 创作端导入依赖 dev server（备选图片策略） | 保留 URL 时导入需 dev server 存活 | 默认推荐 base64 落地策略，避免该依赖 |
| SingleFile 依赖系统 Chrome | agent 运行环境（CI/容器）可能无 Chrome | skill 前置条件写明；容器内预装 Chrome 或走 B 路径 |

## 八、验证方式

- 导入前：`ow project import-prototype ... --dry-run --json`，检查 `prototypeGate.decision === "accept_prototype"`（或 repair 项可被创作端自动修复）。
- 导入后：创作端原型页预览 + `project visual-check` 截图，确认视觉还原度与图片资产引用。
- 评审闭环：原型页预览进入批注模式 → 创建批注 → 发送 AI → 确认修改落到 `prototype.html` / `prototype.css` 并回流预览。
- 意见回流：导出意见 JSON → 在开发项目按 routeKey 定位对应路由源码 → 按契约逐条消费。
- 回归：`pnpm check:project-core` / `pnpm check:project-cli`；创作端接线改动走 `pnpm check:author` + `pnpm check:demo-ui`。

## 九、方案定位

- 本方案为「开发项目页面 → 创作端画布评审」提供完整闭环：agent 批量导出 → normalize 转换（含锚点）→ 创作端 `import-prototype` 导入 → 画布批注/评论 + AI 修改 → 意见按 routeKey 回流开发项目，且可重复同步更新。
- 不引入 agent-service 服务端新能力；创作端仅补既有批注链路的三处局部接线，不新增页面类型、不新增数据模型。
- 本方案聚焦页面同步与评审；如需实时代理预览、状态变体覆盖、AI 直接改码等更强协作能力，另行评估扩展方案（如本地项目包双向同步），不在本方案内实现。
