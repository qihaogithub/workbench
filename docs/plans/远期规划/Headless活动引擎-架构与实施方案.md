# Headless 活动引擎与活动项目类型架构方案

> 状态：远期规划，待产品与技术评审  
> 更新日期：2026-08-31  
> 文档性质：架构方案与分阶段实施建议  
> 说明：本文仅做方案分析，不包含代码修改。

## 一、背景

当前 Workbench 的创作端和使用端的产品定位是“生产 Demo”和“浏览 Demo”：创作端负责把内容做成可预览的 Demo，使用端负责把 Demo 展示出来。这条链路不是生产真实线上页面的链路，也不承担真实活动的线上运行责任。

新的设想不是把 Demo 链路直接改造成线上系统，而是在现有创作端内部增加“真实页面生产”能力，并建设一个独立的 Headless 活动引擎。创作端生产真实页面包和活动定义，Headless 活动引擎接收这些生产包，负责真正的部署、上线、运行、扩缩容、状态管理和版本切换。

提出的新系统是 **Headless 活动引擎**（Headless Activity Engine）：

- 引擎负责活动的业务逻辑、状态、玩法、参与者、权限、调度和运行时治理；
- 创作端保留当前的 Demo 生产能力，同时增加真实页面生产能力，相当于把“毛坯活动”装修成可上线的页面包；
- 真实页面包和活动定义交给独立引擎，由引擎负责接收、校验、部署到线上运行环境、激活、暂停、灰度和回滚；
- 真实页面的客户端负责渲染和发起交互，通过引擎 API 读取状态、提交动作；
- 当前使用端继续作为 Demo 浏览器，不自动变成真实线上页面的托管端。

“无头”在这里不是无页面，而是活动引擎不绑定一套固定的页面 UI。真实页面可以由 Workbench 创作端生产，也可以由其他前端、H5、App 或第三方客户端实现；但只要要承载真实流量，就必须通过引擎的生产部署和运行时协议上线。

本文所说的“真实页面”，指经过生产构建和安全校验、能够绑定正式域名或正式路由、由 Headless 引擎部署并承载真实用户流量的页面，不是当前使用端里的 Demo 页面或预览 iframe。

## 二、项目类型设计

### 2.1 推荐命名

建议不要把新类型的产品名直接定为“正式项目”。“正式”描述的是生命周期状态，不是项目的业务类型；将来会出现“正式项目的测试环境”“正式项目尚未激活”等表达，容易和是否上线混淆。

推荐使用以下名称：

| 产品名称 | 技术标识 | 定位 |
| --- | --- | --- |
| **Demo 项目**（Demo Project） | `projectKind: "demo"` | 当前已有类型，用于生产 Demo、预览、评审和演示 |
| **活动项目**（Production Activity Project） | `projectKind: "activity"` | 新增类型，所有页面基于 Headless 活动引擎能力搭建，支持生产和部署上线 |

在需要强调二者对比的说明中，可以把“活动项目”称为“正式活动项目”；但建议 UI、API 和数据模型使用“活动项目 / `activity`”，不要使用含义过宽的“正式项目”。如果未来引擎承载的不只是活动，也可以将产品名升级为“生产项目”，但当前阶段“活动项目”更能表达其运行时约束。

需要注意，当前代码中的 `ProjectType` 仍表示 `"standard" | "template"`（见 `packages/shared/src/workspace.ts:275`），主要服务于模板项目识别，不应直接把它改造成 `demo/activity`。建议新增正交的 `projectKind` 字段：`projectType` 继续表示普通项目/模板项目，`projectKind` 表示 Demo 项目/活动项目。这样可以表达“活动项目模板”这类组合，也避免破坏现有模板语义。

### 2.2 两类项目的能力矩阵

| 能力 | Demo 项目 | 活动项目 |
| --- | --- | --- |
| 页面定位 | Demo 页面、预览页面 | 真实线上页面 |
| 页面生产方式 | 沿用当前 Demo 生产能力 | 新增生产构建能力，生成 ProductionPagePackage |
| 页面运行基础 | 当前 Demo/Preview runtime | Headless 活动引擎 runtime 与页面协议 |
| 业务状态 | 浏览器/预览态，仅供演示 | 引擎服务端权威状态 |
| 活动定义 | 可选或不需要 | 必须具备并经过引擎校验 |
| 使用端 | 当前 `viewer-site` 浏览 Demo | 由引擎部署的真实页面入口承载流量 |
| 部署入口 | **不提供** | 提供，由 Headless 引擎负责执行 |
| 域名/路由 | Demo 访问地址 | 引擎管理的生产域名、路由和版本流量 |
| 外部效果 | 不承诺真实支付、奖励、消息等 | 通过引擎受控命令和 outbox 接入 |

活动项目的硬约束是：项目中的每一个页面都必须基于引擎支持的页面运行时和交互协议搭建。页面可以有不同视觉风格，但不能存在一部分页面走引擎、一部分页面绕过引擎的隐式混合模式。页面需要声明 routeKey、活动字段绑定、可用 command/query 和运行时能力；不满足这些约束的页面不能进入真实生产包。

### 2.3 项目类型边界

- 项目创建时必须选择 `projectKind: "demo"` 或 `projectKind: "activity"`；该能力类型建议创建后不可直接切换。
- Demo 项目不显示“生产真实页面”“部署上线”“激活/回滚”等入口，也不能调用活动引擎的生产部署 API。
- 活动项目创建时应建立与引擎的活动标识和环境边界；未部署前可以在创作端预览，但预览不等于线上激活。
- Demo 转活动应是显式的“创建活动项目/导入页面/重新绑定活动定义”流程，而不是把一个开关从 `demo` 改成 `activity`。
- 活动项目的页面包、活动定义和引擎 deployment 必须成套版本化；不能只发布其中一部分。

## 三、核心判断

这个方向技术上可行，但应明确为“新增生产系统”，而不是把当前 Demo 发布接口改名为 `deploy`。现有 `AppGraph` 也不能原样搬到新服务。需要新增一个独立的引擎，既提供活动运行时，也提供真实页面的部署与上线能力，并明确区分以下概念：

| 操作 | 解决的问题 | 权威对象 |
| --- | --- | --- |
| Demo 生产 | 生成用于预览和评审的 Demo | Demo Artifact |
| 真实页面生产 | 生成可交给线上系统运行的页面包 | Production Page Package |
| 部署（deploy） | 将真实页面包和活动定义安装到线上运行环境 | Headless Engine Deployment |
| 激活（activate） | 当前真实流量使用哪个完整版本 | Active Release |

综合判断：业务价值明确，技术可行性高；对现有 Demo 链路的兼容性高，但新增真实页面生产、线上部署和活动运行时的实施复杂度高。建议推进，但应从一个范围受控、规则清晰的真实活动类型开始，不宜一次性把所有 Demo 项目迁移到新引擎。

## 四、目标

### 4.1 产品目标

1. 保留现有 Demo 生产/浏览体验，并将其与真实生产链路明确隔离。
2. 在创作端建立清晰的 Demo 项目 / 活动项目类型边界，让项目类型决定可用能力。
3. 让活动项目能够从项目内容生产真实页面包，而不是只能生产 Demo。
4. 让独立引擎真正负责真实页面的部署上线，包括页面托管/分发、活动运行时和版本切换。
5. 让活动业务逻辑与页面外观解耦，同一套玩法可以被多个页面、渠道和客户端复用。
6. 让创作者关注页面体验与配置，不必为每个活动重复实现参与者状态、规则判断、幂等和并发处理。
7. 让引擎成为业务状态的唯一权威，页面刷新、重复点击或更换客户端不会破坏活动状态。

### 4.2 技术目标

- 定义版本化的活动契约（Activity Definition）、真实页面包契约（Production Page Package）和部署契约（Activity Deployment）；Demo Artifact 不得被误认为生产包。
- 采用服务端状态机/规则执行模型，支持命令幂等、并发控制、审计和可观测性。
- 让真实页面通过稳定的运行时协议获取 manifest、会话、状态和事件，而不是直接修改浏览器内存中的全局状态。
- 让引擎拥有真实页面的部署流水线和线上流量入口，部署切换以不可变版本对为单位，避免“活动规则已更新但页面仍是旧版”的半更新状态。
- 为未来的多租户、权限、第三方效果、定时任务、灰度流量和数据分析预留边界。

## 五、非目标与边界

本阶段不计划：

- 用引擎替换创作端的 Demo 编辑器、Demo 预览器或页面组件系统；
- 把任意页面 JavaScript 当作可信的后端业务逻辑执行；
- 直接迁移所有现有 Demo 项目或马上废弃当前 Demo 链路；
- 给 Demo 项目增加活动项目才有的真实页面生产、引擎运行时和部署上线能力；
- 把 Workspace Authority、Agent EventBus 或浏览器 `appState` 直接升级为活动运行时；
- 在没有明确业务场景的情况下设计通用的“万能规则语言”。

引擎不负责替代创作端做页面设计，但必须负责真实页面包的线上部署和活动运行事实；创作端负责生产页面包与定义，不负责最终的业务状态和线上流量切换。

## 六、现状基线与问题

### 6.1 当前链路是 Demo 生产与 Demo 浏览

当前发布接口会先处理协同工作区的 flush/sync，再调用发布管理器生成 Demo 结果。按当前产品定位，这些结果用于预览、评审和 Demo 浏览，不等同于可直接承载真实流量的生产页面：

- `packages/author-site/src/app/api/projects/[projectId]/publish/route.ts:69-146` 负责鉴权、工作区同步和发布入口；
- `packages/author-site/src/lib/publish-manager.ts:515-1200` 负责页面编译、资源本地化、运行时文件复制、发布目录和发布快照；
- 当前结果可同步到 Cloudflare 等托管目标，但这仍属于 Demo 产物或现有基础设施能力，不代表已经形成“真实页面生产 + Headless 引擎部署”的产品链路。

这条链路可以复用其 Workspace flush、资源处理和编译经验，但未来需要新增明确的生产构建目标、生产配置、环境变量/密钥引用、安全校验和可部署页面包格式，不能把 Demo 目录直接当成真实生产包。

当前项目模型中的 `projectType: "standard" | "template"` 还没有表达“Demo 项目 / 活动项目”这一生产能力边界；现有项目在本方案中统一视为 `projectKind: "demo"`。新增活动项目时，应让项目类型在创建、权限、页面创建、预览、生产构建和部署入口处全链路生效，而不是只在项目列表上增加一个标签。

### 6.2 现有 AppGraph 更像导航图，不是活动引擎

`packages/shared/src/workspace.ts:193-214` 的 `AppGraph` 目前包含页面节点、动作、目标页面、参数、状态设置和条件字段；`packages/author-site/src/lib/viewer-app-graph-runtime.ts:56-112` 在浏览器内根据动作改变路由与内存状态。

当前实现存在几个边界：

- 状态主要存在 iframe/浏览器内存中，刷新后不具备参与者恢复语义；
- action 的 `condition` 虽然被保存和规范化，但当前运行时没有形成完整的服务端条件求值链路；
- 没有参与者身份、权限、配额、幂等键、并发版本或审计模型；
- 事件由预览层转发给宿主，适合演示交互，不适合作为跨客户端的业务事实来源。

因此 AppGraph 可以作为迁移输入或页面导航描述，但不应直接成为未来公开的活动引擎契约。

### 6.3 使用端目前只是 Demo 浏览器

`packages/viewer-site/src/components/ViewerApp.tsx:1338-1600` 当前主要根据 Demo 发布数据创建页面并渲染 `PreviewStage`；`packages/viewer-site/src/lib/api.ts` 的发布项目类型也没有形成稳定的真实活动运行时协议。现有部署文档（`docs/项目文档/使用端/03-部署与嵌入/`）重点解决 viewer-site、静态发布目录、CORS 和 iframe 的 Demo 部署，属于 Demo 基础设施，不是某个真实活动页面的线上部署。

真实线上页面原则上应由 Headless 引擎的生产入口提供，或由引擎控制其域名、路由和静态资源分发；不能把当前 `viewer-site` 直接升级为生产托管端，也不能把静态 Demo 目录当作业务状态服务。

### 7.1 各层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 创作端 | Demo 生产、真实页面生产、样式/素材/配置、活动绑定、预览、交付申请 | 最终参与者状态、奖励发放、跨请求规则一致性、线上流量切换 |
| Headless 活动引擎 | 真实页面包部署/托管/路由、活动定义、状态机、命令、规则、参与者、权限、调度、审计、激活/暂停/回滚 | 页面设计和任意不受控页面脚本 |
| 当前使用端 | Demo 浏览、评审和演示 | 真实线上页面托管、直接写业务数据库、决定生产规则结果 |
| 真实页面客户端 | 渲染已部署页面、采集用户操作、展示状态和错误、订阅更新 | 自行决定规则结果或绕过引擎改变业务状态 |
| 产物存储/CDN | 由引擎控制，保存和分发不可变生产页面包与资源 | 判断用户是否有资格参与活动 |
| 外部系统 | 登录、支付、奖品、消息、数据仓库等效果 | 绕过引擎直接改变活动状态 |

## 八、核心领域模型

### 8.1 ActivityDefinition：活动定义

ActivityDefinition 只属于 `projectKind: "activity"` 的活动项目。Demo 项目可以有页面跳转和演示状态，但不产生可部署的活动定义。

建议至少包含以下概念，具体字段应在 MVP 中收敛：

- `activityKey`、租户/项目归属、定义版本；
- 初始状态、状态变量及其类型/默认值；
- 可接受的 commands（命令）及输入 schema；
- guards（资格和条件）、transitions（状态转移）和 effects（外部效果）；
- participant policy（身份、参与次数、配额、时间窗口）；
- 调度策略、超时、暂停规则和终止规则；
- 与页面的绑定，如页面 routeKey、可用 action、展示所需的只读字段。

业务规则必须是受限、可审计的定义或服务端代码，不允许由页面传入任意后端脚本。

### 8.2 DemoArtifact 与 ProductionPagePackage：两类页面产物

必须从模型上区分 Demo 和真实生产页面，避免沿用“发布成功”这个词造成误解：

- `DemoArtifact`：当前创作端生产、当前使用端浏览的演示产物，允许服务评审和快速迭代，不承诺真实线上可用性；
- `ProductionPagePackage`：创作端新增生产能力生成的真实页面包，经过生产构建、安全检查、依赖锁定和环境配置校验，才允许交给 Headless 引擎。

真实页面包由创作端从已确认的 Commit 构建，建议包含：

- `packageId`、`projectId`、来源 `commitId`、生产构建工具版本；
- 页面树、runtime 类型、schema、资源 manifest、内容哈希；
- 页面与活动字段的绑定声明；
- 运行时能力和安全策略摘要；
- 环境变量/密钥引用（只保存引用，不携带密钥值）；
- 生成时间、操作者、生产校验和审计信息。

两类产物都应不可变。真实页面修订应生成新的 ProductionPagePackage，不能在已上线目录上原地覆盖；DemoArtifact 也不能被自动提升为生产包而跳过生产校验。

### 8.3 ActivityDeployment：活动部署

部署是一个“定义版本 + ProductionPagePackage + 线上环境”的不可变版本对，至少包括：

- `deploymentId`、`activityKey`、environment；
- `definitionVersion`、`packageId`；
- `staged / active / paused / superseded / failed` 等状态；
- 页面托管实例/域名/路由、校验结果、部署者、时间、激活策略和回滚引用。

当前激活引用应原子地指向一个完整的 deployment，不能分别切换定义和页面。

### 8.4 ParticipantSession、Command、Event

- `ParticipantSession`：参与者在某个活动部署下的会话和身份边界；
- `Command`：客户端请求引擎执行的意图，必须带 `idempotencyKey`；
- `Event`：引擎确认发生的事实，用于投影、通知、审计和外部效果；
- `Projection`：供页面查询的只读状态，不作为新的业务权威；
- `Outbox`：事务内记录待发送的外部效果，避免状态已提交但通知/奖励丢失。

需要明确区分三类数据：活动定义（可版本化配置）、参与者运行状态（动态业务事实）、密钥/凭证（仅服务端保管）。它们不能混在页面配置或公开 manifest 中。

## 九、运行时协议建议

协议名称和具体字段待评审，以下仅表示边界：

1. `GET /activities/{activityKey}/manifest`：返回当前已激活的真实页面入口、能力和只读字段摘要，不返回私密规则和密钥。
2. `GET /deployments/{deploymentId}/assets/*` 或受控域名路由：由引擎提供已部署真实页面和静态资源，不暴露创作端 Demo 目录。
3. `POST /activities/{activityKey}/sessions`：创建或恢复参与者会话，校验登录/资格/环境。
4. `POST /sessions/{sessionId}/commands`：提交命令，携带 `idempotencyKey`、客户端版本和必要参数。
5. `GET /sessions/{sessionId}/state`：读取经过权限过滤的投影状态。
6. `GET /sessions/{sessionId}/events` 或 SSE/WebSocket：订阅状态变化、命令结果和可展示事件。

命令处理应满足：服务端鉴权、schema 校验、资格/guard 判断、并发版本检查、幂等去重、状态转移、事件和 outbox 原子记录。客户端只能把结果当作事实，不能根据本地预测结果自行发放奖励或跳过限制。

## 十、部署生命周期

建议将“Demo 生产”“真实页面生产”和“引擎部署”设计成相互区分、可独立重试的流程：

1. **Demo 生产（现有链路）**：创作端生成 DemoArtifact，交给当前使用端预览、评审和演示。
2. **生产准备**：创作端确认 Workspace 已 flush，生成 canonical proof 和来源 `commitId`，选择要生产的页面、活动定义和生产环境。
3. **真实页面生产**：创作端使用新的生产构建能力生成 ProductionPagePackage，完成依赖锁定、资源处理、生产配置、安全校验和内容哈希。
4. **提交生产包**：创作端把 ProductionPagePackage、ActivityDefinition 版本、manifest 和绑定声明上传给独立引擎。
5. **引擎校验**：引擎校验 schema、引用完整性、页面绑定、能力白名单、域名/路由、环境策略和版本兼容性。
6. **引擎部署**：引擎将真实页面包安装到线上页面运行环境，配置静态资源、域名/路由、活动 API、扩缩容和运行时隔离，形成不可变 deployment。
7. **暂存与验收**：执行健康检查、冒烟请求和必要的页面/活动联调，状态为 `staged`；失败不得影响当前激活版本。
8. **激活**：按立即、定时、灰度或人工审批策略，把真实流量入口原子切换到该 deployment。
9. **运行与观测**：收集页面可用性、命令成功率、拒绝原因、延迟、状态版本、外部效果和资源错误。
10. **暂停/回滚**：暂停接受新命令或页面流量，或把真实流量入口切回已验证的旧 deployment；页面与定义一起回滚。

这里的“部署”必须是引擎的真实职责，而不只是登记一条部署记录：引擎需要负责生产包的接收、安装、线上访问入口、运行环境、流量切换和回滚。页面的生产构建可以由创作端完成，但页面何时、以什么版本、通过什么域名真正上线，由引擎控制。

## 十一、与现有模块的关系

| 现有模块 | 目标角色 | 必须守住的边界 |
| --- | --- | --- |
| `author-site` | 按 `projectKind` 提供 Demo 生产或活动项目的真实页面生产、预览、生产包校验和交付 | Demo 项目不得出现活动项目入口；不直接写引擎运行状态，不直接切换线上流量 |
| `project-core` | 项目包、Commit、资源和生产构建输入的一致性服务 | 不承载参与者运行时和线上托管 |
| `shared` | 版本化的跨端类型、校验器和运行时能力声明 | 公共契约需向后演进，不能泄漏内部存储模型 |
| `demo-ui` / Preview | Demo 交互、Demo 预览和生产页面的开发期联调 | Demo/联调状态不能冒充线上业务事实 |
| `viewer-site` | 当前 Demo 浏览、评审和演示 | 不作为真实线上页面托管端，不维护第二套业务规则 |
| Headless Engine | 接收生产包、真实页面部署/托管/路由、活动运行时、激活/暂停/回滚和线上治理 | 不承担页面设计和创作端编辑 |
| `agent-service` | 可选的 AI 活动生成/运营助手 | 只能提交受控定义或命令，不能绕过引擎写状态 |
| `data/published` / Demo CDN | 当前 Demo 产物的存储和分发 | 不作为真实页面生产源或活动状态数据库 |
| sandbox runtime | 隔离页面代码和不可信内容 | 不向页面注入引擎密钥或宿主会话 |

现有 Workspace Authority 的单实例写入语义应继续用于创作态提交；它不是参与者运行时的事务协调器。`agent-service` 当前的进程内 EventBus 也不能直接承担跨实例、可恢复的活动事件总线。

## 十二、分阶段实施路线

### Phase 0：区分 Demo 与生产，并收敛契约

- [ ] 选择一个具体 MVP 活动（例如单人答题、抽奖资格或有限状态报名），明确参与者、状态和命令。
- [ ] 固化 ActivityDefinition、DemoArtifact、ProductionPagePackage、Deployment、Command/Event 的最小 schema。
- [ ] 明确 Demo 产物和生产页面包的校验、权限、环境和存储边界。
- [ ] 定义部署状态机、错误码、幂等和权限模型。
- [ ] 明确页面 routeKey 与活动字段绑定规则，避免把当前 AppGraph 的内部字段直接公开。

### Phase 1：纯规则内核

- [ ] 在独立包中实现确定性的 reducer/规则执行器和 schema 校验。
- [ ] 覆盖状态转移、guard、幂等、并发版本和事件输出测试。
- [ ] 不接入页面、不接入外部奖励，先用内存 fixture 验证领域语义。

### Phase 2：独立 Headless 引擎与真实部署底座

- [ ] 新增独立的 `activity-core` / `activity-service` 边界，避免把运行时塞进 `author-site`。
- [ ] 引入持久化活动定义、生产页面包、部署、参与者状态、命令记录、事件、outbox 和审计。
- [ ] 提供生产页面包上传、校验、安装、域名/路由、健康检查、激活和回滚能力。
- [ ] 提供 manifest、page delivery、session、command、state、stream 的最小 API。
- [ ] 建立租户、环境和服务间鉴权；禁止页面直接接触内部存储。

### Phase 3：创作端真实页面生产

- [ ] 在项目创建和项目详情中落地 `projectKind`，并让 Demo 项目与活动项目显示不同的能力入口。
- [ ] 在现有 Demo 生产之外，提供“生产真实页面”入口，显示来源 Commit、Package、定义版本、环境和校验结果。
- [ ] 仅允许 `projectKind: "activity"` 创建 ProductionPagePackage；Demo 项目继续只能生成 DemoArtifact。
- [ ] 建立生产构建配置、资源 manifest、依赖锁定、安全校验和不可变包格式。
- [ ] 生产包生成失败不得产生可部署版本；Demo 产物不能绕过生产校验直接上线。

### Phase 4：真实页面接入引擎

- [ ] 创作端把 ProductionPagePackage 和 ActivityDefinition 提交到 Headless 引擎。
- [ ] 引擎完成开发环境安装、健康检查和激活，提供可访问的真实页面入口。
- [ ] 真实页面客户端提供统一的 command/state adapter；当前 viewer-site 继续只服务 Demo。
- [ ] 增加刷新恢复、重复点击、断线重连、过期会话和权限拒绝场景。
- [ ] 为未来非 Web 客户端保留协议级测试，不把协议绑定到 React 组件。

### Phase 5：生产治理与逐步迁移

- [ ] 增加定时激活、灰度、暂停、回滚、指标、追踪和告警。
- [ ] 接入外部效果时统一走 outbox、重试、去重和人工补偿。
- [ ] 选择少量适合的旧活动，把 AppGraph 中的业务部分迁移为 ActivityDefinition。
- [ ] 评估 Demo 链路和真实生产链路的长期边界，避免把两套产物、状态和部署语义混为一谈。

## 十三、验收标准

MVP 至少应满足：

- 当前 Demo 生产/浏览仍可独立工作，Demo 产物不会被误标为真实生产页面；
- Demo 项目无法看到或调用真实页面生产、活动运行时和部署入口；
- 活动项目的所有页面都经过引擎运行时校验，不存在绕过引擎的生产页面；
- 创作端可以从项目 Commit 生产一个明确标识、可校验、不可变的 ProductionPagePackage；
- Headless 引擎可以接收该生产包，完成安装、健康检查并提供真实页面访问入口；
- 同一活动定义可以被两个不同真实页面或客户端消费；
- 页面刷新、重复提交和网络重试不会重复改变业务状态；
- 未授权或无资格参与者无法通过修改前端参数绕过规则；
- 定义版本和 ProductionPagePackage 总是以同一个 deployment 被激活；
- 页面安装、部署校验或激活失败不会污染当前 active deployment；
- 可以查询命令结果、状态版本、拒绝原因和审计记录；
- 可以暂停活动并回滚到上一个已验证版本；
- sandbox 页面不会获得引擎密钥、宿主会话或未授权源码；
- 运行时异常、超时和外部效果失败有可追踪的诊断信息。

## 十四、主要风险与缓解

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 项目类型混淆 | Demo 项目误出现部署入口，或活动项目混入不受引擎控制的页面 | 用独立 `projectKind` 做能力门禁；创建后不允许直接切换；生产包和部署 API 二次校验 |
| 范围过大 | 一开始就设计通用规则平台，迟迟没有可用活动 | 先选一个活动类型，限制命令、状态和效果集合 |
| 双重权威 | 浏览器、页面 API 和引擎各自维护状态 | 引擎状态为唯一事实，页面仅保留临时展示状态 |
| 版本错配 | 页面已更新但规则未更新，或回滚只回滚一半 | 以不可变 deployment 绑定 definitionVersion + packageId |
| 任意代码执行 | 页面脚本可以调用数据库或内部 API | 仅开放白名单命令和受限绑定，沿用 sandbox 安全边界 |
| 并发与重试 | 双击、断线重试、消息重复导致重复奖励 | 幂等键、版本检查、事件唯一键、outbox 和补偿流程 |
| 服务职责膨胀 | 引擎同时承担页面设计、创作编辑、生产构建、托管和业务规则 | 创作端负责页面生产，引擎负责生产包部署/托管和业务运行时 |
| 迁移成本失控 | 历史 AppGraph/项目无法直接兼容 | AppGraph 只作为迁移输入，设置适配层和明确退出条件 |
| 多租户泄漏 | manifest、状态或日志暴露其他租户信息 | 租户边界、字段级投影、脱敏日志和授权测试前置 |

## 十五、待确认问题

在进入 Phase 0 前需要产品、业务和技术共同确认：

1. 第一类真实活动是什么，状态是全局、每用户、每队伍还是多层级混合？
2. 真实页面的生产形态是什么：静态页面包、服务端渲染应用，还是受限运行时应用？
3. 生产页面包由引擎托管，还是由引擎控制外部 CDN/容器/边缘运行环境？
4. 参与者身份来自 Workbench 账号、业务方账号、匿名访客，还是可插拔身份提供方？
5. 活动是否需要支付、库存、优惠券、奖品、消息等外部效果？失败时谁负责补偿？
6. 页面与引擎之间需要实时推送到什么程度，SSE 是否足够，何时需要 WebSocket？
7. 页面源码、运行时票据、用户状态和审计数据的保留期限与隐私要求是什么？
8. 灰度、定时激活、区域/租户分流是否属于首期范围？
9. `projectKind` 与现有 `projectType: "standard" | "template"` 的数据迁移、模板继承和权限规则如何组合？
10. 当前 Demo 链路与真实生产链路如何命名、授权、计费和运维隔离？

## 十六、建议结论

建议把 Headless 活动引擎列为独立的真实生产平台，而不是现有 Demo 发布链路的升级版。第一原则应是“Demo 与生产明确隔离 + 服务端权威活动状态 + 不可变生产页面包 + 引擎负责真实部署上线 + 原子部署版本对”。近期不应直接改造现有 `publish` 语义，也不应把当前浏览器 AppGraph 运行时当作后端引擎。

最小可行路径是：先定义一个窄活动模型和真实页面包格式，完成独立引擎的页面部署与持久化命令运行时；然后在创作端增加“生产真实页面”能力，把生产包交给引擎部署到开发环境；最后接入真实页面客户端和外部客户端。当前创作端的 Demo 生产、当前使用端的 Demo 浏览和现有 sandbox 能力继续作为独立链路保留。
