# 项目管理架构评估与演进建议

> 更新日期：2026-08-17  
> 文档性质：当前架构评估、目标架构建议  
> 相关基线：[项目工作区](../../项目文档/创作端/03-项目管理/技术/03_项目工作区_v2.md)、[实时保存与协同编辑](../../项目文档/创作端/03-项目管理/技术/11_实时保存与协同编辑.md)、[版本管理](../../项目文档/创作端/03-项目管理/技术/04_版本管理.md)

## 一、结论

当前架构的业务分层是合理的，但实现尚未完全收敛。它已经具备较强的 live Workspace 单写者、协同恢复、资源校验和诊断能力；全局层面仍是“局部强一致、跨边界最终一致、多个版本轴并存”。

最值得投入的方向不是继续增加 Workspace 层，而是建立统一的 Commit/Revision 核心，把 Yjs 编辑态、项目基准工作区、资源历史、发布产物都降级为围绕 Commit 的不同投影。

## 二、当前实现评估

### 2.1 已验证的合理设计

- Session 只保存用户、项目、对话和 `workspaceId`，文件由 Workspace 承载，避免切换对话时切换代码副本。
- `scope=live` 的项目工作区服务多人共享编辑，branch Workspace 服务 CLI、实验性修改和隔离事务，语义边界清晰。
- Workspace Authority 已具备按 Workspace 串行、持久化 lease、prepared mutation、backup/recovery、durable receipt、revision/rootHash 和外部漂移检测。
- 关键动作先 flush，再校验 canonical proof，再生成版本或发布产物，避免直接消费落后的协同草稿。
- 发布目录采用临时目录生成后整体切换，能够避免发布过程中暴露半成品。
- 诊断事件覆盖 mutation、canonical materialization、projection gap 和发布/自动保存阶段，具备较好的可观测性。

### 2.2 主要结构性问题

#### 多个权威来源并存

当前同时存在 Yjs room、live Workspace、Authority state/receipt、canonical Workspace、Project `versions`、content graph commit/resource version 和 published artifact。文档要求这些版本轴不能混用，但发布、恢复、导出和模板流程仍需在多个轴之间转换证明。

#### Authority 没有覆盖项目级事务

Authority 能保证 live Workspace 资源及其事务状态的一致性，但不覆盖 `project.json`、canonical 目录、快照、内容图、发布目录和发布索引。因此会出现 live mutation 已提交，而 canonical、项目元数据或发布索引尚未推进的中间状态。

#### 文件系统同时承担数据库和物化缓存职责

项目元数据存在 author-site 与 project-core 两套写入入口，且均有直接 JSON 写入路径。目录替换、版本记录、项目元数据和索引更新通常是多个独立阶段，进程中断时可能留下孤儿快照、悬空 Workspace 或 metadata/artifact 不一致。

#### live 与 branch 仍是两套事务模型

live 走 Yjs/Authority/revision，branch 走复制目录/project version/直接替换 canonical。两套模型的冲突判断、恢复路径、发布入口和失败语义不同，增加了维护和测试矩阵。

#### canonical Workspace 职责过重

canonical 同时承担发布输入、导出输入、CLI 输入、快照来源、模板来源和内容图物化结果。它既像业务事实，又像缓存，又承担旧 API 兼容层，导致关键动作必须等待大量目录复制。

#### 文档与实现存在演进落差

本架构文档仍保留旧目录示例和旧版总览；实时协同、Authority-first/Yjs-first、内容图和后台物化迁移状态已在后续技术文档中变化。后续维护应以模块最新技术文档和代码为准，并持续收敛总览文档。

## 四、推荐目标架构：Commit Graph + Projections

### 4.1 唯一业务提交核心

每次可靠的 flush、命名版本、恢复或发布动作生成一个不可变 Commit。Commit 至少包含项目、父提交、资源 manifest、操作者、动作类型和创建时间。

项目版本、资源版本、发布快照都不再是独立的事实来源，而是 Commit 的标签或引用；Workspace revision 只是投影游标；canonical proof 只记录某个 Commit 是否已经物化。

这里的 Commit 不应按每次键盘输入生成，而应按 durable flush 或关键业务动作生成。

### 4.2 Yjs 只负责编辑态

Yjs room 负责多人编辑、presence、增量同步和草稿恢复。Yjs flush 后统一进入 Commit Gateway；HTTP、AI、CLI 和协同写入都不能绕过该入口直接修改项目事实。

### 4.3 Workspace 变成可重建投影

建议明确区分：

```text
Draft Projection      = Yjs room / 草稿状态
Committed Projection  = 从 Commit 物化的可运行文件树
Published Projection  = 从 Commit 生成的发布目录
```

live Workspace 不再是第二个业务权威；canonical Workspace 是 committed projection；branch Workspace 是某个 Commit 或分支引用的隔离投影。删除或重建投影不应影响历史事实。

### 4.4 元数据与提交记录进入事务存储

Project、Session、Workspace ref、Commit、Resource version、Publish ref、materialization 状态、outbox 和审计记录应进入 SQLite 或 Postgres。源码、图片和二进制仍可保留在文件系统或对象存储，但应使用内容寻址 blob 与 manifest，避免整目录复制快照。

### 4.5 发布改为不可变 Commit 引用

发布状态应表达为 `Project.publishRef -> commitId`。发布产物也以 commitId 标识并可缓存复用。发布切换只需要一次事务性 ref 更新，项目列表索引和 CDN/静态目录由投影器异步生成。

### 4.6 使用 Outbox 驱动物化

Commit 成功后写入 outbox，由不同投影器消费：canonical、预览、发布产物、知识索引、诊断和导出包。关键动作等待所需 projection ack，而不是同步复制整个项目目录。

## 五、最高 ROI 的实施顺序

1. 统一 Yjs、HTTP、AI、CLI 和 project-core 的提交入口。
2. 引入 `commitId` 作为新的业务版本语义，逐步停止业务代码直接比较多套 revision/baseVersion。
3. 明确 canonical 是可重建 projection，补齐后台 materializer，关键动作等待 projection ack。
4. 让 project-core 成为领域服务，author-site 只保留 API/UI 适配，删除重复的 Session、Version 和 Publish 写入逻辑。
5. 将 Project、Session、Commit、Publish ref 和 outbox 放入 SQLite；内容文件暂时保留在现有数据目录。
6. 最后再推进内容寻址 blob、快照去复制和多实例 fencing token。

## 六、边界判断

不建议为了“架构优雅”直接删除当前 live Workspace、Authority 或 Yjs。它们解决的是不同问题：Yjs 解决编辑态协同，Authority 解决受控提交，Workspace 解决运行时投影。真正需要消除的是它们各自维护一套项目事实和版本语义。

目标应是：

```text
Commit 是事实
Yjs 是草稿投影
Workspace 是运行投影
Snapshot 是历史引用
Publish 是 Commit 引用
```
