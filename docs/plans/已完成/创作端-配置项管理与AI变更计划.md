# 创作端 - 配置项管理与 AI 变更计划

> 状态：实施中（单项编辑器与三处入口已收敛；运行时 planner / 统一提交仍待完成）
> 创建日期：2026-08-17  
> 范围：创作端编辑页配置面板、Schema 定义、预览绑定诊断与 AI 修改交接

## 背景

当前编辑页已经可以填写配置值、保存默认值，并能通过可视化属性面板把局部文本、图片或颜色设为配置项。但配置面板本身缺少一个集中、非 JSON 的配置定义管理入口：用户不能在同一处手动新增、编辑、删除配置项或维护分组和图片限制。

配置定义不是孤立数据。字段 key 被 React props、原型页 `data-bind-*` / `{{fieldKey}}`、页面配置要求软引用和设计规范引用消费。修改定义可能需要修改页面代码；该工作应交给创作端 AI，但必须由用户显式发起，并提供可审阅、结构化的上下文。

## 目标

1. 在配置项面板提供轻量、明确的 `+` 新增入口，并让每个已有配置项名称成为单项编辑入口。
2. 通过一个通用的单项配置编辑器，维护页面级或项目级字段的定义、默认值与图片限制；分组只作为字段属性。
3. 让安全的定义变更直接保存到 Schema；让会影响页面代码消费的变更生成影响清单，用户可一键发送给 AI 处理。
4. 保持 JSON Schema 为唯一持久协议，避免引入第二套配置定义或兼容层。
5. 复用既有协同草稿、运行值持久化、预览刷新和 Schema 冲突校验链路。

## 非目标

- 不把配置面板变成页面结构、布局层级或复杂业务动作的编辑器。
- 不在未经用户点击确认的情况下改写 React / HTML / CSS 源码；“保存并应用”是用户明确确认后的受控操作。
- 第一阶段不开放字段 key 的直接重命名；它是跨资源迁移，不是普通元数据编辑。
- 不改变使用端只读配置面板，也不在使用端展示管理入口。

## 二次调研结论与最终方案：统一编辑，按执行能力落盘

> 调研日期：2026-08-17
> 分支：`main` · 基线提交：`fb837414`

### 调研问题

可视化属性面板的“设为配置项”在 HTML、React 与手绘页面分别如何提交？哪些场景能够由系统可靠地直接应用，哪些必须由 AI 处理？如何让它与配置面板的单项编辑统一，而不抹平不同页面运行时的保存语义？

### 现状事实

当前存在两条没有收敛的配置化路径：

| 页面类型 | 属性面板的“设为配置项” | 旧“选元素后添加配置项” | 结论 |
| --- | --- | --- | --- |
| HTML/CSS 原型 | 仅页面级文本、图片、三类颜色可生成直接写回 patch，其余转 AI | 同样优先直接写回 | 可直接应用范围最广。 |
| 高保真 React | 当前一律暂存为 AI 草稿 | 文本、静态图片、可定位颜色会先确定性改写，失败才转 AI | 并非只能 AI；现有两条路径行为不一致。 |
| 手绘场景 | 当前错误地被“非 HTML”分支送入依赖 `index.tsx` 的 React 接口或 AI 提示 | 没有场景配置绑定写回器 | 必须在入口阻断；不应伪装为支持。 |

代码证据：

- 属性面板点击名称仅创建内存 `VisualConfigMark`，再打开“配置项设置”，并没有即时写入 Schema 或页面文件：`VisualPropertyPanel.tsx:824-861`、`useVisualEditState.ts:748-795`。
- 其底部动作在非原型页无条件显示“发送给 AI”：`useVisualEditState.ts:237-267`；这是 React 可直接应用能力没有被复用的根因。
- 原型页纯函数会生成 `data-bind-text`、`data-bind-src` 与 `data-bind-style-*` 对应的 HTML/Schema patch：`prototype-visual-editor.ts:259-314`；宿主再分别异步写草稿与协同 Schema。页面级 text/image/color 才满足条件：`useVisualEditState.ts:230-235`、`964-998`。
- React 已有确定性改写接口 `/api/visual-configure`：`useVisualEditState.ts:1219-1301`、`app/api/visual-configure/route.ts:11-80`。它只生成并校验源码/Schema/config patch；当前客户端只更新运行值本地状态，尚未把该运行值纳入同一次持久化提交。
- React 的直接改写是**保守匹配**：文本必须唯一、图片 `src` 必须唯一、颜色必须能定位 JSX 开标签且非复杂 style 表达式：`visual-configurator.ts:124-153`、`286-308`。任何无法证明安全的情况都应回退，而不是强行改源码。
- 手绘页存储模型是 `sketch.scene.json`，并非 `index.tsx`；当前没有“场景节点属性 → 配置绑定”的执行器：`fs-utils.ts:1779`、`SketchEditorEngineHost.tsx:69`。

### 最终交互决策

采用**一个编辑器、两个协作计划、多个运行时执行器**。用户始终只面对同一张“配置项编辑”表单：所有来源先生成字段定义影响计划；只有“从属性创建/绑定”才额外生成运行时执行计划。这样“编辑现有字段”不会凭字段名猜测要绑定哪个页面元素。

```text
配置面板字段名 / 可视化属性“设为配置项”
                   │
                   ▼
          配置项编辑器（同一套表单）
      名称 · 类型 · 默认值 · 分组 · 图片规则
                   │
                   ▼
 定义影响计划 +（仅 visual-bind）应用计划
     ┌─────────────┼──────────────┐
     ▼             ▼              ▼
  可直接应用     需要 AI        暂不支持
  保存并应用   交给 AI 应用    告知原因 + 发送需求
     │             │              │
 HTML / React   结构化任务      不误导为已配置
 专用执行器     + 用户确认      （手绘当前归此类）
```

这不是“按页面类型固定一个按钮”：HTML 和 React 都可能直接应用，差异只在可证明安全的条件；AI 是明确的回退分支，而不是一次编辑后的默认第二步。

### 执行计划与用户可见状态

`ConfigDefinitionImpactPlan` 与 `ConfigurationApplyPlan` 都由宿主生成，不能由 UI 猜测。前者覆盖 Schema、默认值和引用影响；后者仅在带有完整 `VisualNodeInfo` 的 visual-bind 场景返回 `mode`、可读原因、影响摘要、直接 patch（若有）和 AI 任务上下文（若需）。打开弹窗后和用户确认保存前都应基于最新协同版本重新校验。

| 计划 | 用户看到的主操作 | 适用场景 | 保存语义 |
| --- | --- | --- | --- |
| `direct / schema_only` | `保存字段` | 默认值、标题、分组、图片限制等安全定义变更 | 只更新 Schema default/元数据；绝不默默覆盖当前预览或持久化运行值。项目级字段需显示受影响页面数，但不声称页面源码已接入。 |
| `direct / bind_and_apply` | `保存并应用` | visual-bind 中节点/源码可确定定位的 HTML、React 配置化 | 生成完整页面源文件、Schema 与初始运行值 patch，交宿主以版本前置条件提交；当前实现尚非跨文件原子持久化，实施时必须补齐统一提交与保存中/失败状态。 |
| `ai_required` | `交给 AI 应用` | 项目级绑定、复杂 React 表达式、重复文字/资源、不能定位的节点、无法迁移的类型变化或删除 | 用户显式确认后创建结构化 AI 任务；高风险变更先保持 active Schema/运行值不变，待 AI 产出完整 patch 后统一提交。若要仅保存定义，必须是明确的次级危险操作。 |
| `unsupported` | `请求实现支持`（次级） | 当前未实现的手绘场景配置绑定，或页面缺少可编辑工作区 | 不写 Schema、不创建绑定或“待接入”状态；任务明确标为能力缺失。 |

直接应用若在最终校验中失败（例如协同版本变动、字段冲突、源码不再唯一），**目标行为**是保留当前编辑草稿，将计划降级为 `ai_required` 并展示原因；不得自动发送 AI。当前视觉新增路径会自动触发 AI，这正是本次改造需要移除的行为。

### 各运行时的直接应用边界

| 运行时 | 可直接应用 | 必须 AI / 不支持 |
| --- | --- | --- |
| HTML/CSS 原型 | 页面级文本、图片 `src`、文字/背景/边框颜色；通过当前 `nodeId` / `domPath` 成功定位节点（必要时同一 patch 补 `data-ow-id`）；Schema 与 key 合法且无冲突。 | 项目级绑定、宽高/间距/透明度等尚无绑定协议的属性、节点定位失败、冲突。 |
| 高保真 React | 文本源码唯一、静态 `img src` 唯一、能安全定位的颜色 JSX；且仅限现有正则可识别的 Props/默认导出/解构形态。 | 重复/动态文本、动态资源、复杂样式表达式、无法补 Props、项目级消费接入、Schema 冲突。 |
| 手绘场景 | 首期不开放“从可视化属性设为配置项”的直接应用。 | 在实现 `scene node/property → schema binding` 专用 mutation 前，入口直接显示“暂不支持”，可请求实现支持，但不创建字段。 |

“普通属性直接修改”和“设为配置项”必须区别对待：HTML 原型页的普通文本、属性和 style 可在属性面板即时写回；配置化还需要额外建立绑定和 Schema，因此只开放上表的明确字段类型。不能因为某个属性能改，就宣称它能安全成为配置项。

### 编辑器结构

`ConfigItemEditorDialog` 为唯一的 UI 壳层，使用同一套字段顺序、默认值控件、图片限制、删除确认、键盘焦点和底部按钮布局。它接收 `source`，但不自行保存：

- `source: "panel-edit"`：配置面板点击现有字段名称。只处理 Schema 元数据与默认值；任意类型变化均先生成运行值迁移/校验计划，删除和已绑定变更进入影响计划。
- `source: "panel-create"`：配置面板 `+`。只创建未绑定字段；没有节点上下文时不能“直接接入页面”，如需页面消费只能明确转 AI。
- `source: "visual-bind"`：可视化属性面板“设为配置项”。必须带完整节点上下文和意图 `create_new | bind_existing`；已有绑定或同 key 时先提示，禁止生成第二个绑定。

默认值区域仍嵌入 `ConfigForm`：文本、颜色、单图、多图各用日常配置表单同一控件。名称、类型、范围、分组和图片约束属于 Schema 元数据，保留在编辑器主表单；不把 `ConfigForm` 错当作定义编辑器。

按钮和提示遵循渐进披露：

1. 打开时先展示“仅保存字段”“可直接应用”或“需 AI 接入”的一行状态及原因。
2. `direct / schema_only` 使用“保存字段”；`direct / bind_and_apply` 才使用“保存并应用”，并明确页面、Schema 与初始值将被变更。
3. `ai_required` 主按钮为“交给 AI 应用”，旁边是“取消”；影响详情默认折叠，展开后看页面/字段/引用。
4. `unsupported` 禁止“保存为已生效”，只提供原因和“请求实现支持”。

### 技术边界：不要把三个状态机硬合并

新增两个由宿主调用的纯领域接口：`ConfigDefinitionImpactPlanner` 处理所有字段定义变更，`ConfigurationApplyPlanner` 仅为 visual-bind 按 `runtimeType` 分派 executor。Dialog 只展示计划快照并回传用户确认，不持有或刷新计划：

| 层级 | 职责 |
| --- | --- |
| `ConfigItemEditorDialog`（demo-ui） | 单字段草稿、表单、默认值控件、计划快照与用户确认；无文件 IO，也不自行重新判定计划。 |
| 两类 Planner（author-site） | 前者读取 Schema/引用/运行值生成影响与迁移计划；后者读取 runtime、完整节点、scope、draft、Schema、源码/HTML，生成 `direct / ai_required / unsupported`。 |
| `PrototypeConfigExecutor` | 复用 `applyPrototypeVisualConfiguration` 生成 HTML、Schema、初始运行值 patch；由宿主统一提交。 |
| `ReactConfigExecutor` | 复用并逐步替换 `applyVisualConfiguration`；初期沿用保守匹配，后续才评估 AST/源映射，避免扩张直接改写范围。 |
| `SketchConfigExecutor` | 暂不实现，不由 React executor 兜底。未来单独写 `scene.json` binding mutation。 |
| 编辑页宿主 | 执行协同写入、运行值持久化、预览刷新、截图标脏、影响分析与 AI 任务发送。 |

每个 `direct` executor 必须先 dry-run 生成完整 patch，做 key/Schema 冲突与目标定位校验，再用 revision/precondition 提交；禁止先写 Schema 再发现源码不可改。提交反馈区分“已应用，保存中 / 已保存 / 保存失败可重试”，不承诺现有异步多资源写入已具备数据库式原子性。每个 `ai_required` 计划必须**新增**结构化契约，携带 runtime、选中节点、失败原因、Schema diff、目标文件与验收条件；不能把现有字符串 prompt 误称为已有结构化 payload。

### 实施顺序

1. 将现有 HTML/React 的能力判断抽为 planner，并以完整节点、最新 code/schema dry-run 为属性面板返回执行计划；在入口先阻断手绘页。保留现有 executor 的安全边界。
2. 新建 `ConfigItemEditorDialog`，先接入 `visual-bind`；移除“点击属性名先写 AI 草稿”的中间状态。
3. 接入配置面板字段名称编辑和 `+` 新增；把 Schema mutation、影响分析、默认值 `ConfigForm` 复用到该编辑器。
4. 新增带 revision/precondition 的统一 workspace 提交（页面源文件、Schema、初始运行值）；再将 React 属性面板接入现有确定性 executor。失败后保留草稿并由用户选择 AI，不自动发送。
5. 将手绘页入口明确置为 `unsupported`，再另立任务实现其场景绑定 executor。
6. 删除旧集中管理弹窗和重复的可视化配置弹窗状态，补齐 HTML / React / Sketch 三类矩阵测试。

## 交互优化方案：由“集中管理”改为“就地单项编辑”

### 决策

停止把配置定义维护作为一个包含字段树、分组、批量暂存和默认值的独立工作台。配置面板中的每个已存在配置项，直接点击其**名称**即可编辑该字段；原“管理配置项”入口改为 `+`，只承担新增字段。

可视化编辑中“设为配置项 / 编辑配置项”与配置面板中的单项编辑，使用同一套“配置项编辑”对话框外观、字段顺序、文案与确认方式；两者只在提交适配器上不同：

| 来源 | 用户意图 | 保存结果 |
| --- | --- | --- |
| 配置面板中点击已有配置项名称 | 修改已存在字段的定义 | 通过 Schema definition command 更新字段；必要时给出影响与 AI 同步确认。 |
| 配置面板 `+` | 新增一个尚未被页面消费的字段 | 新建字段并标记“待接入”；可选交给 AI 接入页面。 |
| 可视化属性面板点击“设为配置项” | 从选中的页面属性创建字段并建立页面绑定 | 保留现有“属性 → 绑定 → Schema/源码”事务；仅复用编辑对话框的元数据表单和视觉规范。 |

这比“所有改动最后统一保存”的模型更适合字段级任务：用户不必先理解字段集合、分组树和暂存状态，也避免无关字段修改被一个总保存动作一起提交。

### 为什么不直接复用现有可视化弹窗

现有可视化入口有两类状态：

1. 编辑页中的新增弹窗是“从 DOM 属性创建候选字段，并同时写入源码/原型绑定”的事务；它没有已存在 Schema 字段可编辑时所需的输入与取消语义。
2. `VisualPropertyPanel` 的“配置项设置”是待发送 AI 的 `VisualConfigMark` 草稿；它只存在于本次可视化编辑状态，关闭或取消不应写入 Schema。

因此不能把现有完整弹窗直接移植到配置面板。应抽取公共的**单项编辑 UI 壳层和字段表单**，但让“Schema 字段编辑”“未绑定字段新增”“从属性创建并绑定”分别保留各自的状态与提交逻辑。

### 目标交互

```text
配置面板
┌───────────────────────────────────────────────┐
│ 配置项                                      [+] │
│  品牌标题                         ← 点击名称   │
│  主题色                           ← 点击名称   │
│  封面图片                         ← 点击名称   │
│                                               │
│  [恢复默认值]                                  │
└───────────────────────────────────────────────┘

配置项编辑（新增 / 编辑共用）
┌───────────────────────────────────────────────┐
│ 编辑配置项                                     │
│ 此字段：封面图片 · 页面级                       │
│ 名称 / 类型 / 分组 / 必填                       │
│ 默认值（复用与配置面板一致的值控件）             │
│ 图片限制（文件类型、大小、W/H 规则）             │
│ 绑定状态：已绑定 / 待接入                       │
│                          [取消] [保存]          │
└───────────────────────────────────────────────┘
```

- **配置项名称是唯一的编辑触发器**：避免在每行堆叠齿轮、更多菜单和重复按钮；类型、值与绑定状态继续作为信息，不抢占主操作。
- `+` 打开“新增配置项”，默认创建页面级、未绑定字段；若当前正在查看共享配置，可在弹窗顶部切换为项目级。不要让 `+` 隐式创建空分组。
- 对已有字段，保存即提交该字段的单项 mutation；关闭有未保存输入时只确认放弃当前字段，不影响别的字段。
- 默认值仍复用 `ConfigForm` 的值控件：文本输入、颜色选择器、单图/多图上传等和日常配置填写完全一致；它不承担名称、类型、分组或影响分析等 Schema 元数据编辑。
- key 继续由系统从名称生成并校验唯一性，界面不显示也不允许手工修改；编辑既有字段时 key 保持不变。
- 字段描述继续仅由设计规范维护；弹窗提供“在设计规范中编辑说明”的链接/状态，而非第二个描述输入框。
- 图片字段使用文件类型下拉选择；宽度、高度各一条尺寸约束，以 `W/H + =、>、≥、<、≤ + 数值` 表达，并规范化写入 `widthRule` / `heightRule`。

### 字段分组的处置

“分组”保留为字段的一个元数据项，用来组织日常配置表单；取消将它作为一个需要专门管理的集合对象。

- 编辑单个字段时可选已有分组，也可输入新分组名称。
- 某分组内最后一个字段移走或删除后，该分组自然消失；无需“新建分组 / 删除分组”工作流。
- 配置面板按分组显示时，分组标题保持非交互，避免用户误以为分组能独立保存。

### 保存、影响与 AI

单项保存并不弱化安全性。保存按钮按变更风险工作：

| 字段变更 | 主操作 | 补充反馈 |
| --- | --- | --- |
| 名称、分组、必填、默认值、图片限制 | `保存` | 保存后立即刷新当前配置表单。 |
| 新增未绑定字段 | `保存` | 保存成功后显示“待接入”，提供“交给 AI 接入”。 |
| 已绑定字段的类型变更或删除 | `保存并交给 AI` | 提交前显示受影响页面、绑定和设计规范引用；定义保存后明确“页面同步中”。 |

影响分析、`SchemaDefinitionMutation`、运行值清理计划和现有 AI payload 继续由编辑页宿主执行，不能下沉到通用对话框，也不能因交互变简单而绕过协同文本、持久化或截图标脏链路。

### 实现边界与组件建议

新增 `ConfigDefinitionEditorDialog`（放在 `packages/demo-ui`）作为受控 UI 组件，建议接口包含：`mode: "create" | "edit"`、`scope`、`initialDraft`、`bindingSummary`、`onSubmit`、`onDelete` 和 `onOpenChange`。它只负责单字段草稿、校验提示和确认 UI。

| --- | --- |

| `packages/demo-ui/src/PageConfigPanel.tsx` | 将齿轮替换为 `+`；把每个配置项名称向上暴露为 `onEditDefinition(fieldKey, scope)`；挂载编辑器而非集合管理器。 |

### 迁移步骤

1. 抽出单项编辑器，先接入配置面板的“已有字段编辑”和 `+` 新增；保留当前集中管理弹窗作为临时内部回退，不再暴露入口。
2. 为 `ConfigForm` 标题增加可选编辑回调，确认创作端可编辑、使用端/引用页不可编辑。

4. 使可视化“配置项设置”复用新组件的表单与 UI shell；保持其源码/原型绑定提交事务与独立草稿状态。
5. 补齐无障碍和回归测试后，删除旧 `ConfigDefinitionManagerDialog` 与其入口。

### 验收标准

- 创作端用户可从配置面板点击任意字段名称，在一次弹窗内完成该字段编辑并立即看到表单/预览结果。

- 使用端、引用页和只读态没有名称编辑能力或 `+`。
- 键盘可聚焦字段名称、对话框初始焦点落在名称、`Esc`/关闭在脏草稿时确认；所有触发器有可见焦点态和 150–300ms 反馈。

## 已废弃的集中管理方案（实施现状）

> 以下内容记录已实现的集中管理弹窗及其数据边界，便于迁移时核对；不再作为后续交互目标。后续以“交互优化方案：由集中管理改为就地单项编辑”为准。

### 1. 入口与弹窗

- 在“配置项”面板的**右下角**放置一个低干扰的悬浮设置按钮（齿轮图标，`aria-label="管理配置项"`）。
- 仅创作端、可编辑工作区且非引用页显示该按钮；使用端和只读/引用页面不显示。
- 没有任何配置项时，空态仍提供同一个“添加配置项”操作；它打开同一弹窗，不再新增第二套创建流程。
- 弹窗标题为“管理配置项”，全屏窄屏适配；关闭时若存在未保存修改，需确认放弃或继续编辑。

### 2. 统一作用域

弹窗顶部提供两个受控页签：

- **项目级共享配置**：编辑 `project.config.schema.json`；显示受影响页面以及每个字段的绑定状态。
- **本页配置**：编辑当前选中页面的 `config.schema.json`；切换编辑页时弹窗保持打开，但需要提示是否切换目标页面。

两个页签复用同一个字段列表与详情编辑器。项目级页签中的“新增字段”不应默认认为所有页面都能消费它；字段保存后需要显示哪些页面已绑定、哪些尚未绑定。

### 3. 弹窗内部布局

```text
┌ 管理配置项 ──────────────────────────────────────┐
│ [项目级共享配置] [本页配置：当前页面]              │
│                                                     │
│ 分组与字段列表              │ 字段定义             │
│ - 未分组                     │ 名称 / 类型 / 默认值 │
│ - 基础信息                   │ 分组 / 分类 / 必填   │
│   - Banner 图片   [已绑定]   │ 图片限制（按类型显示）│
│ - 视觉规范                   │ 影响与 AI 操作        │
│ [+ 新建分组] [+ 添加配置项]  │                       │
│                                                     │
│ [取消]                         [保存定义]           │
└─────────────────────────────────────────────────────┘
```

- 左列按 `ui:options.group` 展示“分组 → 具体字段”。未显式分组字段置于“未分组”；自动推断的表单展示分组不被回写成显式分组。
- 左右两栏各自滚动；新增配置项操作固定在左栏顶部，避免长字段列表遮挡创建入口。
- 支持新建、重命名、删除空分组；删除非空分组必须选择“移入未分组”或逐项重新分组，禁止隐式删除字段。
- 字段列表显示名称、类型、绑定状态、影响警告和关联设计规范标识；它不承载填写当前配置值。
- 右列编辑字段定义。新增字段的最小必填项是名称、类型与默认值；key 自动从名称生成，不向创作者暴露编辑入口。

### 4. 可编辑字段定义

第一阶段支持与现有表单渲染器一一对应的有限字段类型：短文本、长文本、富文本、数字/整数、布尔、枚举、颜色、单图、多图。复杂对象、嵌套动态表达式和页面结构继续走源码/AI 能力。

所有类型支持：

- 显示名称（Schema `title`）
- 默认值（Schema `default`，通过复用日常配置项表单维护）
- 字段业务描述由设计规范维护，不在 Schema 定义管理器中编辑
- 必填（根 `required`）
- 分组（`ui:options.group`）
- 分类（`ui:options.category`）
- 控件语义（`format` / `ui:widget`，仅暴露当前支持项）

图片字段额外支持：

- 文件类型 `accept`
- 文件大小上限 `maxSize`
- 宽度规则、长度规则（px）；每个维度只保留一个比较符和数值

新写入统一使用 `widthRule`、`heightRule` 和 `maxSize`。每条尺寸规则包含一个比较符与一个数值，避免同一维度出现相互叠加的限制。

### 5. 默认值操作边界

仅将“保存为默认值”从配置项面板迁移到弹窗；“恢复默认值”继续保留在主配置面板：

- 每个字段详情显示“当前运行值”和“Schema 默认值”；提供“用当前值覆盖默认值”。
- 弹窗页脚提供当前作用域的“将当前值保存为默认值”。项目级保存只写项目运行值对应字段的 Schema 默认值；页面级保存只写当前页面字段的默认值。
- 主配置面板继续保留现有“恢复”按钮，因为它是高频的预览试错撤销动作；恢复当前作用域后立即以 Schema 默认值刷新运行值，并保留现有确认语义。
- 填写配置值的日常面板只保留值输入、预览联动、资源上传和“恢复默认值”，不再提供“保存为默认值”。

## 定义变更与页面代码消费

### 1. 变更分级

| 变更 | 保存 Schema 后的直接结果 | 是否需要 AI |
| --- | --- | --- |
| 改显示名称、描述、分组、分类、必填、默认值、图片限制 | 表单展示或上传验证更新 | 否 |
| 新增字段 | 新字段出现；未被页面消费时标记“未绑定” | 视用户是否要让页面展示/消费它 |
| 删除字段 | Schema 和对应运行值删除；原页面代码可能仍读取 prop | 是，若存在代码/原型绑定 |
| 改字段类型 | 表单协议变化，页面消费可能不兼容 | 是，若存在代码/原型绑定 |
| 字段 key 重命名 | 当前阶段禁止直接提交 | 后续迁移向导必需 |

### 2. 影响分析

“保存定义”前运行纯函数分析，并在确认区展示：

- Schema diff：新增、更新、删除的字段及协议变化。
- 值迁移计划：需要新增默认值、删除的页面运行值/项目运行值。
- 页面绑定：React 代码 props、原型 HTML 的 `data-bind-*` / `{{fieldKey}}`，以及页面配置要求和设计规范引用。
- 风险等级：无绑定可直接保存；有绑定但仅元数据变更可直接保存；需改源码时标为“需要 AI 处理”。

项目级字段需按页面列出绑定情况，不能因新增共享字段而假定全部页面消费该 key。

### 3. AI 交接操作

当分析发现需要代码处理时，不使用“先保存、再找发送按钮”的两步高风险流程。主操作根据风险自动变为：

- 无需代码同步：`保存定义`。
- 新增但尚未绑定页面：`保存定义`，并提供次级操作“保存并交给 AI 接入页面”。
- 删除已绑定字段、变更已绑定字段类型，或用户明确要求新增字段立即生效：`保存并发送给 AI`。

以上操作均由用户点击触发，绝不自动发送。需要 AI 的操作先写入 Schema 并立即创建同一编辑会话中的 AI 任务；UI 以“定义已保存，页面同步中”显示中间状态。

发送内容必须是结构化任务，而非让模型自行猜测：

```text
目标：让页面消费已变更的配置定义。
作用域：项目级 / 页面级；项目、页面和运行时类型。
Schema 变更：字段 key、旧/新类型、默认值、图片规则、删除项。
已发现绑定：源码位置或原型绑定模式；关联的配置要求/设计规范引用。
需要完成：修改页面源码或原型绑定、保持现有视觉效果、更新引用；不得擅自扩大配置范围。
验收：Schema 校验、预览配置联动、受影响页面截图或相应测试。
```

- 发送后复用当前编辑页 AI 对话和现有 workspace mutation authority；不引入第二个 Agent 或绕过审批/保存链路。
- UI 记录该次定义变更的摘要、发送状态和 AI `run_summary` / mutation receipt。AI 失败、取消或未验证时，Schema 定义保持已保存状态，但突出显示“页面消费尚未完成”。
- AI 成功后的源码/原型写回仍走现有工作区 mutation、协同与预览更新机制。

### 4. 用户可理解的状态与失败恢复

配置项管理不能把“定义存在”误导成“页面已经生效”。字段和变更均采用可解释状态：

| 状态 | 用户看到的含义 | 可执行操作 |
| --- | --- | --- |
| 已绑定 | 页面已发现该字段消费 | 修改值、编辑定义 |
| 未绑定 | Schema 中有字段，但页面尚未消费 | 交给 AI 接入页面、查看建议 |
| 待同步 | 定义已保存，AI 尚在处理代码/原型 | 查看 AI 对话、等待、取消 |
| 同步失败 | 定义已保存，但页面消费未完成 | 重试发送 AI、恢复默认值、从版本记录撤销 |
| 孤立绑定 | 页面仍消费一个已从 Schema 删除的 key | 一键发送 AI 清理页面消费 |

这些状态由 Schema 与当前页面代码/原型绑定的实时比对推导，不另存一套配置状态。这样刷新页面后仍能发现“未绑定”或“孤立绑定”，不会因为 UI 临时状态丢失而掩盖未完成工作。

## 产品经理复核

### 结论

方案方向合理，但初稿存在三处产品风险，已在本版修正：

1. 初稿把“恢复默认值”迁入弹窗，会割裂用户在预览中反复试调、即时复原的高频流程；现已保留在外层主配置面板。
2. 初稿把“保存 Schema”和“发送 AI”完全拆开，删除或改类型后可能让页面短暂读取失效 props；现已将需要代码同步的高风险变更收敛为一个用户点击的“保存并发送给 AI”动作。
3. 初稿的字段定义能力偏工程化；产品界面必须默认以名称、类型、默认值、分组和图片规则表达，`format` / `ui:widget` 只放在“高级设置”，不能要求创作者理解 Schema 术语。

### 用户任务闭环

| 用户目标 | 推荐流程 | 完成信号 |
| --- | --- | --- |
| 新增一个暂时只作数据预留的配置项 | 设置按钮 → 本页/项目级 → 添加配置项 → 保存定义 | 字段出现在配置表单，并标记“未绑定”。 |
| 新增并让页面立即可配置 | 添加配置项 → 勾选“让 AI 接入页面” → 保存并发送给 AI | AI 成功后字段标记“已绑定”，修改值可驱动预览。 |
| 给图片补充尺寸要求 | 选择图片字段 → 图片限制 → 保存定义 | 下次单图/多图上传显示一致的尺寸校验。 |
| 修改字段的显示名称或分组 | 选择字段 → 编辑 → 保存定义 | 配置面板立即更新文案和布局，不触发 AI。 |
| 移除页面不再需要的配置项 | 删除 → 查看影响 → 保存并发送给 AI | Schema、运行值及页面消费均清理；预览无报错。 |
| 试调值后放弃 | 主配置面板点击“恢复” | 当前预览立即回到默认值，不必打开管理弹窗。 |

### 信息架构与文案原则

- 默认打开“本页配置”，因为用户从一个正在编辑的页面进入配置面板时，最常见任务是调整当前页；项目级页签用“影响多个页面”的副标题说明范围。
- 字段编辑页优先级固定为：名称、类型、默认值、分组、图片规则；分类与高级控件设定折叠，防止新手先接触不必要的概念。
- “分组”用于控制面板内的收纳结构；“分类”仅服务筛选，需在字段旁给出简短解释，防止两者被当成同一概念。
- 将“未绑定”作为产品可见状态，而不是错误。它支持先定义数据、后由 AI 或开发者接入的正常工作流。
- 删除、变更类型和未来 key 迁移均展示受影响页面数、绑定数和任务摘要；不展示源码细节作为第一层信息，但提供“查看详情”。

### 范围控制与首期取舍

首期只交付高频且风险可控的能力：字段新增/编辑/删除、分组、图片规则、保存默认值、绑定诊断和 AI 一键交接。以下能力延后：字段 key 重命名、复杂对象编辑、跨页面批量迁移、自动生成配置项、分组排序。

这能避免管理弹窗在首期成为 Schema IDE，同时给出完整的“定义 → 页面消费 → 预览验证”闭环。

## 已废弃的集中管理技术设计

### 1. 领域层：受控 Schema 操作

新增共享纯函数模块（建议 `packages/shared/src/demo/config-schema-definition.ts`），不依赖 React、网络或 Yjs：

```ts
type SchemaDefinitionCommand =
  | { type: "field.add"; field: ConfigDefinitionDraft }
  | { type: "field.update"; key: string; patch: ConfigDefinitionPatch }
  | { type: "field.delete"; key: string }
  | { type: "group.rename"; from: string; to: string }
  | { type: "group.delete"; group: string; disposition: "ungroup" | "move"; targetGroup?: string };

type SchemaDefinitionMutation = {
  schema: string;
  valuePlan: { setDefaults: Record<string, unknown>; removeKeys: string[] };
  diff: SchemaDefinitionDiff;
};
```

职责：解析与规范化 JSON、key/类型/图片限制校验、维护根 `required`、维护 `ui:options`、生成稳定格式化 Schema、计算运行值清理计划。它不扫描页面源码；影响分析留在 author-site，因为只有宿主拥有全部页面、运行时和工作区上下文。

### 2. UI 与宿主边界

- `packages/demo-ui` 新增无业务 IO 的 `ConfigDefinitionManagerDialog`，接受 Schema、作用域、字段绑定诊断、保存回调和只读状态。
- `PageConfigPanel` 只负责右下角入口、弹窗开关和把项目/当前页面的 Schema 传入；不复制 Schema 变换逻辑。
- 编辑页宿主负责将变更写入 `replaceCollabText`、`pageSchemaMap` / `projectConfigSchema`、运行值 map、截图脏标记和既有持久化队列。
- 项目级提交继续使用现有 API/Authority 校验；页面级提交继续使用 Session workspace 文件链路。不得在 UI 组件内 `fetch` 写 Schema。

### 3. 绑定与 AI 计划服务

在 author-site 增加纯影响分析器，复用已有 `extractCodeConfigBindingKeys`、`extractPrototypeConfigBindingKeys` 和页面配置要求/设计规范数据。输出统一的 `ConfigDefinitionImpactReport`，作为：

1. 弹窗保存确认 UI 的数据源；
2. AI 结构化任务上下文；
3. 单元测试的可断言合同。

字段 key 重命名不纳入第一阶段命令集。后续若实施，必须扩展为专用迁移命令：先生成跨源码、原型绑定、配置要求和设计规范引用的补丁预览，再由用户确认与 AI 执行，不能只改 Schema。

## 验证方式

### 单元与组件测试

- Schema 命令：新增、编辑、删除、分组迁移、非法 key、重复 key、页面/项目同名冲突。
- 图片规则：最小/最大值、固定尺寸、负数/倒置范围、`maxSize`、单图和多图 widget 消费一致。
- 值计划：字段删除后默认值、页面运行值和项目运行值均被清理；仅改名称不修改值。
- 单项编辑器：从字段名称打开、`+` 新增、字段级未保存关闭确认、作用域与 key 冲突校验、只读/引用页不显示入口。
- 表单标题：创作端名称可聚焦和打开编辑器；使用端保持文本且不改变原有配置值输入行为。
- 主面板：保留“恢复默认值”，移除“保存为默认值”；恢复后立即同步预览。
- 影响分析：React、HTML 原型、无绑定、资源规范软引用、设计规范引用和项目级多页面结果。
- AI 任务：结构化 payload 含目标页、Schema diff、影响项和验收条件；发送必须由用户点击触发。
- 执行计划：`schema_only` 的默认值变更不覆盖当前运行值；React 的重复/动态匹配 dry-run 返回 `ai_required` 且不创建 Schema；AI 取消/失败后 active Schema 与页面均不变；手绘页返回 `unsupported` 且不创建字段/绑定。

### 集成与人工验收

1. 新增未绑定页面级图片字段，确认表单出现且标注未绑定；发送 AI 后让页面真实消费该字段，修改上传图片应刷新预览。
2. 修改一个已绑定图片字段的尺寸限制，确认单图和多图上传均显示同样的警告语义。
3. 删除已绑定字段，确认 Schema/运行值清理、影响提示和 AI 交接；AI 完成后预览与页面代码不再读取旧字段。
4. 新增项目级字段，确认只有实际消费它的页面显示共享字段与受影响计数。
5. 使用端与引用页确认没有管理入口，也无法改变 Schema。

## 风险与待确认

| 风险 | 处理策略 |
| --- | --- |
| Schema 已保存但 AI 未完成源码改写 | 对需要代码同步的高风险变更采用“保存并发送给 AI”；仍失败时显示可重试的“定义已保存 / 页面消费待处理”状态。 |
| 多人同时编辑同一 Schema | 所有弹窗提交基于最新协同文本重新执行命令；发现目标字段已被删除或类型已变时中止并提示刷新。 |
| 删除字段遗留运行值或引用 | 由值迁移计划清理运行值；影响报告列出引用；AI 任务处理源码和软引用。 |
| 图片限制出现两套协议 | 管理器和可视化入口同时统一为 min/max；不继续扩展比较运算符写法。 |
| AI 任务范围扩大 | 任务 payload 明确页面、字段和验收条件；要求 AI 不扩大配置范围，结果通过 mutation receipt 与预览验证呈现。 |

- 2026-08-17（交互复核）：集中式“管理配置项”要求用户先进入字段集合、选择字段、暂存、再统一保存，步骤与可视化属性配置不一致。确认改为“配置面板点击字段名称即编辑，`+` 仅新增”的单项工作流；公共弹窗只复用 UI 和字段表单，Schema 编辑与可视化 DOM 绑定继续使用各自的提交状态机。
- 2026-08-17（二次代码调研）：确认 HTML 与 React 都已有一部分确定性直接配置化能力，但属性面板的 `VisualConfigMark` 流程仅在原型页使用它，React 一律转 AI；手绘页没有专用 executor。实施基线修订为 `ConfigurationApplyPlanner` + runtime executor：可直接应用时不经过 AI，失败保留草稿并由用户明确选择 AI，未支持的手绘场景不伪装为 React 支持。
- 2026-08-17（方案复查）：两名独立审查确认方向成立，但修正了关键承诺：当前 direct 路径只是生成 patch 后经协同与异步草稿保存，运行值尚未同次持久化；因此方案改为“定义影响计划 + 仅 visual-bind 的应用计划”、预检后带 revision 的统一提交，并将高风险类型/删除变更调整为 AI 成功后再提交。手绘页由“交给 AI 应用”改为不创建字段的“请求实现支持”。
- 2026-08-17（首轮实施）：新增受控 `ConfigItemEditorDialog`；配置面板字段标题改为可访问的单项编辑入口，齿轮改为 `+` 新增，默认值继续嵌入 `ConfigForm`。可视化属性面板和旧“选元素添加配置项”入口均切换到同一表单壳层，接受文件类型、图片尺寸约束和原型页 Schema/AI 上下文已贯通。当前仍保留旧集中管理组件作为内部迁移遗留；visual-bind 尚未接入新的 planner，因此失败草稿保留、统一提交与手绘阻断留作下一阶段。
