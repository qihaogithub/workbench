# 创作端编辑页结构优化方案

> 目标：让 Agent 修改单一功能时只需读 1-2 个文件，而非在当前 8097 行的 page.tsx 中大海捞针。

## 问题诊断

`page.tsx` 对 Agent 不友好的根因不是"太大"，而是**信息没有按功能领域隔离**。当前结构：

```
page.tsx (8097 行)
├── 区域 A: imports + dynamic imports + 模块级工具函数/类型/常量 (1-723)
├── 区域 B: 组件体 — ~83 个 useState + ~38 个 useCallback + ~17 个 useEffect + ~27 个 useMemo (724-6055)
├── 区域 C: 加载态 JSX (6056-6067)
├── 区域 D: 主渲染 JSX (6185-8094)
```

已提取的 hook（位于 `edit/hooks/`）：
- `useVisualEditState.ts`（1639 行）— 可视化编辑状态
- `useVersionControl.ts`（687 行）— 版本管理与发布
- `useWorkspaceAuthorityState.ts`（290 行）— 权威同步状态机
- `useCommandHistory.ts`（154 行）— 撤销/重做

此外，预览/画布/截图的核心逻辑已委托给 `components/demo/` 下的共享 hook：
- `useCanvasWorkspace`（画布状态、协同、焦点管理）
- `useScreenshotGeneration`（截图批量生成、缓存、健康检查）

一个 Agent 想修改"AI 对话的自动修复逻辑"，需要：
1. 在 ~5300 行状态区里找到 `handlePreviewError` 所在位置（行 2132）
2. 在状态区里找到 `triggerAutoSend` 的状态定义（行 1709）
3. 在状态区里找到 `aiMessages` 的状态定义（行 1679）
4. 在 ~1900 行 JSX 里找到 `AIChat` 的 props 传递（行 6410-6650，含大量内联回调）
5. 理解这些状态之间的隐式依赖关系

**核心问题：相关代码跨越了数千行，Agent 无法通过读一个文件理解一个功能。**

## 目标

| 场景 | 现在 | 优化后 |
|------|------|--------|
| 修改 AI 对话逻辑 | 扫描 5300 行状态区 + 1900 行 JSX | 读 `hooks/useAiChatBridge.ts` + `panels/AIChatTab.tsx` |
| 修改页面预览/截图 | 同上 | 读 `hooks/usePreviewOrchestration.ts`（编排层）+ 已有共享 hook |
| 理解页面保存/刷新机制 | 在状态区搜索各种 flush/sync 逻辑 | 读 `hooks/useWorkspaceLifecycle.ts` |
| 修改版本历史 Tab | 在 JSX 中 ~167 行内联 | 读 `panels/HistoryPanel.tsx` |
| 修改某个 Dialog | 在 JSX 末尾嵌套查找 | 读 `dialogs/XxxDialog.tsx` |

## 方案

### 阶段一：低风险提取（零状态依赖）

#### 步骤 1：模块级工具函数 → `utils.ts`

将 `page.tsx` 组件函数外部的纯工具函数/类型/常量（约 620-723 行区域）提取到 `edit/utils.ts`。包括：
- `WorkspaceSyncStepError` 类 + `WORKSPACE_SYNC_PHASE_LABELS` + `getWorkspaceSyncErrorDetails`
- `serializeCanvasLayout` / `parseCanvasLayoutState`
- `arePositionableSizesEqual`
- `getCanvasContentHistorySignature`
- 其他散落在 imports 和组件之间的纯函数

纯函数无副作用，零风险。注意：dynamic import 声明（220-280 行区域）保留在 page.tsx 中，因为它们与组件渲染直接绑定。

#### 步骤 2：内联 Dialog → `dialogs/` 目录

| Dialog | 当前行号 | 新建文件 | 复杂度 |
|--------|---------|---------|--------|
| VisualConfigDialog | 7690-7830 | `dialogs/VisualConfigDialog.tsx` | 高（~140 行，含表单逻辑） |
| PageVersionPreviewDialog | 7927-7986 | `dialogs/PageVersionPreviewDialog.tsx` | 中（~60 行） |
| SaveVersionDialog | 7988-8036 | `dialogs/SaveVersionDialog.tsx` | 低（~48 行） |
| ExitConfirmDialog | 8038-8053 | `dialogs/ExitConfirmDialog.tsx` | 低（~15 行） |
| UnpublishDialog | 8061-8092 | `dialogs/UnpublishDialog.tsx` | 低（~31 行） |

每个 Dialog 提取为接收 `open` + `onOpenChange` + 业务 props 的独立组件。

#### 步骤 3：内联版本历史 Tab → `panels/HistoryPanel.tsx`

`page.tsx:6889-7055`（~167 行）提取为独立组件。接收 `historyGroups`、`historyEventTotal`、`publishStatus`、`publishedVersion`、版本操作回调等 props。

### 阶段二：状态按功能域聚合（核心改动）

当前已提取的 hook 覆盖了可视化编辑、版本管理、权威同步和命令历史，但仍有 ~60 个 useState 散落在 `page.tsx` 中。

目标：将剩余状态收敛为 4 个功能域 hook。注意 `useCanvasWorkspace` 和 `useScreenshotGeneration` 已是独立共享 hook，不需要重新提取——新的编排 hook 只负责**组合和桥接**它们的输出。

| `handleAiStreamingChange` | 2693 |

| `flushPendingWorkspaceBeforeAiSend` | 4990-5045 |

**关键设计决策**：`handleAiFilesChange`（~280 行）内部调用了 `applyDemoSnapshot`、`markWorkspaceChanged`、页面树刷新等——这些是**跨域操作**。解决方式：hook 接收 `applyDemoSnapshot` 和 `markWorkspaceChanged` 作为输入参数（由 page.tsx 从其他 hook 传入），保持单向依赖。

### 阶段三：JSX 面板提取（状态聚合后再做，此时 props 已大幅减少）

状态收敛完成后，页面主体剩余的 JSX 面板提取将变得简单——因为 props 不再需要从页面级 83 个 useState 逐一传递，而是各功能域 hook 的返回值直接传给对应面板。

**重要**：当前 JSX 中存在大量内联回调（如 `AIChat` 的 `onNewSession` 回调约 80 行、`onSelectSession` 约 60 行），这些回调应在阶段二提取 hook 时一并移入对应 hook，而非留在 JSX 中。

## 设计约束

1. **hook 返回值使用对象而非元组**。每个 hook 返回具名对象，Agent 可以通过 IDE 自动补全发现可用字段，不需要依赖文档。

2. **hook 之间通过显式参数传递依赖，page.tsx 是唯一编排点**。不引入 Context、Redux 或任何隐式状态共享。跨域依赖（如 `applyDemoSnapshot`、`markWorkspaceChanged`）由 page.tsx 从一个 hook 的返回值取出，传入另一个 hook。依赖方向：`usePageContentState` / `useWorkspaceLifecycle` → `useAiChatBridge` / `usePreviewOrchestration`（后者依赖前者的输出，不反向）。

3. **一个文件一个领域，但不强求行数上限**。如果 hook 超过 600 行但领域内聚（如 `usePageContentState` 含 8 个 collab 调用），保持完整比人为拆分更好。只在领域确实可分离时拆分。

4. **不引入新依赖**。只用 React hooks（`useState`, `useCallback`, `useEffect`, `useMemo`, `useRef`），不新增状态管理库。

5. **不重复提取已有共享 hook**。`useCanvasWorkspace`、`useScreenshotGeneration`、`useVisualEditState`、`useVersionControl` 等已独立存在，新 hook 只做编排和桥接，不复制其内部逻辑。

6. **内联回调随功能域迁移**。JSX 中超过 10 行的内联回调（如 `onNewSession`、`onSelectSession`）在阶段二提取 hook 时一并移入对应 hook 作为具名函数，不在阶段三才处理。

## 风险

1. **阶段二的闭包依赖提取**：将 ~5300 行状态体拆分为 4 个 hook 需要精确识别每个 useCallback/useEffect 的闭包引用。策略：每个 hook 独立开发、独立验证——先确定接口签名 → 移动代码 → 修复类型错误 → `pnpm check:author` → 下一个。不要同时动两个 hook。

2. **跨域依赖管理**：`markWorkspaceChanged` 被 AI、可视化编辑、页面内容修改等多处调用；`applyDemoSnapshot` 被 AI、手动编辑、版本恢复等调用。这些函数必须作为"公共 API"从所属 hook 返回，由 page.tsx 分发。如果后续发现分发过于复杂（>5 个跨域函数），可考虑引入一个轻量 `useEditPageContext` 只读 Context 减少 prop drilling，但初期不引入。

3. **collab hook 的 Yjs Provider 依赖**：8 个 `useCollabDocument` 调用依赖上层 Yjs Provider 组件。提取到 `usePageContentState` 后，Provider 层级不能变。需确认 `useCollabDocument` 内部通过 React Context 获取 Yjs doc，只要 Provider 仍在 page.tsx 的父组件中即可。

4. **测试覆盖**：现有测试覆盖 `useVisualEditState`、`useVersionControl`、`useCommandHistory`、`useWorkspaceAuthorityState`，page.tsx 本身无直接测试。阶段二新增 hook 建议至少补充接口级冒烟测试（renderHook + 基本断言），但不阻塞重构进度。

5. **Git 历史断层**：大范围代码移动会使 `git blame` 失效。每个步骤在同一 commit 中完成（提取 hook + 修改 page.tsx 调用方式），commit message 注明 "refactor: extract useXxx from edit page, no behavior change"。

6. **阶段三的必要性评估**：阶段二完成后，page.tsx 的 JSX 部分可能仍有 ~1200 行。如果此时 Agent 修改 UI 布局仍需扫描大量 JSX，再执行阶段三；如果 JSX 结构已足够清晰（各面板有明确注释边界），阶段三可推迟。
