# 创作端与浏览端 — 评论列表功能方案

> 创建日期：2026-07-26
> 状态：方案设计
> 关联：`docs/plans/进行中/创作端开发项目模式方案/`（开发项目方案中的任务面板设计参考本文档的评论模型）

## 背景

当前系统中存在 `VisualAnnotation`（`packages/demo-ui/src/iframe-types.ts`）用于元素级批注：用户在 iframe 中点击元素 → 弹出气泡输入 → 标注固定到 DOM 元素上。但该机制有几个局限：

1. **只在编辑页可用**，浏览端没有
2. **输入在 iframe 内气泡**，体验受限（小输入框、不方便查看列表）
3. **没有"给谁看"的区分**（给人还是给 AI）
4. **没有列表视图**——标注散落在页面上，无法按时间线浏览
5. **没有持久化**——标注存储在 React state 中，刷新即丢失
6. **没有回复/线程**——每条标注是孤立的

需要一个跨创作端和浏览端的通用评论列表功能。评论分两种：给人看的协作留言（两端都可用），给 Agent 处理的任务（仅创作端可用）。浏览端作为只读预览环境，不涉及项目编辑和 AI 执行能力，因此只能添加「给同事」的评论。

## 目标

1. **统一评论列表**：创作端和浏览端共用同一个评论系统，右侧栏展示评论列表
2. **两种评论类型，按站点区分**：
   - **给人**（两端都可用）：协作留言，同事间讨论，回复式线程
   - **给 Agent**（仅创作端）：AI 处理任务，由 AI Chat / Pi Agent 消费并执行。浏览端不支持此类型
3. **两种页面模式都支持**：单页模式 + 画布模式均可添加和查看评论
4. **点击页面标点**：在评论面板中点击「标点」进入标点模式后，可在页面任意位置点击添加评论气泡（类似 Figma），标点模式下页面仍可正常滚动
5. **跨项目类型**：演示项目和开发项目都可用
6. **持久化**：评论存储在后端，刷新不丢失
7. **实时同步**：多人同时查看时，新评论实时出现

## 范围

| 范围 | 包含 | 不包含 |
|------|------|--------|
| 创作端编辑页 | 右侧栏新增「评论」Tab，完整 CRUD | — |
| 浏览端预览页 | 右侧栏新增「评论」Tab，查看 + 添加「给同事」评论 | 浏览端不能编辑项目内容、不可添加「给 Agent」评论、不可解决/删除他人评论 |
| 单页模式 | 点击页面标点添加评论 + 评论大头针渲染 | — |
| 画布模式 | 截图上按比例渲染评论气泡，点击进入单页模式标点 | 画布网格中的自由位置评论（MVP 仅支持页面级） |
| 演示项目 | 完整支持 | — |
| 开发项目 | 完整支持（给 Agent 的评论可触发 AI 执行） | AI 执行链路不属于本文档范围 |
| 与现有 VisualAnnotation | 并存不冲突；远期可统一 | 本期不改 VisualAnnotation |

## 核心设计

### 1. 数据结构

```typescript
// packages/shared/src/comment.ts（新建）

/** 评论类型 */
type CommentKind = "human" | "agent";

/** 评论状态 */
type CommentStatus = "open" | "resolved";

/** 评论定位目标 */
interface CommentTarget {
  /** 项目 ID（创作端 projectId 或开发项目 sessionId） */
  projectId: string;
  /** 页面 ID */
  pageId: string;
  /** 子页面/状态 ID */
  subPageId?: string;
  /** 页面路由 */
  pageRoute: string;
  /** 元素选择器（元素级评论时使用） */
  selector?: string;
  /** 元素在视口中的位置（百分比，用于大头针渲染） */
  position?: { x: number; y: number };
  /** 元素文本快照 */
  elementText?: string;
  /** 评论时的视口尺寸 */
  viewport?: { width: number; height: number };
}

/** 评论回复 */
interface CommentReply {
  id: string;
  content: string;
  author: string;
  createdAt: number;
}

/** 评论 */
interface Comment {
  id: string;
  projectId: string;
  /** 序号（按项目递增） */
  sequence: number;
  /** 评论类型 */
  kind: CommentKind;
  /** 评论内容 */
  content: string;
  /** 作者标识 */
  author: string;
  /** 定位信息 */
  target: CommentTarget;
  /** 状态 */
  status: CommentStatus;
  /** 回复线程 */
  replies: CommentReply[];
  /** 关联的 Agent 消息 ID（kind=agent 且已被 AI 处理时） */
  agentMessageId?: string;
  createdAt: number;
  updatedAt: number;
  resolvedAt?: number;
  resolvedBy?: string;
}
```

### 3. 评论模式交互

核心原则：**「浏览评论」和「标点添加评论」是两个独立状态，互不干扰。**

#### 浏览评论（默认状态）

用户切换到「评论」Tab 时：
1. 右侧栏显示评论面板，展示评论列表
2. 左侧 iframe 页面**完全正常交互**——链接可点、表单可填、页面可滚动
3. 已有评论在页面上渲染为 **Figma 风格评论气泡**（圆形数字徽章，固定在对应位置）
4. 点击气泡 → 右侧栏滚动到对应评论并高亮；点击列表条目 → 气泡高亮 + 页面滚动到该位置

#### 标点添加评论

用户在评论面板中输入评论内容后，点击 `[📍 标点定位]` 按钮进入标点模式：

```
用户点击 [📍 标点定位]
  → iframe 收到 ENTER_PIN_MODE 消息
  → 光标变为十字准星，页面底部出现提示条：「💬 点击页面任意位置放置评论气泡」
  → ⚠️ 标点模式下页面仍可正常滚动（滚轮/触摸事件不被拦截）
  → 用户点击页面某处
    → iframe 计算点击位置的元素信息和相对坐标
    → iframe 在该位置渲染临时评论气泡（脉冲动画）
    → iframe 发送 postMessage：
        { type: "COMMENT_PIN_DROP", target: { selector, position, elementText, viewport } }
    → 自动退出标点模式，光标恢复默认
  → 父窗口收到 → 右侧栏评论区显示已定位信息（如「📍 首页 > 提交按钮」）
  → 用户确认内容 + 选择类型（创作端）→ 点击「提交评论」
  → 调用 API 创建评论
  → iframe 收到 COMMENT_BUBBLES_UPDATE → 渲染正式评论气泡
  → 右侧栏列表刷新
```

**退出标点模式**：按 `Esc` 或点击页面空白处（无元素区域），取消本次标点，恢复默认光标。

#### 评论气泡（Figma 风格）

页面上的评论标记采用类似 Figma 的圆形数字气泡：

```
  ●── 圆形徽章，中间显示评论序号（如 #3）
  │   未解决：蓝色背景 + 白色数字
  │   已解决：灰色背景 + 勾号 ✓
  │   悬停时：放大 + 显示阴影 + tooltip 预览评论前 60 字
  │   点击时：气泡高亮，右侧栏滚动到对应评论
  └── 通过 CSS `position: fixed` 按百分比坐标定位，随页面滚动自然移动
```

与旧版「大头针」的区别：大头针是图钉形状（📍），Figma 气泡是圆形数字徽章，视觉更简洁，信息量更大（直接显示序号）。

#### 查看评论

- **列表点击**：点击评论条目 → 对应气泡高亮 → iframe 滚动到该位置
- **页面点击气泡**：iframe 发送 `COMMENT_BUBBLE_CLICK` → 右侧栏滚动到该评论并高亮
- **筛选**：
  - 创作端：按状态（全部 / 未解决 / 已解决）+ 类型（同事 / Agent）组合筛选
  - 浏览端：仅按状态（全部 / 未解决 / 已解决）筛选，无 Agent 类型
- **搜索**：按内容关键词搜索

#### 回复评论

- 在评论条目下点击「回复」→ 展开内联输入框 → 输入 → 提交
- 回复实时出现在线程中
- 仅「给人」的评论支持回复（「给 Agent」的评论回复由 AI 系统消息替代）

#### 解决评论

- 点击评论条目上的 ✅ 标记为「已解决」
- 已解决的评论默认折叠（可展开查看）

### 4. 画布模式下的评论

画布模式（Canvas）展示多个页面的截图网格。评论定位方式：

| 评论粒度 | 定位方式 | 显示 |
|---------|---------|------|
| 页面级 | 绑定 `pageId` | 该页面截图左上角显示评论计数徽章 |
| 子页面级 | 绑定 `pageId + subPageId` | 该子页面截图显示计数徽章 |
| 元素级 | 绑定 `selector + position` | 截图上按比例渲染评论气泡（圆形数字徽章） |

- 点击画布中某页截图 → 进入该页的单页模式 → 自动切换到评论 Tab → 可标点评论
- 画布中不支持直接标点（截图上没有 DOM），仅在单页模式下标点

### 5. 与 Agent 的集成

#### 演示项目

「给 Agent」的评论不直接触发代码执行（演示项目没有代码仓库），而是：
1. 评论内容注入 AI Chat 上下文
2. 用户可在 AI Chat 中引用评论：`"处理评论 #3"`
3. Pi Agent 读取评论内容，在演示项目范围内执行修改（通过现有 schema_edit、page_edit 等工具）

#### 开发项目

「给 Agent」的评论触发标准修改流程（参见开发项目方案）：
1. 评论内容 → Pi Agent 分类（UI / Logic）
2. UI 类 → 入任务队列 → Codex 执行
3. Logic 类 → 标记「待开发者处理」
4. 执行结果回写到评论的 `agentMessageId`，状态更新为「已完成」

### 6. 后端 API

所有评论 API 挂在 agent-service 下：

```
# 评论 CRUD
GET    /api/projects/:projectId/comments
       ?kind=human|agent
       &status=open|resolved
       &pageId=xxx
       → Comment[]

POST   /api/projects/:projectId/comments
       Body: { kind, content, target }
       → Comment
       校验：kind=agent 仅接受来自创作端的请求（通过 API key 区分），
       浏览端请求 kind=agent 时返回 403

PATCH  /api/projects/:projectId/comments/:id
       Body: { content?, status?, agentMessageId? }
       → Comment

DELETE /api/projects/:projectId/comments/:id
       → { success: true }

# 回复
POST   /api/projects/:projectId/comments/:id/replies
       Body: { content, author }
       → CommentReply

# 批量解决
POST   /api/projects/:projectId/comments/resolve-bulk
       Body: { commentIds: string[] }
       → { resolved: number }
```

#### 存储

| 选项 | 优缺点 |
|------|--------|
| **文件系统** `data/projects/:id/comments.jsonl` | 简单、免依赖；需处理并发写；适合 MVP |
| **SQLite** | 已有 users.db 先例；支持查询；需建表 |
| **内存 + 定期落盘** | 最快、代码最少；进程重启丢失；不推荐 |

**推荐 MVP 选 SQLite**，与 users.db 模式一致，后续迁移成本低。

#### WebSocket 事件

复用现有 `ws-event-router.ts`，新增：

```typescript
// 评论创建
{ type: "comment_created", comment: Comment }

// 评论更新（内容、状态变更）
{ type: "comment_updated", commentId, changes: Partial<Comment> }

// 评论删除
{ type: "comment_deleted", commentId }

// 新回复
{ type: "comment_reply_added", commentId, reply: CommentReply }
```

创作端和浏览端都通过 WebSocket 连接 agent-service 接收实时评论更新。

### 7. iframe 通信协议扩展

基于现有 postMessage 协议（`packages/demo-ui/src/PreviewPanel.tsx`），新增：

| 方向 | 消息类型 | 关键字段 | 用途 |
|------|---------|---------|------|
| 父→子 | `ENTER_PIN_MODE` | `enabled: boolean` | 进入/退出标点模式（光标变十字准星，页面仍可滚动） |
| 父→子 | `COMMENT_BUBBLES_UPDATE` | `bubbles: CommentBubble[]` | 同步评论气泡数据 |
| 父→子 | `COMMENT_BUBBLE_FOCUS` | `commentId: string` | 高亮某个气泡（从列表点击时） |
| 子→父 | `COMMENT_PIN_DROP` | `target: CommentTarget` | 用户在标点模式下点击页面放置气泡 |
| 子→父 | `COMMENT_BUBBLE_CLICK` | `commentId: string` | 用户点击已有评论气泡 |
| 子→父 | `COMMENT_BUBBLE_HOVER` | `commentId: string` | 用户悬停评论气泡 |

> ⚠️ 标点模式下不拦截滚动事件——滚轮和触摸滚动正常传递，确保长页面也能方便定位。`Esc` 或点击无元素区域退出标点模式。

```typescript
// 评论气泡数据（父窗口传给 iframe）
interface CommentBubble {
  commentId: string;
  sequence: number;
  kind: CommentKind;
  selector: string;
  position: { x: number; y: number };
  resolved: boolean;
}
```

### 9. 与现有 VisualAnnotation 的关系

| 维度 | VisualAnnotation（现有） | Comment（新增） |
|------|------------------------|----------------|
| 触发方式 | 编辑模式中点击元素 | 标点模式中点击页面放置气泡 |
| 输入位置 | iframe 内气泡 | 右侧栏表单 |
| 内容 | 单条文本 + 样式变更 | 文本 + 回复线程 + 类型标记 |
| 定位 | 绑定 DOM 元素（selector） | 元素或自由坐标，Figma 风格圆形气泡 |
| 列表视图 | 无 | 右侧栏完整列表 |
| 持久化 | React state（刷新丢失） | agent-service SQLite |
| 跨站点 | 仅创作端 | 创作端 + 浏览端 |
| 样式编辑关联 | 是（styleChanges） | 否 |

**本期不改 VisualAnnotation。** 两者并行——VisualAnnotation 继续服务编辑工作流，Comment 服务协作讨论。远期评估是否统一。

### 10. 权限与鉴权

| 站点 | 查看评论 | 添加「给同事」 | 添加「给 Agent」 | 回复 | 解决/删除 |
|------|---------|-------------|---------------|------|----------|
| 创作端（已登录） | ✅ | ✅ | ✅ | ✅ | ✅（自己的 + 项目所有者可删任意） |
| 浏览端（公开） | ✅ | ✅ | ❌ | ✅ | ❌ |

- 创作端通过现有 JWT 鉴权识别用户
- 浏览端**无需登录**即可查看和添加评论，评论作者使用固定匿名标识（如随机 ID），用户无感知
- 浏览端**不能添加「给 Agent」评论**——浏览端没有 AI 执行能力，且不参与项目编辑
- 评论 API 不额外增加独立鉴权层，`kind=agent` 的创建请求在服务端也校验来源（创作端 API key）

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 浏览端用户身份 | 使用匿名标识（如随机 ID），用户无感知；无需昵称输入 |
| iframe 跨域导致 postMessage 不通 | 现有系统已验证同域 postMessage 正常工作 |
| 画布模式截图无法精确定位评论 | MVP 仅页面级定位 + 比例换算；远期考虑重新截图时标注 |
| 评论量大时 SQLite 查询性能 | 按 projectId 索引；远期加全文搜索 |
| 多人同时标点导致并发冲突 | 评论创建是幂等的（每次创建新记录），无冲突；编辑采用 last-write-wins |
