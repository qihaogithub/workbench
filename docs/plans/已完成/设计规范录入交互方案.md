# 设计规范录入交互方案

> 状态：远期规划 · 方案设计期（交互验证中）
> 关联 Demo：`design-spec-interaction-demo.html`（仓库根目录，纯前端单文件）
> 关联模块文档：`docs/项目文档/创作端/04-配置与预览/`

## 背景

创作端目前把"设计规范"当作两个松耦合的软性载体，尚未形成一等公民：

1. **知识库文档层**（`knowledge/设计规范.md`）：自然语言约定，由用户手写维护，AI 在生成/修改页面时按需读取。无结构化值、无 token、无校验。
2. **项目级共享配置层**（`project.config.schema.json` + `values.json`）：承载可穷举的样式值（品牌色、统一文案、通用图片），通过预览运行时合并注入各页面。

**问题**：
- 设计规范与真实配置值脱节——知识库文档里的规范不随配置变化而更新，容易过期漂移。
- 没有一种"设计规范"的录入/维护交互，导致规范散落在文档里，团队难以对齐、AI 难以可靠消费。
- 配置面板是单元素级配置化（`visual-configurator.ts`），无法表达"一个设计规范对应多个配置项"、"部分配置项不需要规范"这类更高层语义。

**目标**：面向非技术设计师 / 产品经理，提供一套设计规范的录入与维护交互，使规范成为**条目标为主体、绑定配置项为素材**的可维护资产，主要给人阅读，AI 可读写。

## 需求澄清（已确认）

| 决策点 | 结论 |
| --- | --- |
| 目标用户 | 非技术设计师 / 产品经理，低门槛 |
| 规范内容 | 围绕"配置项"的设计规范 |
| 录入方式 | **自动采集当前配置项数据**，不强制手工加文字说明；说明文字支持富格式（Markdown） |
| 价值是否可回写 | **必须只读**（不回写配置，避免双数据源漂移） |
| 聚合范围 | 项目级 + 页面级配置都纳入 |
| 说明格式 | Markdown（与现有 knowledge 机制一致，AI 易读写） |
| 分组结构 | **规范条目为主体**，自由创建/命名/删除；不是配置项驱动的自动分组 |
| 绑定关系 | **多对多**：一个条目引用多个配置项；一个配置项可被多个条目引用 |
| 绑定作用 | **仅展示参考**（展示当前值 swatch），不强制作为 AI 约束 |
| 未绑定配置项 | 保持普通，不强制纳入规范 |
| 消费方式 | 主要给人类阅读；AI 可读写 |

## 数据模型

```
workspace/
└── design-spec.json          ← 新增
     {
       entries: [
         {
           id: string,
           title: string,             // 规范名，如"主按钮"
           markdown: string,          // 富文本说明，可选
           refs: [                    // 引用的配置项（0~n）
             { scope: "project" | "page", pageId?: string, fieldKey: string }
           ]
         }
       ]
     }
```

**核心不变量**：`design-spec.json` 只存"条目结构 + 说明文字 + 对配置项的引用"，**不存值**。值永远实时从 `project.config.schema.json` / 页面 `config.schema.json` 投影。这样规范永远不过期，AI 改配置后规范自动跟上。

**跨页引用稳定性**：页面级配置项按 `pageId + fieldKey` 引用。若页面被删除，引用悬空——规范中显示"已失效引用"灰条，不阻断，由设计者手动清理。

## 交互设计

### 布局（三区）

1. **配置项素材池**（侧栏）
   - 列出项目级 + 所有页面级配置项
   - 支持搜索、按来源（项目级/页面）过滤、按分类分组
   - 每项显示：标题、类型徽标（文本/颜色/图片）、来源；未绑定项保持普通样式
2. **规范条目列表**（主区）
   - 条目标题、绑定配置项 refs、Markdown 说明
   - 条目可展开/折叠，可重命名、删除
3. **绑定交互**
   - 从素材池**拖拽**配置项进条目，或点 **＋** 弹出"加入哪个条目"菜单
   - 条目内渲染已绑定配置项的值 swatch（颜色块 / 文本缩写 / 图片缩略图），**只读**

### 流程

1. **自动采集**：系统扫描项目级 + 页面级 schema，生成素材池；不自动生成条目（规范条目由设计者主动创建）
2. **创建条目**：＋ 新建规范 → 命名 → 可选填 Markdown 说明
3. **绑定**：拖拽 / ＋ 把配置项加入条目，形成多对多
4. **值只读投影**：条目内展示绑定项的当前值，不提供编辑入口

## AI 读写模型

- **AI 读**：把 `design-spec.json` 渲染成 Markdown + 合并配置值快照，注入上下文（复用现有 knowledge 读取机制 `packages/author-site/src/lib/agent/prompts/system-prompt.md`），AI 生成/修改页面时感知规范。
- **AI 写**：AI 通过改配置（write_config）+ 写 entry 的 `title`/`markdown`/`refs`，规范自动重渲染，无需额外同步。

## 落地步骤

1. **数据层**：`design-spec.json` 读写 util（放 `@workbench/project-core`，保证 Web API 与 CLI 复用）；聚合器扫描项目级 + 页面级 schema 生成素材池
2. **UI 层**：设计规范页（Tab 入口，与配置预览并列）、素材池、条目列表、绑定交互、值 swatch 渲染、Markdown 说明块
3. **AI 集成**：读（merge 视图注入 prompt）+ 写（工具挂到 `design-spec.json`）
4. **引用稳定性**：跨页引用失效时显示"已失效引用"灰条
5. **文档**：更新 `docs/项目文档/创作端/04-配置与预览/` 相关技术文档 + INDEX

## 风险与待确认

- **Tab 入口位置**：待确认是① 项目编辑页新增独立 Tab（与配置预览并列）② 并入知识库/文档区 ③ 面板抽屉
- **AI 读的权重**：已确认"仅展示参考"，但 AI 生成时参考规范到多深，决定 AI 集成优先级
- **多对多带来的管理复杂度**：配置项被多个条目引用时，编辑端需清晰标记"已绑定于 N 个条目"
- **与现有知识库 `设计规范.md` 的关系**：是并存（知识库做自由文档、本功能做结构化资产）还是收敛，需产品决策
