# 创作端页面运行时转换-像素级还原方案

## 背景

创作端当前支持三种页面运行时：`prototype-html-css`、`high-fidelity-react`、`sketch-scene`。用户在编辑过程中会通过页面类型切换入口，把 HTML/CSS 原型页转为高保真 React 页，或反向降级。

实际体验中，HTML/CSS 原型页（尤其包含复杂背景图、渐变、装饰元素、非标准布局的活动页、地图页）转为 React 后视觉效果明显劣化：背景丢失、装饰元素被通用组件替换、布局错位、颜色/阴影简化。

根本原因是当前转换流程把「转换」和「新建/重写」混用同一套提示词约束，且没有给 AI 提供视觉上下文。

## 目标

让「页面运行时转换」在两种方向上都能达到**像素级还原**：

- 原型页 → 高保真 React 页：视觉、布局、资源、层级与原型渲染结果一致。
- 高保真 React 页 → 原型页：静态化后的 HTML/CSS 与 React 页当前渲染结果一致。

同时保留「新建/重写页面」时利用 `@preview/sdk` 通用组件和 Tailwind 提升效果的能力，不因为转换场景而废弃通用组件策略。

- 用户触发切换后，系统调用 [`buildRuntimeConversionPrompt`](file:///Users/jojo/Documents/workbench/packages/author-site/src/app/demo/[id]/edit/page.tsx#L419-L465) 构造隐藏 prompt。

- 当前 prompt 仅要求「保持产品意图、页面结构、配置字段和视觉层级一致」「还原为可交互 React 页面」，没有视觉上下文，也没有「像素级还原」的强制约束。

### System Prompt 的组件导向

[`packages/author-site/src/lib/agent/prompts/system-prompt.md`](file:///Users/jojo/Documents/workbench/packages/author-site/src/lib/agent/prompts/system-prompt.md#L287-L312) 对高保真 React 页的质量标准要求：

- 使用 Tailwind CSS。
- 图标、按钮、卡片、弹窗、图片、倒计时、进度条、常见动效、图表、庆祝效果、轮播等优先从 `@preview/sdk` 导入。
- 不要引入未登记依赖。

这套规则适合**新建页面**或**重写内容**，但在**转换已有复杂视觉页面**时会导致 AI 用通用组件替换原型的自定义视觉。

### 上下文机制

- L3 工作区上下文 [`scan-workspace.ts`](file:///Users/jojo/Documents/workbench/packages/author-site/src/lib/agent/scan-workspace.ts#L90-L92) 不再自动嵌入源码，只列出文件路径；源码依赖 AI 通过 `readFile` 读取。
- 转换消息没有附带当前页面的截图或任何视觉附件（`images` 参数为 `undefined`）。
- 转换完成后只走编译/原型契约校验，没有视觉对比或自动修复闭环。

### 原型页大小限制

[`preview-validation.ts`](file:///Users/jojo/Documents/workbench/packages/agent-service/src/backends/pi-tools/preview-validation.ts#L79-L136) 对原型页有 `MAX_PROTOTYPE_HTML_LENGTH = 2_000_000` 和 `MAX_PROTOTYPE_CSS_LENGTH = 120_000` 的限制。CSS 超限会触发「请压缩 CSS，移除不必要的样式规则」，可能导致源文件视觉细节已经受损，再转 React 会进一步劣化。

## 方案

### 1. 区分「转换」与「新建/重写」的提示词策略

在高保真 React 页的代码质量标准中明确区分两种场景：

- **新建/重写页面**：鼓励使用 Tailwind CSS 和 `@preview/sdk` 通用组件，提升开发效率和一致性。
- **页面运行时转换（prototype ↔ high-fidelity）**：要求**像素级还原**，优先保留原有视觉、布局、资源引用、装饰元素、背景图、渐变、阴影、字体、z-index 层级。只有在原效果确实无法在当前运行时实现时，才允许替换，并需说明原因。

- [`packages/author-site/src/app/demo/[id]/edit/page.tsx`](file:///Users/jojo/Documents/workbench/packages/author-site/src/app/demo/[id]/edit/page.tsx#L419-L465) 的 `buildRuntimeConversionPrompt`

### 2. 转换时附带视觉上下文

在转换触发前获取当前页面的渲染截图，作为 `ImageAttachment` 一起发送给 AI。

- 原型页 → React：截取当前原型页在 Shadow DOM 中的渲染结果。
- React → 原型页：截取当前 React 页在 iframe 中的渲染结果（当前已有单页预览截图能力，可复用）。

实现位置：

- 截图获取：复用 [`packages/author-site/src/components/demo/useScreenshotGeneration.ts`](file:///Users/jojo/Documents/workbench/packages/author-site/src/components/demo/useScreenshotGeneration.ts) 或 [`PreviewStage`](file:///Users/jojo/Documents/workbench/packages/author-site/src/components/demo) 的已有截图能力。
- 消息发送：修改 [`packages/ai-chat-shared/src/chat/hooks/use-chat-stream.ts`](file:///Users/jojo/Documents/workbench/packages/ai-chat-shared/src/chat/hooks/use-chat-stream.ts#L1360-L1450) 和 [`packages/ai-chat-shared/src/ai-chat.tsx`](file:///Users/jojo/Documents/workbench/packages/ai-chat-shared/src/ai-chat.tsx#L390-L421)，让 `auto_repair` 触发也支持 `images` 参数；并在 [`page.tsx`](file:///Users/jojo/Documents/workbench/packages/author-site/src/app/demo/[id]/edit/page.tsx#L5756-L5782) 中传入截图。

### 3. 增强转换 Prompt

`buildRuntimeConversionPrompt` 需要补充：

- 明确要求「像素级还原」，以视觉截图为基准。
- 列出必须保留的视觉要素：背景图/背景色、渐变、阴影、圆角、边框、装饰元素、图标、字体、字号、字重、颜色、元素位置与层级。
- 禁止擅自用 `@preview/sdk` 通用组件替换原有自定义视觉。
- 资源引用规则：保留项目内相对路径的图片/字体/资源引用，禁止丢弃或替换为占位图。
- 转换后自检：要求 AI 用 `captureScreenshot` 截图对比，确认视觉一致。

### 4. 高保真 → 原型页的静态化增强

当前 React → 原型页会先尝试程序静态化（[`extractStaticPrototypeSnapshot`](file:///Users/jojo/Documents/workbench/packages/demo-ui/src/PreviewPanel.tsx#L180-L212)），失败才交给 AI。

- 程序静态化路径应保留更多样式：背景图、渐变、阴影、z-index、transform 等。
- 静态化结果如果视觉差异大，应自动把截图一起交给 AI 修复，而不是只传错误文本。

### 5. 转换后视觉验证闭环（可选 / 二期）

- 转换完成后，系统自动截取目标运行时的渲染图。
- 与源运行时截图进行像素/感知对比（SSIM 或简单尺寸/关键元素检查）。
- 如果差异超过阈值，自动进入一次修复迭代。

该步骤涉及截图服务/对比算法，成本较高，建议作为二期。

### 6. 放宽原型页 CSS 大小限制（可选）

如果确认大量视觉细节丢失是因为 `MAX_PROTOTYPE_CSS_LENGTH = 120_000` 导致 CSS 被压缩，可以考虑：

- 提升上限。
- 或改为按页面截图/渲染结果评估，而不是单纯按字符数。

需要先收集实际项目数据再决定，避免放宽后影响性能。

1. 代码层面：`pnpm check:author`、`pnpm check:demo-ui`、`pnpm check:agent`。
2. 功能层面：准备一个复杂视觉原型页（如用户提供的活动页），触发转换后检查 React 页是否保留背景图、装饰元素、布局位置。

## 风险与待确认事项

1. **截图时机**：转换触发时页面可能尚未完成渲染（尤其是 iframe 中的 React 页），需要确保截图在 `singlePreviewLoaded` 或 Shadow DOM 稳定后执行。
2. **模型视觉能力**：当前后端模型是否支持多模态输入？如果不支持，`images` 参数即使传了也无法被利用，需要确认 Agent Service 和模型配置。
3. **Token/上下文成本**：复杂页面的截图 Base64 较大，会增加 LLM 调用成本和延迟。需要评估是否所有转换都默认带图，还是仅复杂页面带图。
4. **通用组件策略冲突**：在 System Prompt 中区分「新建」和「转换」场景后，需要确保 AI 能正确识别当前任务属于哪一类。`buildRuntimeConversionPrompt` 已经明确是转换场景，但日常对话中的「把首页改成 React」可能仍是模糊边界。
5. **原型页 CSS 大小上限**：提升上限可能影响预览性能和校验耗时，需要先确认当前是否有项目真实触达上限。
6. **反向降级视觉一致性**：React → 原型页的程序静态化路径当前只抽取 DOM 和内联样式，对复杂 CSS 规则（如伪元素、动画、媒体查询）支持有限，需要评估是否把这些场景交给 AI 兜底。
