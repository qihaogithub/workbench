# 创作端-开发模式路由加载性能治理方案

## 背景

开发模式下，创作端在“首页 → 项目编辑页”与“编辑页 → 首页”两条日常路径上存在明显等待，影响页面开发、验收和调试效率。

本方案只治理路由响应、编译和首屏就绪链路。协同会话过期、诊断 SQLite 损坏等问题与本次性能根因无直接因果关系，继续在对应模块中独立处理。

## 结论摘要

这是系统性开发性能问题，不是单个业务 API 慢或浏览器偶发卡顿。已确认三层根因：

1. **编辑路由静态可达模块图过大（主因）**：Next.js 14.1 Webpack 首次编译需处理约 10,300 个模块；其中存在明确的聚合入口泄漏和可选功能重依赖。
2. **编辑页在 bootstrap 未完成时发出非法 Workspace Authority 请求（主因的放大器）**：空 `workspaceId` / `sessionId` 生成了双斜杠 URL，触发 `/not-found` 冷编译并阻塞同期 API。
3. **首页缩略图 metadata 请求扩散（返回首页的视觉就绪瓶颈）**：空闲延迟后一次发出 103 个请求，长尾主要来自浏览器连接排队，而不是单个截图服务请求处理数秒。

编辑页 9,451 行是架构可维护性风险，但不是耗时的直接证据；trace 中该入口自身的 SWC 转换仅为百毫秒级。因此，不应把“拆大文件”当作本次性能修复本身。

截至 2026-08-12，本方案的 P0 导入/请求治理和 P1 首页批量读取已经实施并通过验收。默认开发编译器仍为 Next.js 14.1 Webpack：Next 14.2/Turbopack 兼容探针没有带来额外冷编译收益，且会扩大 instrumentation、原生依赖和测试环境的变更面，因此已撤回。迁移到受支持的 Next LTS 继续作为独立升级事项，不与本次已验证的业务链路优化混合。

## 目标与范围

- 显著降低首页与编辑页的开发模式冷编译时间。
- 消除编辑页正常进入链路中的空 ID 请求和 `/not-found` 意外编译。
- 将首页截图 metadata 由页级 N 次查询收敛为一次批量读取，图片文件仍按可见性懒加载。
- 建立可重复的 Next dev trace 和浏览器 timing 基线，防止聚合入口回流。
- 范围包含 `author-site` 首页、编辑页入口、编辑 bootstrap 请求以及截图读取链路；不改变项目数据格式、协同协议或生产业务行为。

## 复现与证据

### 测量口径

- 环境：Node 24.10.0、Next.js 14.1.0、Webpack dev bundler、本地 `author-site` 4200 端口。
- 固定路径：冷启动后打开 `/`，进入 `/demo/proj_1779608460372/edit`，再回到 `/`。
- 主要证据：Next 终端日志、`.next/trace`、Navigation Timing 与 Resource Timing。
- 区分三个指标：路由首响应、编辑器可用、首页缩略图视觉就绪。三者不能用同一个 `load` 时间混合表达。

### 已确认数据（2026-08-12）

| 链路 | 观测 | 证据结论 |
| --- | --- | --- |
| 首页首次进入 | 两次采样的首次路由编译分别约 9s 与 16.8s，模块数约 2,400 | 首次等待主要是开发路由编译，不是项目目录读取。 |
| `listProjects()` | 同一进程 5 次读取为 6.2–24.5ms，16 个项目 | 当前数据规模下不是优化重点，不应提前引入项目索引或长生命周期缓存。 |
| 编辑路由冷编译 | 两次独立观测分别约 165s / 10,304 modules 和 78.6s / 10,293 modules | 绝对时间受缓存与机器状态影响，但稳定的万级模块图是可重复主因。 |
| 编辑路由 trace | `compile-path` 78.565s，client invalidation 78.192s，server invalidation 28.253s | 等待发生在路由响应之前，而非 React 渲染完成之后。 |
| 空 Authority 请求 | `/api/workspace-authority/<projectId>//state?sessionId=` | 路由不匹配并触发 `/not-found` 冷编译 35.7s。 |
| 同期编辑 API | `/api/sessions`、`/api/auth/me` 等在上述编译期间出现约 38s 长尾 | 主要是 Next dev 编译争用，不能直接归因为各 API 业务 I/O 慢。 |
| 返回已热编译首页 | `responseStart` 约 1.81s，`load` 约 3.40s | 页面框架可先出现，后续缩略图是独立的视觉就绪问题。 |
| 首页 metadata | 一次出现 103 个请求；最慢 3.82s | 其中约 3.74s 为浏览器排队，服务端等待约 84ms；核心是请求扇出，不是单请求超时。 |

### 实施后验收数据（2026-08-12）

环境与项目路径保持不变，每轮在无旧浏览器请求干扰的前提下清理 `.next` 并重启 author-site。第三轮首次采样被旧标签的 Authority 请求污染，已明确作废并重新采样，不纳入结果。

| 指标 | 样本 | 中位数/结论 |
| --- | --- | --- |
| 编辑路由冷编译 | 24.0s、23.0s、22.4s | 23.0s；相对治理前两次样本中位数 121.8s 约下降 81.1%，不再出现分钟级样本。 |
| 编辑路由模块数 | 8,605、8,605、8,605 | 8,605；相对治理前约 10,299 modules 下降约 16.4%。 |
| 浏览器冷导航 `responseStart` | 26.12s、25.00s、24.16s | 25.00s。 |
| 浏览器冷导航 `load` | 29.53s、28.53s、27.41s | 28.53s。 |
| 已热编译编辑页返回首页 | UI 就绪 111ms | 达到 1s 内目标。 |
| Authority 请求 | 无空 workspace/session 标识请求 | 未触发由本缺陷导致的 `/not-found` 编译。 |
| 首页截图读取 | 1 个 `POST /api/screenshots/metadata`，0 个 `?meta=1` | 图片文件保持可见性加载；screenshot-service 未启动时仍从共享磁盘正常显示已有缩略图。 |

这组数据说明收益来自静态导入边界、Bootstrap 门禁和首页请求收敛，而不是框架版本变化。模块数降幅小于时间降幅，符合“移除几条高成本 issuer 子树并消除并发意外编译”的根因判断；不能把所有波动都归因于模块数量本身。

### 模块图证据

`.next/trace` 显示，编辑页客户端入口的几条直接 issuer 子树带入了大量模块：

| issuer 子树 | 约定位模块数 | 已确认的路径 |
| --- | ---: | --- |
| AI Chat 宿主 | 1,706 | [`ai-chat-setup.ts`](../../../packages/author-site/src/lib/ai-chat-setup.ts) 仍从 `@workbench/ai-chat-shared` 根入口导入配置函数，进而解析 Mermaid、D3、lodash-es 等。 |
| 知识文档弹窗 | 647 | [`KnowledgeDocDialog.tsx`](../../../packages/author-site/src/components/demo/KnowledgeDocDialog.tsx) 同时引用 demo-ui 根入口、DocumentEditor 和 Streamdown/Shiki。 |
| `date-fns/locale` | 537 | [`page.tsx`](../../../packages/author-site/src/app/demo/[id]/edit/page.tsx) 从 locale 桶入口取 `zhCN`，导致全量 locale 被解析。 |
| author-site validator 兼容入口 | 535 | [`lib/validator.ts`](../../../packages/author-site/lib/validator.ts) 经 `@workbench/demo-ui` 根入口带入 DocumentEditor、Milkdown/Crepe 等无关功能。 |

此外，历史提交已将 16 个重组件改为 `next/dynamic`，生产构建中编辑页 chunk 从 318KB 降至 211KB，First Load JS 从 1.34MB 降至 1.13MB。这证明动态边界对首次下载有效，但本次 trace 同时证明 Webpack dev 仍会为同一路由构建这些异步 chunk。因此，“继续增加 `next/dynamic`”不能单独作为冷编译解法。

### 首页截图链路证据

- [`home-page.tsx`](../../../packages/author-site/src/components/demo/home-page.tsx) 在开发模式延迟 15 秒后统一允许 metadata 加载。
- [`demo-card.tsx`](../../../packages/author-site/src/components/demo/demo-card.tsx) 为每个进入视口或近视口的页面单独发出 metadata 请求。当许多卡片已被 observer 标记可见时，开关切换会同时触发所有请求。
- [`route.ts`](../../../packages/author-site/src/app/api/screenshots/file/[projectId]/[pageId]/route.ts) 先转发 screenshot-service，失败后再读本地 `DATA_DIR`。当前 Docker 中 author-site 与 screenshot-service 共享同一个 `DATA_DIR` volume，metadata 读取不必与截图生成服务强耦合。

## 根因分级

### P0：编辑 bootstrap 空 ID 请求

[`page.tsx`](../../../packages/author-site/src/app/demo/[id]/edit/page.tsx) 在 `workspaceId` 和 `sessionId` 初始为空字符串时就启用 [`useWorkspaceAuthorityState`](../../../packages/author-site/src/app/demo/[id]/edit/hooks/useWorkspaceAuthorityState.ts)。浏览器 client 没有拒绝空 ID，最终构造出不可匹配路由。

这不只是一个 404；在 Next dev 冷状态下，它会迫使 `/not-found` 参与编译，并与正常 bootstrap API 争用编译器。

### P0：编辑路由模块图泄漏与工具链不匹配

直接的重依赖、根入口再导出和 locale 桶入口共同放大了 Webpack 依赖图。Next.js 14.1 距当前工具链较远，而项目又统一使用 Node 24，因此应同时治理应用导入边界和开发编译器。

已对当前 Next 14.1 直接尝试 `next dev --turbo`，结果在 instrumentation 阶段失败：`better-sqlite3` 被编译后无法找到原生 binding。所以不能只改一个启动参数；Turbopack 必须与 Next 升级和现有自定义配置迁移一起验证。

### P1：首页 metadata 请求扇出

这组请求不阻塞首页 HTML 首响应，但会延迟卡片缩略图就绪，占用浏览器同源连接与 Next dev 请求处理资源，也会使用户感知“返回首页仍在加载”。

### 已排除的主因

- `listProjects()` 当前仅十几毫秒级，不需要为本次问题引入新缓存层。
- 截图 metadata 最慢请求中，大部分时间为浏览器排队，不是 screenshot-service 单请求处理 3–4 秒。
- 单纯把 9,451 行页面拆成更多文件不会自动减少静态可达模块图。
- 已有 `next/dynamic` 降低了生产首次 JS，但不能证明 Webpack dev 会延迟编译该异步图。

## 治理方案

### 阶段一：先修复确定性缺陷和导入泄漏

1. 只有当 `projectId`、`workspaceId` 和 `sessionId` 均就绪时才启用 Workspace Authority 首次拉取与轮询。
2. 在 [`workspace-authority-browser-client.ts`](../../../packages/author-site/src/lib/workspace-authority-browser-client.ts) 增加参数完整性防线；空 ID 直接返回可识别错误，不得发起网络请求。
3. 把 `author-site/lib/validator.ts` 改为只从 `@workbench/demo-ui/validator` 和 `@workbench/demo-ui/types` 等精确子路径导入。
4. 为 `configureAiChatShared` 提供独立 `config` export，禁止 `ai-chat-setup.ts` 经共享包根入口解析整套消息渲染组件。
5. 将 `date-fns/locale` 桶导入改为单个 `zh-CN` locale 子路径。
6. 把 `KnowledgeDocDialog` 中的 demo-ui 根导入改为 DocumentEditor 精确子路径，并核对 Streamdown 代码高亮是否可限定语言和主题集。
7. 在高频路由建立静态导入约束，防止 `@workbench/demo-ui`、`@workbench/ai-chat-shared`、`date-fns/locale` 根/桶入口回流。

这一阶段保持业务 UI 和状态管理不变，优先用小改动消除已证实的无效工作。每个导入修复单独采样，不将多个假设捆绑成一次大重构。

### 阶段二：升级开发编译器，不盲目切开关

1. 在独立升级任务中选择当时仍受支持的 Next.js 版本，不继续围绕 14.1 打补丁。
2. 将现有 Webpack 定制能力显式映射到 Turbopack：`.md` 文本加载、`.js` 扩展别名、`vscode-jsonrpc` / `langium` 客户端排除、workspace package 解析。
3. 对 instrumentation 的原生依赖单独验证：`better-sqlite3`、`typescript`、`langium` 不得被错误打入需要重建 binding 的 bundle。
4. 通过首页、编辑页、文档编辑、AI Chat、草图、预览、截图和 Fast Refresh 兼容性门禁后，才把 Turbopack 作为默认 dev bundler。
5. 保留明确的 Webpack 诊断命令用于转换期对照，但日常开发只保留一个默认入口。

Turbopack 的价值在于增量计算、并行和按请求懒构建；它才能让现有的真实条件式 `next/dynamic` 边界更好地服务开发编译。不建议为规避 Webpack 冷编译而把编辑器拆成 iframe 或微前端。

### 阶段三：将首页 metadata 收敛为本地批量读取

1. 新增 author-site 首页专用的批量 metadata 接口，一次接收当前项目/页面标识集合，返回 hash、variant、renderBox 和带 hash 的图片 URL。
2. metadata 直接读取 author-site 与 screenshot-service 共享的 `DATA_DIR`；用文件 stat 完成空图判定，不为每页先转发 screenshot-service。
3. 截图生成仍归 screenshot-service，截图读取与生成边界保持分离；批量读取不得触发生成、补生或重试。
4. 首页空闲后只发起一个 metadata 请求；卡片图片文件继续根据可见性懒加载，路由离开时中止未完成请求。
5. screenshot-service 离线时，已存在的共享磁盘截图仍能读取；缺失项直接显示占位，不增加全局复杂熔断状态。

该方案同时消除 N 次内部转发、服务不可用耦合和浏览器连接排队，比“保留 103 个请求再增加并发队列/熔断”更简单。

### 阶段四：只在仍未达标时做功能域减重

完成导入修复和编译器升级后，再根据新 trace 决定是否继续处理 AI Chat、知识文档、Shiki 语言集或 Mermaid 图。只优化 trace 中仍然排名靠前的子树，不做无指标的全页拆分。

页面容器、状态 hook 和 UI 组件的结构拆分可以作为可维护性任务，但其性能验收仍必须以“模块图真正不再静态可达”为准，而不是文件数或行数。

## 验证与验收

### 性能采样

- 分别保留“清理 `.next` 的冷启动”和“同一 dev 进程的热路由”结果，不混合取平均。
- 同一提交、同一项目、同一服务拓扑下各运行至少 3 次，以中位数为主，保留范围。
- 记录 Next `compile-path`、client/server invalidation、modules 数、浏览器 `responseStart`、编辑器 ready marker 和首页缩略图 ready marker。
- screenshot-service 运行/停止分别验证，但不将服务停止时的结果混入路由编译基线。

### 必须满足的功能门禁

- 正常进入编辑页时，Network 中不得出现空 `workspaceId` / `sessionId` 的 Authority 请求，Next 日志不得因此编译 `/not-found`。
- 导入修复后，trace 中 `lib/validator.ts` 不得再经 demo-ui 根入口到达 DocumentEditor/Milkdown，`ai-chat-setup.ts` 不得再经根入口到达 AssistantMessage/Mermaid。
- 返回首页后，metadata 网络请求数从页面数量级降为 1；图片文件仍只为可见/近可见卡片加载。
- screenshot-service 不可用时，已有共享磁盘缩略图可正常显示，缺失图显示占位，不触发生成或重试风暴。
- AI Chat、评论、知识文档、草图、配置、保存、协同、预览和 Fast Refresh 行为保持一致。

### 性能目标

- 阶段一完成后，编辑路由冷编译模块数和中位时间必须同时下降；任一指标无变化时不得将对应改动宣称为编译优化。
- 全部治理完成后，同机冷启动的编辑路由 `compile-path` 中位数至少比本次 Webpack 基线降低 60%，且不再出现分钟级样本。
- 编辑路由已热编译时，返回首页的 `responseStart` 中位数目标为 1s 内；若未达标，必须用服务端分段计时证明新瓶颈，不重新假定 `listProjects()` 慢。

### 回归命令

- `pnpm check:author`
- `pnpm check:demo-ui`
- `pnpm check:ai-chat-shared`
- 截图接口改动时增加定向 author-site API 测试；如果调整 screenshot-service 合同，再运行 `pnpm check:screenshot`。
- Next/Turbopack 升级还需运行项目现有创作端核心 E2E 回归与生产构建。

本次实施已运行 `pnpm check:author`（154 suites / 1,110 tests）、`pnpm check:demo-ui`（16 files / 94 tests）以及 author-site 生产构建。生产构建成功；既有 Edge Runtime、Hook dependency 和 `<img>` lint 提示仍为 warning，不影响构建产物生成。

## 风险与待确认事项

- `.next/trace` 的聚合 duration 会因并行 span 重叠，不能直接求和当作墙钟时间；本方案只用 `compile-path` / invalidation 的墙钟时间和 issuer 子树的模块数做判断。
- 导入子路径需要在 package `exports` 中正式公开，不应从其他 workspace package 深度导入未公开源文件。
- Next.js 升级会触及 React、App Router、instrumentation 和原生扩展边界，必须独立实施，不与业务功能变更混合。
- 首页批量 metadata 接口需限制项目/页面数量并复用现有 ID 校验，防止路径穿越和无界文件扫描。
- 如果未来 author-site 与 screenshot-service 不再共享 `DATA_DIR`，需在部署架构变更中重新定义批量读取合同；不为当前不存在的拓扑提前增加兼容层。
