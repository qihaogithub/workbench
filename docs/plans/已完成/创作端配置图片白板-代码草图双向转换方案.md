## 一、背景

当前项目的白板不需要达到 Figma 的完整设计能力，是让用户绘制简单草图，绘图能力媲美excalidraw即可。让AI以对AI最擅长的代码方式输出，让人类用传统绘图工具绘图，AI和人类可以共同编辑白板

因此可以采用“代码描述 + 草图编辑”的协同方式：AI 生成受限 HTML/CSS，系统将其解析为可编辑的草图节点；用户在草图上修改后，系统再生成规范化 HTML/CSS，供 AI 继续读取和二次修改。

这里的“代码与草图一致”不是让 HTML 和草图各自保存一份独立状态，而是让两者共同表达同一个底层视觉文档。否则经过多轮“代码 → 草图 → 代码”后会出现节点重复、样式丢失、坐标漂移和修改互相覆盖。

## 二、目标

- AI 可以按受限 HTML/CSS 规范描述白板构图。
- 系统可将受限 HTML/CSS 确定性解析为以 `SketchSceneDocument` 为核心的唯一 `WhiteboardDocument`。
- 用户可以在现有 `SketchEditorSurface` 中手动编辑节点。
- 草图修改可以确定性地序列化为规范化 HTML/CSS。
- AI 可以读取规范化代码、结构化摘要和截图，继续执行节点级修改。
- 代码、草图和 PNG 使用同一套节点 ID、布局规则、配置绑定和图片资产引用。
- 不改变既有 `WhiteboardDocument + WhiteboardBinding + WhiteboardCommit` 的持久化与原子回填边界。

## 三、非目标

- 不支持任意 HTML、任意 CSS、JavaScript 或复杂响应式页面的无损双向转换。
- 不把配置图片白板改造成完整 Figma、OpenPencil 或网页编辑器。
- 不让 HTML 文本和草图 scene 同时成为独立的持久化权威数据。
- 不把生成代码直接写入正式页面 `prototype.html/css`，除非用户明确发起页面运行时转换。
- 不在一期引入新的 Rust/CanvasKit/Skia 编辑器或替换现有 `sketch-core`/`sketch-react`。

## 四、核心决策

### 4.1 统一底层视觉文档

采用单一持久化 envelope：直接升级既有 `WhiteboardDocument`，不再额外引入一个与其并列的 `WhiteboardVisualDocument`。`scene` 仍是唯一的几何与渲染权威；`nodeSemantics`、安全区和 `documentRevision` 是同一 document 的严格类型化字段，只表达 scene 本身没有的稳定语义，绝不保存第二套坐标或样式。

受限 HTML/CSS、语义 action 和人工编辑都必须先归一化为同一个 `WhiteboardDocument` 草稿，再交给持久化与 PNG 导出。节点删除、复制和分组等 scene 变更必须在同一个 reducer 中同步清理或生成 `nodeSemantics`，禁止宿主分别修改两份状态。

一期不实现自动布局。所有可编辑节点以 `scene` 的绝对几何定位；以后若确实需要横/纵向布局，再为它定义可验证的约束模型和确定性解算器，不能把浏览器 Flex/Grid 当作隐式真相。

```text
受限 HTML/CSS ──解析──▶ WhiteboardDocument 草稿 ──▶ scene → SVG / PNG
       ▲                         │                       ▲
       │                         │人工编辑 / 语义 action  │受管 assetRef 解析
       └────规范化序列化──────────┘                       │
                                                     render-time src
```

HTML/CSS 是 AI 友好的输入输出投影，草图是人工编辑界面，PNG 是最终配置值的渲染产物。HTML 不是白板的渲染器：预览与 PNG 继续只走 `sketch-core` / `sketch-react` 的渲染链路。两者都不能绕过底层 scene 直接互相覆盖。

### 4.2 转换器的包边界

受限 HTML/CSS 的解析器、白板语义 validator 和 action reducer 不放入 `sketch-core`。现有 `@workbench/shared` 已依赖 `@workbench/sketch-core`；若由 `sketch-core` 返回定义在 shared 中的白板模型，会形成反向依赖。新增无 React、无宿主 IO 的 `@workbench/whiteboard-core`：它依赖 `sketch-core`，拥有 bridge profile、转换器和白板 reducer；shared 只消费或再导出其跨包合同，author-site 与 agent-service 调用该纯函数包。

### 4.3 白板和正式页面运行时分开

配置图片白板只允许受限视觉代码桥接到白板 scene。正式 `prototype-html-css` 页面仍然以 `prototype.html/css` 为页面运行时权威；不要把白板代码同步机制扩展成所有页面运行时的双向编辑协议。

### 4.4 AI 使用语义动作，不直接生成底层节点

AI 可以生成代码作为初始导入，但进入白板后优先使用节点角色和语义动作进行修改。服务端负责节点 ID、坐标、文本测量、裁剪、安全区域、资产解析和 scene 校验。

### 4.5 同一套布局与渲染规则

受限代码解析、scene 编辑和 PNG 导出必须复用 `sketch-core` 的几何、校验和渲染规则。HTML 代码是序列化投影，不另行引入一套浏览器布局真相；这样可以保证结构和视觉效果在多轮转换后保持稳定。

## 五、数据模型

### 5.1 唯一持久化模型与版本

```text
WhiteboardDocument {
  id, version, documentRevision,
  scene, nodeSemantics, safeArea?, editorView, updatedAt
}
```

`documentRevision` 是白板 document 自身的单调乐观并发版本；`WhiteboardBinding.documentRevisionAtOutput` 表示其 PNG 对应的 document 版本（替换名称含混的 `sceneRevision`）；Authority 的 `workspaceRevision` 只用于 Workspace mutation。三者不得互相替代。

Commit 请求携带 `baseDocumentRevision`，服务端重新读取当前 document 与 binding 后比较，再自行构造 `documentRevision + 1`。成功响应返回新的 document、binding 与 Authority receipt；409 响应返回当前 revision 和用于恢复本地草稿的脱敏摘要。首次创建使用明确的 `baseDocumentRevision: null`，但仍须比较目标 binding 不存在。

### 5.2 节点稳定身份

受限 HTML 中每个可编辑元素必须带 `data-sketch-id`：

```html
<img data-sketch-id="hero-image" data-sketch-kind="image" data-sketch-role="subject" />
<h1 data-sketch-id="hero-title" data-sketch-kind="text" data-sketch-role="title">产品标题</h1>
```

scene 中使用相同的 `id`。序列化、重新解析和 AI patch 均以稳定 ID 定位节点，不能使用数组索引或文本内容作为身份。v1 输入严格要求 ID；缺失、重复或非法 ID 均为阻断错误。只有创建新节点的受控 action 可由服务端分配 ID，并在 action 结果中返回映射；解析器不得隐式分配，避免重试和诊断发生漂移。

### 5.3 代码桥接子集与编辑器 profile

HTML/CSS v1 只支持以下 bridge profile：

- `group`（仅作为不可见的层级分组；不等同 DOM frame）
- `rect`
- `ellipse`
- `image`
- `text`
- `button`

支持的基础属性包括绝对位置、宽高、层级、背景色、描边、圆角、透明度、字体大小/字重、文本对齐和图片 `cover/contain/fill`。`frame`、`section`、横/纵向自动布局都不是一期可编辑节点；它们如需出现在 HTML 投影中，只能是转换器生成的结构标记，不能引入新的可编辑布局语义。

该 profile 必须由 `whiteboard-core`、`SketchEditorSurface` 的白板配置、序列化器和 AI schema 共同使用。当前编辑器可创建的 `diamond`、`line`、`arrow`、`path`、`sticky`、`input`、`card` 不属于 v1：代码模式下不展示对应工具；遇到历史或外部导入的非 bridge 节点时，导入/导出均返回阻断 diagnostics，绝不静默丢弃。若产品必须保留这些工具，应先扩展 bridge grammar 与 round-trip 测试，而不是由 HTML serializer 特判。

`group` 是非渲染的关系索引，不是 DOM frame 或布局容器：其 children 与 z-order 分别遵守 scene 的既有校验和扁平 `zIndex` 规则；group 不得拥有 role 或 assetRef，DOM 嵌套不能改变坐标、裁剪或绘制顺序。

### 5.4 语义角色

角色写入 `WhiteboardDocument.nodeSemantics[nodeId].role`，并由 validator 保证节点存在、角色值合法；不得以任意 `metadata` 约定承载：

```text
background / subject / logo / decor / title / subtitle / label
```

角色用于 AI 修改和布局，不替代节点类型。例如 `role=subject` 仍然可以是 `image` 节点。

### 5.5 图片资产引用与解析

`nodeSemantics[nodeId].assetRef` 使用唯一的受管 `assetId`（注册表记录其 hash、MIME、尺寸和来源摘要）；`src` 只作为非身份的受管路径投影。由于现有 scene validator 与 renderer 仍要求 image node 具有非空 `src`，attached asset 时服务端必须以 resolver 填入稳定的本地受管 asset path，再在浏览器渲染时解析为已授权 URL：`assetRef → managed asset path（持久化 node.src）→ authorized render src`。持久化 document 不得以 base64、临时 URL 或模型 URL 作为长期身份。

资产生命周期严格分为 `candidate`（仅候选、不可放置）→ `localized`（受管但尚未引用）→ `attached`（写入 nodeSemantics.assetRef）→ `output`（PNG hash）。只有用户确认后 candidate 才可本地化；只有 attached asset 与输出 PNG 都进入 Commit 的引用和 GC 计算。draft 中的临时 render src 不参与 identity、round-trip 比较或 GC。

## 六、代码规范

### 6.1 允许的结构

```html
<main data-sketch-canvas="v1" data-width="1200" data-height="400">
  <img data-sketch-id="hero-image" data-sketch-kind="image" data-sketch-role="subject" />
  <h1 data-sketch-id="hero-title" data-sketch-kind="text" data-sketch-role="title">产品标题</h1>
</main>
```

只接受 `main[data-sketch-canvas="v1"]`、转换器拥有的固定标签和单节点 `[data-sketch-id="…"]` 选择器；所有位置均为 px 绝对值。CSS grammar 必须单独版本化，逐项列明：节点 kind、`left/top/width/height/z-index`、style 白名单、rotation、显式换行文本编码、group children 表达和 assetRef 占位符。标签名、class 名和格式不是 round-trip 不变量，序列化器统一输出 canonical tag 与属性顺序。

转换器不计算 class、继承、CSS cascade 或浏览器 layout。所有影响视觉的默认值只能由 `sketch-core` renderer 推导，或由导入归一化后显式写入 scene；serializer 不得复制一套默认值。v1 文本仅支持显式 `\n` 换行，不承诺按节点宽度自动换行；除非后续引入由编辑器、SVG 与 serializer 共用的字体度量、line-height 与 wrapping 协议。

bridge profile 还必须明确 `rotation`、`visible`、`locked`、`name`、`textStyleRuns` 与 bindings 的处理。未被 v1 支持的字段要么在输入时拒绝，要么不允许在代码模式编辑产生；不能在 round-trip 时悄然删除。

### 6.2 明确拒绝的能力

以下内容一期一律作为阻断错误；保留原草稿，不创建“只读外部节点”：

- JavaScript、事件处理器和动态 DOM；
- `position: fixed`、复杂 `sticky` 和滚动容器；
- CSS 动画、伪元素和复杂选择器；
- 任意 Flex/Grid、百分比/自动尺寸、媒体查询和未知字体度量；
- `filter`、混合模式、复杂渐变和不可移植阴影；
- 任意 SVG 内部编辑；
- 不能映射到 scene 节点的第三方组件、`@import`、自定义属性、任意 `url()` 与外部资源。

不支持的能力必须返回结构化 diagnostics（`code`、严重级别、HTML/CSS source range、节点 ID、修复建议），不能静默丢失。解析器还必须限制输入字节数、节点数、嵌套深度和 CSS token 数。

## 七、双向转换流程

### 7.1 代码导入草图

```text
AI 生成受限 HTML/CSS
  → HTML/CSS AST 解析（独立 parser，不使用浏览器 DOM）
  → 节点、受限样式、角色与 assetRef 归一化
  → bridge profile + WhiteboardDocument + SketchSceneDocument 校验
  → assetRef resolver 填入合法的受管 scene src 投影
  → 私有白板草稿
  → 用户确认或继续修改
```

导入阶段不直接覆盖现有白板。解析失败或存在不支持特性时，保留原草稿并展示定位到节点/属性的错误。

### 7.2 草图导出代码

```text
WhiteboardDocument
  → 按 bridge profile 的 canonical fields 稳定遍历
  → 生成带 data-sketch-id 的 HTML
  → 生成规范化 CSS
  → 输出代码摘要与 document revision
```

序列化输出应稳定排序、稳定缩进和稳定属性顺序，使 AI 读取时噪声最小，也便于 diff 和版本审计。排序必须确定义为唯一 z-order 和 node ID；若现有 scene 没有唯一整数 zIndex，则先由 canonicalizer 重编号。原始 HTML 的注释、class 命名和非语义格式不承诺保留。

round-trip 的等价式为 `parse(serialize(document)) === canonicalize(document)`，只比较 bridge profile 的 canonical fields：ID、节点类型、几何、z-order、白名单样式、显式换行文本、角色、assetRef 与 group children。render-time src、标签名、格式和未纳入 profile 的 scene 字段不属于不变量。

### 7.3 AI 二次修改

AI 上下文至少包含：

- 当前白板截图或选区截图；
- 规范化 HTML/CSS；
- 精简 scene 摘要；
- 节点 ID、角色、边界和资产引用；
- 当前 `documentRevision`；
- 目标图片尺寸、宽高规则和安全区域。

AI 修改应优先产生有版本的结构化 action，例如“将 `subject` 移到右侧并缩小 20%”，服务端经 `whiteboard-core` reducer 转换为 document mutation。每种 action 均需声明目标节点、允许字段、坐标系与精确参数；整份代码重写只用于新建或用户明确要求重构。AI 不直接提交 `Partial<SketchSceneNode>`：现有 scene update 为浅合并，嵌套 `style` 或 bindings 容易覆盖未涉及字段。

## 八、AI 接口建议

新增白板专用能力，不复用面向 `demos/<pageId>/sketch.scene.json` 的页面草图工具：

```text
readWhiteboardContext
importWhiteboardCode
planWhiteboardComposition
generateWhiteboardAsset
applyWhiteboardActions
serializeWhiteboardCode
```

建议的动作类型：

```text
generateAsset
placeAsset
addText
updateRole
align
distribute
setImageFit
removeNode
```

`bindConfig` 不属于 AI action：白板绑定的配置目标由打开 Dialog 的宿主确定，AI 无权改变。`generateAsset` 只生成待确认候选；`placeAsset` 只能引用已确认的受管资产。

本地草稿 action 只更新 dialog 内存，不产生持久写入。任何服务端 dry-run / 最终 `WhiteboardCommit` 必须携带 `baseDocumentRevision`；服务端原子比较 document revision、binding target guard 与 Workspace mutation 的 expected hash，成功后递增 document revision，失败则返回当前 revision 与可恢复草稿所需摘要。

## 九、与现有持久化边界的关系

```text
AI/人工操作
  → Whiteboard 草稿 scene
  → 代码/草图预览
  → PNG 导出与图片校验
  → WhiteboardCommit
  → document + binding + asset + config value 原子提交
```

代码投影不进入普通 assets，不进入 HTML sandbox，也不替代 `WhiteboardDocument`。提交失败时保留完整 document 草稿与临时资源，原配置不变，继续沿用现有冲突与 GC 规则。读取 API 必须区分“未绑定”（正常空结果）与“binding 存在但 document 损坏”（结构化服务端错误），不得将损坏 document 静默伪装为新白板。

live Workspace 必须通过一条 Authority mutation 写入 document、binding、attached assets、PNG 与 config value。非 live 路径若不能复用同一事务实现，则方案不得承诺原子性；实施时应使用临时文件/可恢复 journal 将它补齐。GC 同时检查 binding 的 output PNG、所有 document 的 attached assetRef 与配置值引用，避免把输入素材或可复用输出误删。

## 十一、验证方式

### 纯函数测试

- 受限 HTML 解析为预期 bridge 节点类型、ID、角色、样式和资产引用。
- `parse(serialize(document))` 与 canonical document 在 bridge canonical fields 上相等；assetRef 单独保持不变，render-time src 不参与身份比较。
- 属性顺序、节点顺序和 CSS 输出稳定。
- 非法 HTML、缺失/重复 ID、未知节点、非 bridge scene 字段、越界几何、外部资源、输入上限和不支持 CSS 返回带 source range 的结构化错误。
- 删除、复制、分组、asset 替换与角色修改会原子更新 nodeSemantics；字段级 action 不会覆盖既有 style 或 bindings。

### 编辑器测试

- 导入代码后可以在 `SketchEditorSurface` 中移动、缩放、改文案和换图。
- 人工修改后导出的规范化代码反映最新 scene，而不是旧导入文本。
- Studio 与 WhiteboardDialog 的编辑结果和 PNG 输出一致。
- 代码模式不提供非 bridge 工具；若 document 含非 bridge 节点，导出被阻断并显示可定位 diagnostics。

### AI 回归

- AI 能读取截图 + 规范化代码 + scene 摘要。
- “把主体移到右侧”“标题留出安全区域”“替换背景”等语义修改只产生目标节点 patch。
- base document revision 不匹配或配置目标冲突时拒绝覆盖并保留草稿。
- AI 生成图片候选未确认前不改变配置值。
- AI action 的坐标系、目标节点、允许字段与 dry-run 结果可审计；AI 无法构造或改变 binding target。

## 十二、风险与取舍

- HTML 仅是 scene 的投影，浏览器不参与白板 layout；字体栅格化仍可能造成 PNG 像素差异，因此固定测试字体并使用视觉容差，而不是承诺跨环境逐像素相同。
- v1 不承诺浏览器式自动换行、继承或 cascade；文本仅按显式换行渲染。若产品需要富文本、换行测量或复杂图形，应先扩展共享 scene/bridge 协议，不允许 serializer 私自补偿。
- bridge profile 是白板代码模式的能力上限，不等于所有 sketch-core 合法节点。限制编辑器工具的成本低于事后对每一种节点实现不可靠的 HTML 映射。
- `assetRef` 是持久身份，render-time src 是临时投影；二者不可混用。资产解析失败应阻断预览/提交但保留 draft，不能退化为持久化外链或 data URL。
- document revision、binding 输出版本与 Authority workspace revision 各司其职；不得因现有 `baseRevision: 0` 约定而省略 document CAS。
- 非 live 写入若不能提供与 Authority mutation 等价的恢复语义，就不能宣称全链路原子提交。
- 如果未来要求 Flex/Grid、响应式断点或任意 CSS，应将该内容升级为正式 `prototype-html-css`，不要扩大白板转换子集。
- AI 生成的代码可能包含格式噪声，因此应始终先 AST 解析和规范化，再进入 scene。
- 原始代码的注释和 class 名称可能在序列化后丢失；如果需要保留，应将其作为独立编辑来源，而不是要求 scene round-trip 无损。
- 图片生成、资产本地化和白板提交属于不同阶段，必须继续遵守现有 staging、权限、冲突和 GC 边界。

## 十三、当前结论

1. 当前白板不需要增强到 Figma 级别；受限代码与简单草图的组合更符合配置图片场景。
2. “代码和草图效果一致”可实现，但前提是唯一的 `WhiteboardDocument` 为权威数据，HTML/CSS 只是 canonical 投影；一期不支持自动布局、隐式换行和浏览器 cascade。
3. 白板专属转换器、语义 reducer 与 bridge profile 应放在新增的 `@workbench/whiteboard-core`，不能放进通用 `sketch-core`，以避免 shared/core 反向依赖并保持编辑器可复用。
4. v1 只保证 bridge profile 的 canonical fields round-trip；非 bridge 节点必须被编辑器限制或以 diagnostics 阻断，不能静默丢失。
5. assetRef 生命周期、document CAS、binding 输出版本、Authority mutation 与 non-live 恢复语义是第一阶段前置合同；完成它们后再接入 AI 语义 action。
