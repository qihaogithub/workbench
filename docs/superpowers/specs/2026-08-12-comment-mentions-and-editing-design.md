# 评论提及输入与编辑设计

## 背景与目标

评论创建与回复当前均使用原生 `textarea`：`@` 只在行首或空格后触发、候选列表不支持完整键盘选择，已选对象也只是普通文本。本次统一改善评论输入体验，并补足已发送评论的二次编辑和评论标记的可见性边界。

目标是让创作端和浏览端的创建评论、回复评论拥有一致的提及交互，同时保持既有评论正文和 `mentions` 数据契约不变。

## 方案

### 结构化提及输入器

以轻量 `contenteditable` 输入器替换 `MentionTextarea` 的原生 `textarea`。输入器将普通文本和提及标签作为两类节点维护：

- 任意位置输入 `@` 都开启候选筛选，不要求前方为空格；查询范围是光标前、从最近 `@` 起到光标的连续非空白文本。
- 候选列表始终默认高亮第一个匹配项；`ArrowDown`/`ArrowUp` 循环切换，`Enter` 或 `Tab` 选中，`Escape` 关闭。`Cmd/Ctrl+Enter` 保留给提交操作。
- 选择候选后插入不可编辑、带图标和身份色的提及标签，并在其后插入普通文本位置。光标只能处于标签前或后。
- 在标签相邻位置按 `Backspace` 或 `Delete`，整体删除标签并从 `mentions` 中移除对应对象；不会删除标签内部的单个字符。
- 输入器向消费方继续输出序列化后的 `content`（标签表示为 `@名称`）和 `CommentMention[]`；API、存储和已存在评论均无需迁移。

### 编辑已发送评论

主评论和回复都提供编辑入口。点击后以相同的结构化输入器载入原有正文和提及信息：

- 保存将提交新的 `content` 与 `mentions`，并由服务端更新对应线程或回复；取消不改变数据。
- 客户端适配器和外部受控回调增加线程、回复更新能力，`useComments` 与宿主 API 将结果合并到当前列表。
- 编辑权限沿用当前界面可操作范围；本次不引入新的身份/权限规则。

### 评论标记可见性

创作端右侧面板处于“评论”页签时才渲染预览区评论 pin；切换到其他页签立即隐藏。评论模式、评论数据和当前线程状态不因隐藏被清除。浏览端不具备该右侧页签，保留现有显示逻辑。

## 涉及边界

- `packages/demo-ui/src/comment/`：共享输入器、创建/回复/线程 UI、CommentLayer 数据回调与 pin 条件。
- `packages/shared/src/comment.ts`、评论 REST API、创作端与浏览端 API 适配器：仅新增编辑所需的输入/更新方法与路由调用。
- `packages/author-site/src/app/demo/[id]/edit/page.tsx`：将评论页签状态传给 CommentLayer，作为 pin 可见性条件。
- `docs/项目文档/创作端/12-意见反馈/`：同步评论的提及、编辑和标记显示规则。

## 错误处理与验证

- 无匹配候选时保留空状态；键盘选择不拦截正常文本输入。
- 失败的编辑保留编辑态与用户输入，并显示已有的操作错误提示。
- 为提及触发、键盘选择、标签整体删除、编辑保存/取消和 pin 页签可见性增加组件或行为测试；运行 `pnpm check:demo-ui`，并为 API 变更运行受影响的 author-site 验证。

## 非目标

- 不新增富文本格式、跨评论自动补全、多人实时协同编辑或数据迁移。
- 不改变评论的 AI 任务入队规则：只有最终 `mentions` 中包含 AI 时才触发既有流程。
