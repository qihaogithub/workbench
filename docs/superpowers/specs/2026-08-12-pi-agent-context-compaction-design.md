# Pi Agent 上下文自动压缩设计

## 目标

在不丢失近期对话连续性的前提下，避免 Pi Agent 的会话历史超过模型上下文窗口。用户应看到一条低干扰状态提示，知道较早的上下文已被整理。

## 范围

- agent-service 在每轮发送前预估会话上下文并按需压缩。
- 供应商仍返回上下文溢出时，最多执行一次压缩后的原请求重试。
- 模型配置提供真实上下文窗口与最大输出 token 的覆盖能力。
- 对话 UI 将压缩事件显示为非消息型系统状态。

不改变用户可见的完整聊天记录、会话编辑重发语义或模型供应商协议。

## 方案

### 压缩协调

Pi Agent 后端新增一个独立协调器。它在 Harness 空闲、即将调用 `prompt` 时读取当前分支消息，使用 Pi Core 的 token 估算逻辑和当前模型的窗口大小计算可用输入预算。

当预估用量跨越安全阈值时，协调器先调用 `harness.compact()`，再发送本轮消息。阈值为模型窗口减去最大输出、压缩预留和额外安全余量；不能把所有模型当成 128k 窗口。

压缩失败不清空会话，也不吞掉用户请求：发送会继续走既有链路，必要时由溢出兜底处理。

### 溢出兜底

如果供应商对本轮首次请求返回可识别的上下文溢出，后端在 Harness 已恢复空闲后尝试一次 `compact()`，并重发完全相同的请求。每轮最多重试一次，避免压缩失败或错误窗口配置产生循环调用。第二次溢出仍映射为现有 `CONTEXT_OVERFLOW`。

### 模型容量配置

模型管理器为自定义供应商模型接受 `contextWindow` 和 `maxTokens` 的可选配置值；缺省值保持现有兼容值。管理端的配置模型与同步契约将传递这些字段，当前运行中已创建的 agent 继续使用会话已选模型的容量设置。

### 用户提示与可观测性

每次真正完成压缩时，服务端发出专用 `context_compacted` 流式事件，包含压缩前 token 数与触发原因（预检或溢出恢复），不携带摘要内容。共享聊天 UI 把它渲染为一行居中的弱化系统状态：小图标、12px 左右文字、透明背景、无头像和无可编辑消息卡片。文案固定为：

> 已整理较早的对话内容，保留近期上下文

后端结构化日志记录会话、模型、预估 token、窗口、触发原因、压缩耗时及成功/失败，避免记录压缩摘要或原始用户内容。

## 错误处理

- 无可压缩历史时：跳过压缩，继续本轮请求。
- 压缩调用失败：记录 warning；预检路径继续发送，溢出恢复路径返回原始溢出。
- 模型容量缺失或无效：使用兼容默认值并记录配置诊断。
- 第二次溢出：保留现有不可重试 `CONTEXT_OVERFLOW` 响应及“新建对话继续”提示。

## 验证

- 协调器单测覆盖阈值判断、容量覆盖、无历史、压缩失败及单次重试限制。
- Pi Agent 后端单测验证压缩发生在 `prompt` 前，且重试内容与首次一致。
- 事件映射与共享聊天组件测试验证系统状态出现一次且不污染消息历史。
- 运行 agent-service 类型检查与针对性 Vitest 测试。
