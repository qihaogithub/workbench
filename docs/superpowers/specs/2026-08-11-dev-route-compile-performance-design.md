# 开发环境路由编译性能改造设计

**日期：** 2026-08-11  
**范围：** 本地 `pnpm dev` 的创作端首页与编辑页导航体验

## 背景

实测本地 Next 14 Webpack 开发服务器首次编译首页耗时 133 秒（2425 modules），首页后台截图请求随后编译动态截图 API 耗时 282.2 秒。该编译占用同一开发服务器，使编辑页路由排队等待。生产 Docker 已预构建所有路由，因此不受影响。

本地与 Docker 统一使用 Node 24 LTS。Node 20 已结束维护，不能作为长期开发基线；切换主版本后需要重建本机原生扩展，容器则在镜像构建阶段生成匹配产物。

## 目标

- 进入项目编辑页时，首页的可延后截图工作不抢占开发编译队列。
- 已编译的开发路由在常见导航周期内不被过早释放。
- 本地、Docker 与依赖构建使用同一 Node 24 主版本。
- 不改变生产环境截图生成、项目导航或编辑功能。

## 方案

### 1. Node 24 开发基线

`.nvmrc`、`package.json` engines 与所有服务 Dockerfile 统一声明 Node 24。切换 Node 主版本后，在本机重建原生扩展；Docker build 负责生成容器内匹配的原生产物。

### 2. 首页后台截图让路

首页的截图补生仅在用户持续停留于首页后启动；用户点击项目链接开始导航时取消尚未开始的补生。生产继续执行补生，但不让它与即时编辑导航竞争。开发环境使用更保守的空闲延迟，以优先完成当前路由编译。

截图缩略图元数据仍按卡片可见性读取。该项读取不改变，只在首页停留且卡片需要展示时发生。

### 3. 开发路由保活

在 `next.config.js` 配置 `onDemandEntries`，延长已编译路由的保留时间并提高并存路由数。它只调整开发服务器内存与重编译权衡，不进入生产构建。

## 不纳入本次范围

- 不切换 Turbopack。现有 `webpack()` 配置需要独立迁移验证。
- 不重构编辑页全部依赖图；此次先消除已实测的首页后台任务竞争。
- 不修改生产截图 API 契约或数据格式。

## 验证

1. 单元测试覆盖：导航触发时取消尚未启动的截图补生。
2. `corepack pnpm --filter @workbench/author-site typecheck` 与首页相关 Jest 测试通过。
3. 使用 Node 24 记录首页、截图 API、编辑页的冷/热访问时间；确认后台截图不再阻塞立即导航。

## 风险与回退

更长的开发路由保活会增加内存占用，取保守阈值；若本机内存压力显著，可下调配置值。截图补生仅延后或取消未开始工作，后续重新进入首页仍会恢复调度。所有改动均限开发体验，回退为移除对应启动校验、调度条件和 `onDemandEntries` 配置。
