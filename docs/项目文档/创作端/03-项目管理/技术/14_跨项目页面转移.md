# 跨项目页面转移 - 实现设计

> 版本：v1.0
>
> 更新日期：2026-09-11

## 一、架构边界

人工画布与 Agent 统一调用 PageTransfer API，author-site 只负责认证、HTTP 适配和项目文件适配；任务状态机、幂等、授权与 outbox 由 `project-core` 的 `PageTransferService` 管理；所有目标 Workspace 写入继续经过 Workspace Mutation Authority。

```text
Canvas / Agent
      │
      ▼
PageTransfer API
      │
      ▼
project-core PageTransferService ── SQLite/WAL
      │                              job / item / grant / head / outbox
      ├─ SourceSnapshotPort
      └─ TargetMutationPort ─────── Workspace Mutation Authority
                                      │
                                      └─ receipt 驱动前端刷新
```

公共契约位于 `@workbench/shared/page-transfer`，包括 request、job、item、conflict、manifest、reference grant/head 和 resolver 输出。`DemoPageMeta.reference` 以稳定 `grantId` 作为授权入口，同时保留源项目与终端源页面 ID 供服务端校验；调用方不能凭源 ID 直接读取目录。

## 二、prepare、execute 与恢复

`preparePageTransfer` 固定源 Workspace revision/root hash，为每个页面构建不可变 PagePackage，并预分配稳定目标页面 ID。构建器使用 Workspace Resource Registry 接受页面资源，author-site 适配器补充项目配置闭包、资产、白板、DesignSpec 和 visibility 规则。引用输入先解析到 active grant 的终端源页面，避免引用链。

`executePageTransfer` 以页面为原子单元：页面资源、必要配置、tree 条目和初始画布位置在一次 Authority mutation 中提交。每个 item 使用稳定 mutation ID；进程在提交后、状态写回前中断时，可通过 Authority receipt 查询恢复，不会重复写入。成功 item 保留，失败 item 可沿用同一 job 重试。

页面 item 完成后，拓扑 outbox 只为成功集合提交相对布局、完整容器和集合内导航。outbox 可幂等重放；拓扑失败不回滚已经完整提交的页面。

## 三、冲突与依赖策略

预检和执行均可返回结构化冲突：

- 目标项目配置定义或值不一致；
- routeKey 已被占用；
- visibility 或导航关系指向选择集合之外；
- 动态配置访问无法安全静态提取；
- 源版本漂移或目标 Workspace 并发变化；
- runtime 依赖缺失或目标策略不接受。

解决动作限定为 `reuse_target`、`replace_target`、`map_to_target` 和 `omit_relation`。字段映射只在结构化引用可以全部重写并重新验证时提交。React 编译始终使用目标 Preview Dependency Policy；编译接口不再产生后台“补锁”写入，`lockedDependencies` 不参与转移判断。

## 四、引用授权与编辑态解析

引用创建采用 pending grant → Authority 创建目标绑定 → active grant 的顺序。pending grant 不可解析；失败后由同一 job 重试或补偿。授权精确到源页面与目标引用页，创建者必须同时通过源、目标权限校验。

编辑态引用路由先校验目标会话、目标 `DemoPageMeta.reference` 绑定和 active grant，再从终端源页面构建 grant-scoped 页面包。响应只包含该页面闭包中的 runtime 文件和配置。sandbox 页面另外签发目标项目、目标页面和目标 Workspace 作用域的短期 ticket。

撤销把 grant 和 head 置为不可用；后续编辑解析、公开解析与 sandbox ticket 签发均 fail-closed。源项目或源页面缺失时 resolver 把 grant 标记为 `source_deleted`。

## 五、发布态 materialization

发布引用页时先创建并校验初始 materialization，发布清单只保存 `referenceId`、目标页面元数据和解析入口。Viewer 加载目标发布版本时逐页调用 published-reference resolver：

1. 校验目标发布清单包含该 grant，且 grant 仍 active。
2. 从终端源页面重新构建 grant-scoped 页面包，并按内容哈希生成 materialization。
3. 原子推进 ReferenceHead 后返回当前产物；目标页面名称、routeKey、排序和目录位置继续使用目标发布清单。
4. 新版本编译或校验失败时返回 `lastKnownGoodMaterializationId`，并将 head 标为 failed。
5. grant 撤销或源删除时拒绝读取，不允许 LKG 兜底。

当前 projector 是访问时触发的幂等 reconcile：编辑或 Viewer 的下一次解析会追平源页面最新已提交内容，因此无需重发目标项目；当前没有常驻的源提交事件消费者。SQLite outbox 与 head 已隔离持久化，后续可增加事件驱动 worker，而不改变 API、授权或物化模型。

`sandboxed-html` 的 HTML 与 meta 保存在私有 materialization 目录；公开 resolver 只签发目标作用域 execution ticket。其他 runtime 的公开产物按内容哈希寻址。

## 六、入口收敛

- 画布剪贴板 v2 只保存源项目、页面 ID、复制时版本与布局关系快照。
- Cmd/Ctrl+C/V、右键操作和复制/引用动作统一调用 prepare → execute。
- Agent `pages` capability 提供 `listTransferSourcePages`、`transferPages`、`getPageTransferStatus`、`resolvePageTransferConflicts` 和 `revokePageReference`。
- Agent 内部端点使用 author-site 绑定的用户和目标项目授权；工具返回 item receipt，`ToolHookManager` 按 receipt 的资源变化刷新 tree、页面、画布和配置。
- 原有携带源码的逐页前端复制和仅凭源 ID 读取引用的路由不再作为实现入口。

## 七、持久化与数据所有权

PageTransferStore 使用独立 SQLite/WAL 保存 job、item、grant、reference head 和 outbox。目标页面名称、routeKey、目录、画布、目标导航与评论属于目标项目；源更新只改变引用内容和运行依赖。评论、诊断、历史版本及集合外关系不进入 PagePackage。

任务和授权表是协调事实，Workspace Authority receipt 是目标文件已提交的事实；二者中断时以 receipt 恢复任务状态，不能绕过 Authority 直接修补工作区。

## 八、验证范围

- project-core：四 runtime PagePackage、资源 sidecar、部分成功、幂等重试、授权和拓扑 outbox。
- author-site：引用投影、最近可用版本、撤销/删除 fail-closed、编辑态 sandbox ticket。
- agent-service：五个页面转移工具、服务端授权和 receipt 透传。
- demo-ui：剪贴板不携带源码及人工入口的页面身份/布局传递。
- viewer-site：发布引用 hydration 与目标作用域 sandbox 执行。
