# 对话账本与恢复

> 更新日期：2026-09-11

## 责任边界

`author-site` 是对话业务数据的唯一写入者，通过 `ConversationRepository` 管理 `data/conversations/conversation.db`。创作端 UI 恢复、导出、删除和 Agent 上下文重建都以该账本为权威来源。`agent-service` 的 Harness、checkpoint 和 JSONL run log 都是可丢弃缓存或诊断数据，不得反向覆盖账本。

编辑 Session 与 conversation 目前共用稳定 ID，但语义分离：Session 管理编辑租约与 Workspace 绑定，conversation 管理用户消息、assistant 终态和 run。项目共享 Workspace 不使对话共享；所有外部接口以当前用户作为 owner 查询条件。

## 提交与运行顺序

1. 浏览器先把未确认的单条用户命令放入 IndexedDB outbox，并等待 IndexedDB 事务真正提交；可重试网络/服务错误最多尝试 3 次并指数退避，耗尽后保留命令，确定不可重试的 4xx 则移除无效命令。后续页面恢复并重放旧命令时，幂等取得 ACK 后立即取消尚未交给 Agent 的 queued run；取消确认失败则继续保留 outbox 项，避免留下无终态运行或静默执行过期指令。
2. `POST /api/conversations/:id/messages` 以 `clientMessageId` 幂等受理，由服务端分配 `sequence` 并返回 `messageId/runId/assistantMessageId/conversationRevision`。只有收到 ACK 后才能发起 WebSocket 运行；ACK 前 UI 标记“正在同步”，失败后标记“同步失败”，成功后用服务端 message ID 替换临时 ID，确保后续编辑、重试和删除锚点引用权威记录。
3. Agent Service 通过内部令牌调用 run start，在运行身份、owner 和 project 全部匹配后取得最近有效的版本化上下文摘要和未覆盖的 `historyBeforeRun`。新建或被失效的 Harness 按“官方压缩摘要→摘要尾部消息→账本未覆盖消息”的顺序恢复，不信任浏览器回传历史。
4. Agent 完成、失败或取消后，Agent Service 先幂等提交 run 终态，收到账本 ACK 后才向 UI 发送 `finish/error`。`ready` 只是连接/会话状态，不是终态信号。
5. 进程启动后用启动时间作为 cutoff，将遗留的 queued/running run 收敛为 `interrupted`。

取消语义是保留已 ACK 的 user message 和 `cancelled` run，不创建 assistant 取消占位。尚未交给 Agent 的 queued run 可在账本事务内直接进入 `cancelled`；已经 running 的 run 先记录持久取消意图，再由 Agent 终态或重启协调器收敛。同一终态 payload 重放返回同一 ACK；相同 run 改写为另一终态时返回冲突。

如果消息已 ACK、但 WebSocket 建连或发送失败，客户端会对该 run 发起三次有界取消请求；账本把尚未启动的 queued run 直接收敛为 `cancelled`。用户对同步失败消息重新操作时会走新的单条命令；对已 ACK 的失败轮次重试时，账本先把同一 user message 上遗留的非终态 run 标为 `interrupted`，再创建新 run，避免一条用户消息积累永久 queued 状态。

编辑重发、重新生成和历史回滚不再向 Agent WebSocket 发送浏览器消息数组。客户端先读取当前 conversation revision，再以 `supersede` 将锚点后的记录作废；重新生成随后以 `retry` 为同一条 user message 创建新 run，编辑重发则提交新的单条消息命令。revision 冲突或请求失败时不截断本地列表，避免本地状态假装已覆盖权威账本。checkpoint 通过 conversation revision 自动失效，无需独立的历史重同步协议。

每次单条消息持久化记录 `ai.message_persist_succeeded` 或 `ai.message_persist_failed`。事件只保留 request/operation ID、conversation/session ID、client/server revision、HTTP 状态、负载字节数和耗时，不保留消息正文。诊断库的完整性和损坏恢复语义见[创作端诊断事件系统](../../11-诊断与日志/技术/01_创作端诊断事件系统.md)。

## 存储与治理

SQLite 使用 WAL、foreign keys、`busy_timeout=5000` 和 `synchronous=FULL`，启动打开时执行 `quick_check`。数据库不可用时新命令 fail closed，不使用 JSONL 作业务 fallback。在线备份通过 SQLite backup API 产生，轮换窗口默认 7 份且最多 30 份。

对话在最后活动 30 天后硬删除，手动删除使用同一语义。删除账本数据不删除共享 live Workspace。旧 `.messages.json` 整份快照函数和浏览器历史重同步协议已删除；兼容 POST 路由固定返回 410，不再写文件。

`display_parts_json` 只保留最多 64 KiB 的 UI 展示摘要，会递归移除工具结果、参数、prompt/reply、密钥、token、cookie 和 data URL。净化后的展示数据超过 64 KiB 时，改存最多 512 KiB 的 owner-scoped `run_artifacts`，消息只保留 artifact ID、类型、大小和 SHA-256；产物按 30 天 TTL 失效，随对话删除级联清理。不存原始工具参数或结果。

独立的结构化运行轨迹只保存模型阶段、工具或子 Agent 名称与状态、耗时、错误码、上下文恢复/压缩和能力加载状态，以及 Workspace 相对路径上的创建、修改、删除动作。它不复用 JSONL run log，也不接收 prompt、思考或流式正文、工具参数与结果、文件正文、附件正文、token、Cookie、密钥和 data URL。单次 run 最多保留 500 个事件和 256 KiB；超限时保留首尾并写入截断标记。正常终态的轨迹与 run 终态在同一事务提交，终态哈希包含规范化轨迹以保证重试幂等；进程硬中断只能由协调器标记状态，管理页明确提示部分轨迹不可恢复。

聊天附件物理目录的 manifest 固化 `ownerUserId` 和 `conversationId`，只在该范围内按 SHA-256 去重。客户端把 `attachmentIds` 与未 ACK 消息一起保存到 IndexedDB outbox，但 outbox 的 `displayParts` 由 `buildLedgerAttachmentParts` 构造，图片也只保存附件 ID/名称/MIME/大小/提取状态，不复制实时气泡使用的 base64/data URL。消息路由校验物理 manifest 归属后，在同一 SQLite 事务中写入 attachment/message/run/outbox。项目「聊天文件」只投影当前 owner 未删除对话的附件；无归属字段、他人或已删除对话的附件 fail closed。手动删除会标记 attachment 引用，对话手动删除和保留期清理均会清理该 owner/conversation 的物理目录。

`context_summaries` 只保留每个 conversation 最新有效版本，记录 schema/version、来源 revision、覆盖 sequence、有界摘要、尾部消息和内容哈希。读取时验证版本、边界和哈希；编辑重发/supersede 会使摘要失效。摘要正文不下发浏览器、不写运行日志或产品分析库。

默认分析开关为关；显式启用时，outbox projector 只把事件白名单、版本、时间和去标识化 conversation key 写入独立 `analytics.db`，不写原始 prompt、reply、文件正文或可逆用户标识。

## 接口与运维入口

- 外部：`/api/conversations`、`/api/conversations/:id/messages`、`title`、`retry`、`supersede`、`export`、`artifacts/:artifactId`、`DELETE /api/conversations/:id`。
- 内部：`/api/internal/conversations/:id/runs/:runId/start|terminal` 和 `/api/internal/conversations/runs/reconcile-interrupted`；使用共享 `INTERNAL_API_TOKEN` 的 `X-Internal-Token` header。
- 管理员可靠性：`/admin/conversation-reliability` 和 `/api/admin/conversation-reliability` 展示最近 24 小时的消息持久化成功率/延迟、Agent 上下文恢复成功率，以及当前账本的 run 终态完整率、超时未终态数、outbox 和诊断 gap。终态完整率仅以已终态 run 和超过 15 分钟仍未终态的 run 为到期样本，不把正常运行中请求计为失败。看板只查询聚合元数据，不读取对话正文。
- 管理员对话查看：`/admin/conversations` 通过同一 Admin Secret 读取所有未删除对话，按项目、人员和 `updated_at` 半开时间区间筛选，并使用 `(updated_at,id)` 游标分页；详情接口返回消息、run 和结构化轨迹。所有页面与接口只读并强制 `no-store`。项目名称从项目领域服务读取，已删除项目回退为稳定 ID；普通对话接口仍按 owner 隔离。
- 旧数据盘点：`corepack pnpm inventory:legacy-conversations -- --data-dir data`。该命令统计 Session/消息快照，以及附件目录数、manifest 可解析性、owner/conversation 归属完整性、ID 匹配、物理字节数和旧消息中的附件 ID 引用。引用分析只输出可唯一映射、歧义、缺少物理文件与无引用附件的计数，不输出 ID 或文件名。命令不输出对话或附件正文，也不执行导入、归档或删除。
- 旧数据可恢复归档：`corepack pnpm archive:legacy-conversations -- --data-dir data --archive-id <id>` 默认只输出文件数、字节数和目标目录，不创建文件。只有业务明确选择归档后才允许追加 `--apply`；apply 仅复制 `.session.json/.messages.json` 和 `.ai-attachments`，不复制 Session workspace 或其他资源，逐文件校验 SHA-256，写入 manifest 后原子更名目标目录。该命令永不删除源数据；源数据清理必须在归档校验后另行明确批准。
- 归档独立验证：apply 后必须运行 `corepack pnpm verify:legacy-conversation-archive -- --data-dir data --archive-id <id>`。验证器重新读取 manifest，拒绝路径逃逸、重复路径、符号链接和未声明文件，逐文件核对大小与 SHA-256。只有返回 `verified: true` 后才能进入源数据清理批准；该验证命令只读。
