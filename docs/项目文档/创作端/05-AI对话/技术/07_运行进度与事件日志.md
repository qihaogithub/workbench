# 运行进度与事件日志

> 更新日期：2026-09-06

本文描述 AI 对话在一次运行中的事件可视化和后端日志保存机制。业务侧需求见 [AI 对话需求文档](../AI对话_需求文档.md)。

## 设计目标

AI 运行过程可能包含模型输出、工具调用、子 Agent 委派和文件变更。第一版不推断百分比进度，也不显示等待秒数，只展示真实事件带来的反馈。

对普通创作用户，聊天区只需要知道 AI 正在处理，避免在长任务中反复看到“模型响应”“子 Agent 运行中”等容易误解的内部状态。具体产物仍由右侧预览区、页面列表和文件变更反馈承载。

对排查问题的开发者，后端需要保存本轮运行的事件日志，便于定位空回复、工具结果丢失、子 Agent 无结果和文件变更遗漏。

## 事件流转

agent-service 的 WebSocket 路由在收到用户消息后，为本轮消息创建运行日志，并把后端事件统一交给事件路由器。

事件路由器负责两件事：

- 继续向前端透传必要的实时事件，保证既有流式响应、工具展示和权限确认可用。
- 将后端 JSONL 日志加入 run 内有序异步队列，保留模型、工具、子 Agent、文件和系统状态的关键事件，不阻塞 WebSocket 事件转发。

WebSocket 消息不会把“长时间没有新 token 或工具事件”直接判定为 Agent 死亡。普通模型执行阶段使用无进展和绝对执行计时保护；计划审批则转换为 `awaiting_approval`，暂停这两类执行计时，并由权限管理器独立的 10 分钟审批期限约束。审批工具发出终态更新后，Agent 恢复 `processing` 并继续消耗剩余执行预算。这样人工决策时间不会被误报为 `MESSAGE_TIMEOUT`，同时等待不会无限延长。

同一个 Agent 会话只允许一个 Pi Agent harness 运行。WebSocket 和 HTTP 发送入口都需要在启动新 run 前检查后端 busy 状态；若上一轮仍在运行，不再调用 `harness.prompt`，而是记录一条 `AGENT_BUSY` 失败日志并向前端返回可重试错误。该错误不表示模型切换失败，也不表示网络断连；它表示当前会话仍被上一轮占用，前端应提示等待完成或先取消。

Pi Agent 事件映射需要保留工具入参、工具结果、details、错误和耗时。底层工具执行以 `tool_execution_start` 和 `tool_execution_end` 表示，后端需要把它们映射为应用层 `tool_call` 和 `tool_call_update`。`delegateTask` 这类子 Agent 工具不应只传状态，否则前端详情弹窗和后端日志都无法还原任务入参、输出摘要、文件变更与失败原因。

当会话历史接近模型上下文窗口时，Pi Agent 在下一条用户消息发送前先估算现有历史与待发送内容。可用输入预算会扣除模型最大输出、Pi Core 压缩摘要预留和额外安全余量；达到阈值后，后端在 Harness 空闲时压缩较早历史并保留近期消息。供应商仍返回上下文溢出时，后端最多执行一次“压缩后重发原请求”的恢复流程；第二次溢出仍作为 `CONTEXT_OVERFLOW` 返回，绝不无限重试。自定义供应商可在模型配置中声明实际 `contextWindow` 与 `maxTokens`，未声明时使用兼容默认值。

文件变更不再通过 legacy `file_operation` 作为实时刷新、日志或持久化成功依据。该事件不属于当前 agent-client / WebSocket stream contract，agent-service 也不再路由或写入该事件。Pi Agent 工具链仍会汇总本轮文件结果，供 finish 摘要、运行日志和开发排查使用；live Workspace 的实际写入成功以 Workspace Authority receipt 和 `workspace_mutation_committed` 为准。前端 chat stream 不监听 `file_operation`，也不维护由该事件驱动的实时文件缓冲；如果需要展示“本轮改了哪些文件”，应读取运行结果中的 `finish.files`、运行日志文件摘要或 receipt 派生资源列表。

## 前端展示

聊天区在一次请求刚开始、尚未出现思考过程、工具调用或文本输出时，使用靠左的紧凑 5x5 点阵循环动效作为空窗期兜底提示，只表达“AI 正在处理”。当界面开始出现思考、工具调用或正文输出后，点阵动效收进 assistant 消息底部的操作栏，与复制等操作按钮处在同一控制区；流式输出期间该操作栏保持可见，避免运行反馈被正文增长挤出用户视野。界面不显示额外文字标签，但保留无障碍状态语义；它不是任务列表，也不承担进度估算。

完成上下文压缩后，服务端额外推送 `context_compacted` 事件。共享聊天组件把它显示成居中的低对比度状态行“已整理较早的对话内容，保留近期上下文”，不使用头像或消息气泡，也不写入可编辑或持久化的聊天历史。该提示仅说明上下文整理已经完成，不展示摘要内容、原始 prompt 或 token 细节。

当本轮产生 Workspace Mutation Authority receipt 时，服务端会在终态前推送 `run_summary`，其中只包含 mutation 的 ID、版本、提交状态、资源路径/动作，以及 projection 的版本、surface 和状态。若查询时 ack 尚未到达，服务端会为对应 revision 保留 `pending` 投影状态；相同摘要也保留在 `finish.metadata.runSummary`，供断续的流式消费方以终态消息兜底，不携带工具原始输出、附件内容或凭证。共享流服务把摘要附入本轮 assistant 消息：已提交的 mutation 显示“已提交 N 项修改”，投影失败显示失败数量，投影仍未确认则显示“预览待验证”。创作端 Authority 轮询使用独立的 projection revision 游标，收到晚到 ack 后通过受限的浏览器事件按 project/session/revision 更新已归档消息并再次持久化；没有 receipt 时不显示该状态，UI 不能仅凭文本回复宣称验证成功。

历史执行过程仍可在 assistant 消息内折叠查看，用于展示思考、普通工具调用和子 Agent 摘要。子 Agent 条目可以打开详情弹窗，查看委派任务、补充上下文、输出摘要、文件变更、失败原因和原始事件详情。

前端不展示会话日志入口。日志是开发排查能力，不是普通用户界面的一部分。

## 后端日志

运行日志默认保存在数据目录下：

`data/agent-run-logs/<sessionId>/<messageId>.jsonl`

这些运行日志属于开发排查数据，由 agent-service 启动时及每 30 分钟执行的保留任务只保留最近 3 天；同一任务也清理 `data/editor-diagnostics/agent-service.jsonl`。该策略不触碰项目工作区、素材、会话恢复数据或截图等用户项目数据。日志写入和定期清理都不阻塞对话主链路，清理失败只记录服务端 warning。

每条日志是一行 JSON，包含时间、级别、来源、事件类型、标题、摘要、关联工具调用 ID 和脱敏后的 payload。run 内队列以短窗口合并写入，分别批量追加运行 JSONL 与结构化诊断 JSONL，写入顺序保持与事件顺序一致。

`finish.payload.metrics` 保存可比较的阶段指标，不保存 prompt、图片正文或完整工具结果：`runDurationMs` / `finishMs`，首个 thought/tool/text 的相对耗时，thought 事件数与字符数，tool call/result 数，工具耗时总和与并行区间并集耗时，能力激活次数与耗时，`mutationCommitted`、`runtimeValidationOk`、`projectionStatus`，以及完整模型 ID 和可解析的 provider ID。`projectionStatus` 只有 `applied` 或 `failed` 来自真实 ack，其余为 `not_verified`；这些指标用于后续回放和代表性任务评估，当前不作为硬预算或自动终止条件。

工具开始/结束、权限、错误、取消和完成等关键事件会立即触发异步 flush；`thought` 和状态等可重建增量会在 25ms 窗口内合并。队列默认最多保留 256 条待写事件；满载时优先舍弃旧的可重建增量，绝不舍弃关键事件。run 完成、取消后的收尾或连接销毁会先 `drain()` 队列，再释放该 run 的日志引用。日志写入失败不应中断用户对话，只记录服务端 warning。

上下文压缩成功会写入 `context_compacted` 事件，保留触发原因、压缩前 token 数、模型窗口和耗时；不写入摘要正文或用户消息。压缩失败以 warning 记录并继续原有发送链路。

日志 payload 会对 key、token、authorization、password、secret 等敏感字段做脱敏；长文本会截断，避免把完整大段内容写入排查日志。

同时，agent-service 会把本轮运行的关键边界事件通过同一异步队列写入创作端结构化诊断事件流，供 [诊断与日志模块](../../11-诊断与日志/) 的 SQLite/JSONL 查询入口串联。同步事件只保存运行 ID、工具名、状态、耗时、文件路径摘要、数量和错误摘要；完整 prompt、模型正文、工具入参和工具结果仍只存在受控的 AI run log 中。

每轮结束时必须记录 finish 摘要，包括：

- 最终回复内容长度。
- 累计流式输出长度。
- 工具结果数量。
- 子 Agent 结果数量。
- 文件结果数量。
- Authority receipt 中的资源数量或资源路径摘要。
- 后端返回的错误或空回复调试信息。
- 运行阶段指标（首个 thought/tool/text、总耗时、工具并行区间、能力激活、Authority/validation/projection 状态和模型/provider 标识）。

当模型成功返回但最终回复为空时，finish 日志使用 warning 级别，并保留后端提取到的响应结构摘要，便于判断是模型真实无输出、响应结构变化，还是文本提取逻辑遗漏。

如果 Pi Agent 返回的 assistant message 带有错误摘要，例如供应商错误或模型调用失败，后端必须把本轮结果转成失败事件，而不是作为空内容的成功响应继续传给前端。这样用户看到的是明确错误，日志中的 finish 也能保留错误摘要和响应结构。

Pi Agent 发送链路捕获到底层异常时，服务端错误日志必须记录标准化后的错误字段，而不是直接依赖运行时对象的默认 JSON 序列化。标准化信息至少保留错误名称、消息、状态码、堆栈和最近一次 assistant response 结构摘要；对于 SDK 抛出的非标准对象，也要尽量提取 `message`、`error.message`、`status` 和 `statusCode`。这保证运行日志里不会只出现空对象，排查模型供应商、网络或响应结构问题时能直接看到可行动的失败原因。

如果运行失败时前端已经收到部分 assistant 正文、思考过程或工具调用，前端应把错误说明合并进当前 assistant 消息并固化该消息；只有在本轮完全没有可见内容时才单独追加错误气泡。这样导出记录和聊天区不会同时出现一条超时错误消息和另一条同轮半截 assistant 消息。

流服务在连接尚未建立时收到服务端错误，只交付一次包含服务端错误码和消息的终态错误回调。它不会再额外触发泛化的“连接错误”回调，因为上层对两种回调都会创建聊天消息，双发会造成重复错误气泡。断连重连超时仍使用单独的 `TRANSPORT_DISCONNECTED` 终态错误。

取消采用两阶段收束：收到用户取消、无进展超时或绝对超时时，Agent 先进入 `cancelling`，继续持有当前 Harness 的 busy 所有权并请求底层 abort。只有 `sendMessage` 对 abort 的成功或失败实际收束后，才转为 `ready` 并返回 `CANCELLED` 或 `MESSAGE_TIMEOUT`。在 `cancelling` 期间，新消息统一得到可重试的 `AGENT_BUSY`，不能并发重入同一个 Harness。WebSocket 的 `cancel` 指令只发送 `cancelling` 状态，不再提前发送 `ready`。

计划审批的拒绝、取消和超时属于审批工具自身的终态：服务端必须先发出对应的 `tool_call_update`，前端据此固化工具卡，再继续或收束本轮。运行日志记录该工具终态及原因；不得把正常审批等待直接改写为通用模型超时。

编辑重发的会话重同步可由 `PI_AGENT_CANONICAL_CHECKPOINTS_ENABLED=true` 灰度开启。开启后服务端在内存中为每个 live session 保存最近的真实 user/assistant 轮次、消息 ID 与单调版本号；单条正文最多 4,000 字符，最多 24 条且总量最多 48KB。客户端提交已知版本与截断后的最后消息 ID，服务端只从 canonical checkpoint 截取并重建 Harness；版本或锚点不一致返回明确错误，不会用前端全量历史静默覆盖。没有服务端 checkpoint 的首个灰度请求才可用经过角色、非空内容与预算校验的历史 seed。该机制不保存图片 base64、密钥或工具原始输出，也不跨 agent-service 进程重启持久化；Pi 压缩摘要、附件索引和持久化恢复尚未纳入当前承诺。

## 兼容性

`tool_call` 和 `tool_call_update` 在保留旧字段的基础上扩展参数、结果、详情和耗时字段。旧消费者仍可只读取原有状态字段；新消费者可以按需读取更完整的事件 payload。
