# 10 评论批注机制

评论批注的产品规则见[预览系统需求](../预览系统_需求文档.md)中的页面批注部分。本文件说明双端如何复用同一套输入、存储和展示机制。

## 输入与提及

共享评论输入器把普通文字与提及标签放在同一个可编辑区域。标签是不可拆分的结构化对象，显示为带身份色的短标签；删除键落在标签边缘时会移除整个对象，并同步清理提及列表。

输入器从光标向前寻找最近的 `@`，不要求它前方有空格。候选列表在打开时固定首项为活动项，方向键切换、回车或 Tab 确认、Escape 关闭。最终提交时，标签会被还原为正文中的 `@名称`，并与独立的 `mentions` 列表一同提交，因此已存评论和评论展示仍可使用同一份数据契约。

普通用户提及的 `CommentMention.id` 是当前项目的随机 `participantId`，不是本地用户 ID 或钉钉 `userId`。参与者只在钉钉绑定用户进入创作端编辑页，或以创作端身份写入评论时登记；服务端按项目重新解析 ID 并覆盖展示名，拒绝跨项目、失效或伪造目标。创作端候选搜索返回最近参与者，单次最多 20 人；浏览端候选搜索要求项目已发布、至少输入一个字符，单次最多 10 人，并只返回安全展示投影。共享编辑器通过评论适配器异步搜索候选，约 180ms 防抖并取消过期请求；加载、限流和错误状态不会改变既有 `@AI` 候选。

页面评论、回复和新建评论共用 `CommentComposer`；配置批注继续使用保留自动保存语义的 `CommentMarkdownEditor`，但复用同一套深色 token、头像、操作色与项目图片上传回调。Composer 未获得焦点且没有草稿时采用 Figma 风格的紧凑单行输入框，只显示占位文本和灰色发送按钮；获得焦点、存在草稿或上传/错误状态时展开为深色多行编辑区，显示蓝色 focus ring、表情、`@` 提及和图片工具。上传期间按钮进入进行中状态，失败通过 `role=alert` 告知并保留正文；成功后只插入受控 Markdown 图片语法。发送按钮和 Cmd/Ctrl+Enter 共用同一提交回调，空正文或提交中的编辑器不可提交。新建评论浮窗只保留输入器发送按钮，底部不再重复渲染“取消/评论”操作区；右上角关闭按钮负责放弃草稿。

评论图钉按主评论作者及去重后的回复作者生成头像堆叠，最多显示三枚并以 `+N` 表示其余参与者。图钉 hover 或键盘 focus 时显示最近活动作者、时间与正文摘要；已解决线程改为灰化完成样式，按钮 `aria-label` 同时描述状态与参与人数。

## 编辑与同步

主评论和回复都可进入编辑态，默认先使用 `renderNoteMarkdown` 只读渲染；页面线程点击编辑图标后复用 `CommentComposer`，配置批注继续使用保留自动保存语义的 `CommentMarkdownEditor`，将修改后的 Markdown 正文与提及列表提交给各自更新接口。页面线程编辑时，“取消/保存”按钮位于 Composer 工具栏右侧并替换圆形发送按钮，不再额外渲染底部操作区。主评论与回复输入区之间不渲染额外的外层分割线，仅保留 Composer 内部正文与工具栏的结构分隔。主评论输入停止 800ms 后自动保存，失焦、切换字段或关闭气泡前 flush；空正文恢复最近一次已保存内容，不调用空内容接口。回复编辑不自动保存，通过发送/确认图标或 Cmd/Ctrl+Enter 显式提交。服务端先按既有作者权限验证，再原子更新对应对象及线程更新时间；匿名用户提交的普通用户提及还要经过项目参与者校验和匿名通知限流。

更新完成后服务端广播完整线程更新事件，订阅方以该线程替换本地副本，避免主评论和回复的局部更新产生不一致。编辑中首次加入 AI 提及会沿用创建评论时的入队规则；移除提及不会回滚已经开始的 AI 任务。

### 权限与图片资源

服务端把内容编辑和删除作为独立权限边界：主评论只能由主评论作者操作，回复只能由对应回复作者操作；匿名身份以 `anonymousId` 作为作者 ID，不能借助登录角色或同时提交 `resolved` 字段绕过校验。匿名用户可以提及当前项目参与者，但单次最多 5 人且通知受独立限流；解决/恢复保留原有协作权限语义。评论图片上传复用现有图片存储的格式和 10MB 限制，写入时登记项目引用，登录请求使用 Cookie 或 `X-Auth-Token`，匿名请求必须携带匿名身份与显示名。

两个宿主适配器都实现 `CommentApiAdapter.uploadCommentImage(file)`：创作端发送同源 Cookie，浏览端带 token 或匿名身份。返回值只包含 canonical `/api/images/:id` 地址和文件元数据；展示端传入 `mediaBaseUrl` 后再解析该地址。`renderNoteMarkdown`/`sanitizeNoteHtml` 在客户端和 SSR 都拒绝 data、blob、协议相对及非受信任媒体地址，避免把原始 data URL 或外链直接注入评论 DOM。

### 钉钉工作通知投影

评论和回复先写入评论存储，再为每个普通用户提及建立独立通知意图。通知 outbox、发送尝试和限流事件保存在 author-site 的 SQLite 中；评论正文不保存钉钉任务号等发送细节，API 与 WebSocket 只投影 `CommentDeliverySummary` 的状态和计数。状态为 `pending`、`submitted`、`failed` 或 `suppressed`，其中 `submitted` 只表示钉钉已接受异步任务。编辑时以旧、新 `participantId` 集合求差，只发送新增提及；移除提及、解决或删除不会产生新通知，删除评论/回复会清理未完成任务。

发送器复用钉钉企业 access-token 缓存，使用应用 AgentId 向收件人发送异步工作通知，并记录 taskId 后按有限间隔查询结果。公开 HTTPS viewer 基址和当前发布快照均能定位目标时使用 ActionCard；未发布、目标不在当前快照或基址不安全时降级为无按钮 Markdown。正文先转纯文本、转义并截断，匿名作者统一显示为“未登录访客”。创作端作者可对失败项发起重试，匿名访客不能手工重试。

匿名通知在写入成功后独立限流：单次最多 5 位收件人，并按 IP+项目、匿名身份+项目、收件人+项目及项目总量分别统计窗口；缺少可信代理 IP 或限流密钥时 fail-closed，将通知标记为 `suppressed` 而不回滚评论。候选搜索另有 IP+项目频控，连续钉钉发送失败会触发全局短时熔断。限流摘要不向客户端暴露 IP、userId、taskId 或原始错误。

## 配置项批注面板交互

配置项批注由 `ConfigCommentPopover` 托管，顶部标题与关闭按钮沿用规范气泡的 portal、箭头、定位和响应式回退；中部线程列表独立滚动，底部新增批注编辑器固定显示。主批注、回复及已解决线程都按最新创建时间倒序展示，正文和回复统一通过 `renderNoteMarkdown`/`sanitizeNoteHtml` 安全渲染。

创作端的回复、编辑、完成/恢复、删除均是带 `aria-label` 与 `title` 的 Lucide 图标按钮，始终可发现；主批注编辑失焦后回到只读态，失败时保留编辑态并提供图标化重试。编辑按钮在 `pointerdown` 阶段阻止抢焦点，`CommentMarkdownEditor` 会等待编辑器挂载和自动聚焦完成，并在下一帧复核 `relatedTarget` 与 `document.activeElement`；只有焦点真正离开编辑区域才触发自动保存退出，组件卸载时取消待处理检查。新增批注仅保留本地草稿，输入框默认一行并自动增高，失焦或 Cmd/Ctrl+Enter 创建线程，成功后清空草稿；浏览端仅显示 Markdown、作者、时间、回复和解决状态，不渲染任何写入控件。`CommentMarkdownEditor` 关闭固定 TopBar、保留选区浮动 Toolbar、@提及候选和结构化 `mentions` 回传。

配置批注的线程卡片与页面浮窗共用深色 token、头像颜色、菜单和上传编辑器。编辑/删除入口仅在当前操作者与目标作者 ID 完全一致时渲染，主批注和回复分别判断；删除通过自定义 `role=alertdialog`、遮罩、Esc 关闭和焦点回收完成，不再调用浏览器原生确认框。菜单不再提供“复制链接”，解决菜单项根据线程状态切换“标记为已解决/标记为未读”，后者仍调用同一恢复接口。页面线程的“更多”菜单通过 `document.body` portal 以固定定位渲染，脱离正文滚动容器的裁切；根据触发按钮和视口空间自动选择上下方位置，并保持在评论浮窗及输入区之上。

编辑入口的失焦保护不能替代底层编辑器的实例归属检查：自动聚焦必须落在仍存活的当前实例，避免 StrictMode 中旧实例销毁后丢焦。共享生命周期约束与真实编辑器测试要求见 [Markdown 核心架构与 Crepe 适配](../../../共享能力/Markdown文档/技术/01_核心架构与Crepe适配.md#五生命周期与依赖)。

## 预览标记边界

`CommentLayer` 负责计算标记位置，但标记是否渲染由宿主提供的可见性开关决定。创作端和使用端在右侧「评论」页签激活时开启该开关；切换到其他页签只隐藏预览覆盖层，不清除线程数据、评论模式或当前选择。

这种分工让评论功能的状态保持在页面级，而展示范围始终与用户当前的工作上下文一致。

画布模式下，评论标记和浮窗通过页面卡片当前的 DOM 矩形与页面内归一化 `pin` 计算位置。画布平移或缩放提交后，评论层在布局阶段重新测量页面矩形，因此已打开的线程浮窗和新建评论浮窗会与页面一起移动；浮窗标题是可聚焦拖动手柄，鼠标/触控拖动会记录相对锚点的偏移，方向键也可按步移动；视口变化只更新锚点基准，不覆盖用户手动位置。首次点击产生的屏幕坐标只作为无法取得页面矩形时的降级值。锚点的组件、文本和 DOM 路径仍写入线程数据用于定位与审计，但线程浮窗不再渲染锚点摘要，避免遮挡评论正文和预览内容。

## 未解决提示范围

`useComments` 的 `target` 可省略：省略时 REST 与 WebSocket 都维护项目内全部评论线程；传入页面或文档 target 时继续只维护对应目标。共享筛选工具将页面线程、文档线程和未解决计数的规则集中在 `demo-ui`，避免宿主各自解释同一份数据。

作者编辑页统一省略 `target`，通过一次项目级 REST/WS 订阅维护全部评论线程；单页和画布模式都从这份线程集合派生当前页面线程、页面标签数量和配置项目标线程。右侧评论列表使用完整页面线程分组，预览标记和线程弹窗仍只接收当前聚焦页面线程，不能把项目级结果直接映射到其他页面坐标。文档评论不参与项目级红点统计。

`CommentUnreadDot` 只在存在未解决评论时渲染红色圆点，绝对定位且不显示数字。页签本身通过 `title` 和 `aria-label` 提供“有 N 条未解决评论”的文字提示，圆点保持 `aria-hidden`。

## 配置项评论目标

配置项评论与页面、文档评论共用 `CommentThread`，但目标身份不同。配置目标由 `kind: "config"`、`scope`、页面级时的 `pageId` 和 `fieldKey` 组成，`fieldTitleSnapshot` 只用于展示；它不携带 `anchor`、`pin` 或 `documentAnchor`。项目级配置不传页面 ID，页面级配置必须传当前引用页/普通页面 ID。

评论列表查询采用显式的配置范围、页面和字段条件，服务端拒绝 scope 与 pageId 不匹配、缺少 fieldKey 或混入页面/文档锚点的请求。配置项评论写入当前项目 comments store：引用页不会把评论写入源项目。字段删除或改名后线程仍保留，前端用字段快照或“配置项已不存在”状态继续展示。

作者编辑页与 viewer 订阅项目内全部评论，再用统一筛选函数把页面线程和当前配置目标线程分发到右侧栏。字段标题后的批注 Tag 触发 `ConfigCommentPopover`：创作端无线程时仅在鼠标悬停标题所在行或该行获得键盘焦点时显示且不接收鼠标事件，有任意线程（包括已解决线程）时常驻；viewer 无线程时不渲染，有任意线程时常驻。两端有线程时均使用高亮色且不显示数量。气泡与设计规范共用 portal、定位和外部点击机制。气泡内容分为线程列表和新增编辑区：线程列表独立滚动，创作端新增批注编辑区固定在底部并采用单行自动增高（约 8 行后内部滚动），避免编辑器把已有批注推离视口；线程卡片的作者、时间和操作图标保持同一行，作者名超长时省略；批注专用编辑器隐藏块级拖拽手柄；浏览端隐藏新增编辑区。目标下的全部线程按最新在前顺序展示，主批注和回复默认只读 Markdown，编辑才切换 `CommentMarkdownEditor`；主批注输入停止 800ms 后自动保存，失焦/关闭前 flush，新增批注失焦或 Cmd/Ctrl+Enter 提交，回复通过发送/确认图标显式提交。解决、恢复、删除和 WS 更新沿用现有线程接口，因此配置项评论不会进入页面评论未处理数量。viewer 通过只读控制器传入项目级线程，仅展示正文、作者、时间、回复和解决状态，不提供任何写入控件。

### 与相邻语义的边界

| 能力         | 语义                                   | 存储/消费                     |
| :----------- | :------------------------------------- | :---------------------------- |
| 设计规范     | 设计指导信息，可复用到页面或配置项     | 设计规范文档与规范面板        |
| 页面需求     | 页面级 Markdown 需求，可软引用多个配置 | 页面需求文档                  |
| 配置项批注   | 字段级评论线程，面向业务说明和协作跟进 | comments store、评论面板和 WS |
| `$demo.note` | 历史兼容字段，仅保留读取能力           | 配置 Schema 读取链路          |

## 画布侧栏边界

画布工作台复用右侧的评论列表与线程选择能力，并与配置面板通过页签切换。用户在画布评论模式点击页面卡片时，透明选择层优先接收点击；点击的屏幕坐标由外层评论层换算后，复用与单页相同的浮动输入框。提交时保存为页面级锚点与卡片内归一化位置，不切换到单页预览。这样评论能稳定归属页面，又不会绑定到会随画布缩放与拖拽变化的自由坐标。

评论的归一化位置始终相对于所属页面卡片保存，不随画布视口的平移和缩放改写；展示时按当前页面矩形重新换算，确保标记和浮窗与页面内容保持锚定。

画布页面标题旁的“评论 X”标签由项目级线程派生，X 只计算 `resolved=false` 的页面线程；标签点击先同步页面选择，再打开评论页签，不触动画布视口重定位。评论列表先执行“全部 / @我的 / 未解决”筛选，再按页面顺序分组；分组标题显示页面名称及该组未处理数量，“全部”筛选仍可查看已处理线程。画布当前页面变化时，侧栏通过页面分组锚点滚动定位并短暂高亮；选择其他页面线程时，宿主先切换聚焦页面，确保 `CommentLayer` 的页面线程与活动线程一致。滚动动画遵循 `prefers-reduced-motion`。
