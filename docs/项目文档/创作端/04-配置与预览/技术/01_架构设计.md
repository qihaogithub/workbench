### 1.3 AI 编辑数据流

当 AI 通过对话编辑代码时，数据流与 Figma 导入路径不同：

```
AI 对话（SSE / HTTP）
      │
      ▼
agent-service 执行编辑，写入文件
      │
      ▼
SSE 推送 session.diff 事件（文件变更）
SSE 推送 session.idle 事件（AI 响应完成）
      │
      ▼
┌─────────────────────────────────────────────────┐
│  useChatStream — onFinish                       │
│                                                  │
│  1. 优先使用 result.files（drain 机制保证完整） │
│  2. 兜底 fetchSessionFiles() HTTP 获取          │
│  3. 统一调用 onCodeUpdate / onSchemaUpdate      │
│  4. 触发 onSnapshotReady 回调                   │
└─────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────┐
│  page.tsx — applyDemoSnapshot()                 │
│                                                  │
│  原子化更新以下状态（一次性批量设置）：         │
│  ┌────────────────────────────────────────────┐ │
│  │ • code / schema / editorContent            │ │
│  │ • previewSize                              │ │
│  │ • configDataMap（合并新 schema 默认值）    │ │
│  │ • snapshotVersion++（驱动 PreviewPanel/    │ │
│  │   ConfigForm 强制重渲染）                  │ │
│  │ • compileVersion++（向后兼容）             │ │
│  └────────────────────────────────────────────┘ │
│                                                  │
│  配置合并策略：mergeSchemaDefaults() 纯函数     │
│  - 新增字段 → 使用 schema default               │
│  - 删除字段 → 从 configData 移除                │
│  - 仍存在字段 → 保留用户值                      │
│  - 类型变化 → 使用新 default                    │
└─────────────────────────────────────────────────┘
      │
      ├──────────────────────────────────────────┐
      ▼                                          ▼
┌─────────────────┐                    ┌─────────────────┐
│  PreviewPanel   │                    │   ConfigForm    │
│  snapshotVersion│                    │  key={`${id}-$ │
│  驱动重新编译   │                    │  {snapshotVer  │
│                 │                    │  sion}`}        │
│                 │                    │  强制重新挂载   │
└─────────────────┘                    └─────────────────┘
```

**关键机制**：

- **snapshotVersion 驱动**：`snapshotVersion` 是 UI 更新的单一可信源，在所有相关状态更新后才递增
- **applyDemoSnapshot 原子更新**：AI 编辑产生的 code 和 schema 变更被一次性原子化应用，保证预览与配置强一致性
- **配置合并策略**：`mergeSchemaDefaults(existingConfig, newSchema)` 按字段级规则智能合并，保留用户修改过的值
- **key 强制挂载**：`key={\`${activeDemoId}-${snapshotVersion}\`}` 使 ConfigForm 在快照变更时完全重建
- **drain 机制保障**：后端 `session.idle` 后等待 `session.diff`（最多 2s），确保 finish 时文件快照完整

详细说明参见 [02\_实时预览机制.md](./02_实时预览机制.md) 和 [03\_表单生成器.md](./03_表单生成器.md)。

### 1.4 备注功能数据流

备注功能采用 **Schema 变更驱动** 模式，备注内容以 **Markdown 字符串**存储在属性级 `$demo.note` 字段中，通过 `onSchemaChange` 回调统一持久化：

```
用户点击备注按钮
      │
      ▼
┌─────────────────────────────────────────────────┐
│  NoteDialog 打开（编辑模式 / 只读模式）          │
│                                                  │
│  编辑模式（创作端）：RichTextEditor Markdown 编辑 │
│  只读模式（使用端）：renderNoteMarkdown 渲染      │
└─────────────────────────────────────────────────┘
      │
      ▼
用户点击"保存"（编辑模式）
      │
      ▼
┌─────────────────────────────────────────────────┐
│  ConfigForm.updateSchemaNote                    │
│                                                  │
│  1. 解析 schema JSON                            │
│  2. 在对应属性的 $demo 下写入 note 字段(Markdown)│
│  3. 通过 onSchemaChange 回调传出完整 Schema 字符串│
└─────────────────────────────────────────────────┘
      │
      ▼
page.tsx 接收新 Schema → 持久化到项目数据
```

**备注与表单数据的关系**：

| 维度           | 说明                                                            |
| :------------- | :-------------------------------------------------------------- |
| 存储位置       | 属性级 `$demo.note`（Markdown 字符串），随 Schema 持久化        |
| 与配置值的关系 | 备注独立于 `formData`，不参与预览渲染                           |
| 变更回调分离   | `onChange` 传递表单数据；`onSchemaChange` 传递 Schema（含备注） |
| 使用端展示     | 使用端读取 Schema 中的 `$demo.note`，渲染为受控 HTML 展示       |
| 媒体插入     | 编辑态经 `/api/images/upload` 上传图片，插入 `![alt](/api/images/{id})` |

**创作端 vs 使用端的角色差异**：

| 端     | 备注操作           | 实现方式                                   |
| :----- | :----------------- | :----------------------------------------- |
| 创作端 | 添加/编辑/删除备注 | `NoteDialog` + `RichTextEditor`（共享 Crepe 编辑器） |
| 使用端 | 仅查看备注         | 独立的只读 Markdown renderer                       |

详细说明参见 [配置系统_需求文档.md](../配置系统_需求文档.md)。

### 1.5 页面配置要求数据流

页面配置要求（Page Requirements）是与页面 1:1 绑定的 Markdown 文档，存储于 `demos/{pageId}/requirements.md`，与配置项解耦、通过行内 legacy 配置项引用（`@[名称]` + `(config_key)`）指向配置项。

| 层 | 实现 |
| :--- | :--- |
| 存储 | `demos/{pageId}/requirements.md`，纳入 `DemoFiles`/`readPageFiles`/页面版本快照，随页面版本/拷贝/恢复/删除自动跟随 |
| 引用解析 | `packages/shared/src/demo/page-requirements.ts`：`parsePageRequirementsRefs`、`resolvePageRequirementRefs`、`inferPageRequirementTitle`。`config_key` 即 Schema 属性 key |
| 领域服务 | `project-core`：`getPageRequirements` / `updatePageRequirements` / `listPageRequirements`（反向视图数据源） |
| Web API | `author-site`：`/api/projects/[projectId]/demos/[demoId]/requirements`（GET 读取并解析引用 / PUT 写入） |
| 只读渲染 | `demo-ui`：`renderPageRequirementsMarkdown` 把软引用渲染为 `span.pr-ref[data-ref-key]` chip；`PageRequirements` 组件经事件委托触发 `onRefClick(configKey)` |
| 面板接入 | `PageConfigPanel` 将页面规范卡片列表直接置于页面配置要求之前，省略额外分组标题与数量；页面配置要求保持为独立区域，配置内容在两端都无“配置项”外层标题与整体折叠，可用操作由右下角更多悬浮菜单按宿主能力组装 |
| 编辑器 | 通过共享 `RichTextEditor`/`DocumentEditor` 接入；配置项引用候选和 legacy 语法适配见[编辑器扩展与渲染适配](../../../共享能力/Markdown文档/技术/03_扩展与渲染适配.md) |
| 编辑页接线 | `edit/page.tsx` 按活动页 GET 加载配置要求、PUT 持久化，两处 `PageConfigPanel` 挂载点传入 `requirements`/`onRequirementsChange`/`requirementsLoading` |

软引用基于当前页 `config.schema.json` 实时解析；配置项删除/改名时引用标记为「失效」但不阻塞文档，配置项增删改不破坏配置要求文档。

> 页面配置要求与「可视化批注」（单页预览元素浮层，见 [06\_可视化批注与编辑机制.md](./06_可视化批注与编辑机制.md)）是两套独立能力，术语互不混淆。配置项备注（`$demo.note`）为页面配置要求的演进来源，迁移脚本 `scripts/migrate-config-notes-to-page-requirements.mjs` 将旧备注聚合为页面要求。

### 1.6 设计规范消费位置数据流

设计规范条目以 `target` 表达唯一的消费位置：`{ type: "page", pageIds }` 或 `{ type: "config", refs }`。标题是条目独立字段，Markdown 只保存正文；一个条目不得同时保存两类绑定。

| 层 | 实现 |
| :--- | :--- |
| 读写与迁移 | `author-site` 的 `lib/design-specs/storage.ts` 在读取时把旧 `refs` 迁移为配置项目标；无旧引用的自动页面文档条目绑定其 `autoManagedPageId`，其余成为未绑定页面规范，仅在文档编辑器可见 |
| 编辑器 | `DesignSpecWorkspace` / `DesignSpecEditor` 不提供手动类型切换；页面或配置项绑定自动决定消费位置，跨类型绑定由 workspace 统一确认并替换。页面目标可多选页面，配置项目标可多选字段 |
| 规范项面板 | `DocumentModeRightPanel` 在设计规范文档下显示统一「规范项」绑定池；配置项按页面分组，分组节点标题同时作为页面拖拽绑定入口，不再额外渲染独立页面列表；分组下的配置项列表使用缩进和竖向层级线，明确表达其所属页面；空分组隐藏展开箭头但保留图标占位，确保页面名称列对齐 |
| 绑定编辑入口 | 页面绑定统一从右侧页面分组节点拖拽完成，条目卡片展示已绑定页面名称摘要，并在页面行悬停或聚焦时提供解绑按钮；不渲染重复的页面勾选区或展示位置说明。页面节点始终可拖拽复用，跨类型替换由 `DesignSpecWorkspace` 统一确认并清空旧绑定 |
| 配置项编辑回填 | 文档内字段定义编辑不切换预览视图。页面级提交按目标 `pageId` 写入 Schema 与默认值计划；即使目标不是活动页，也不借用活动页保存链路。工作区与项目同步成功后才广播带 `committed` 标记的 Schema 更新事件；`DesignSpecWorkspace` 可据此即时投影，随后无缓存读取服务端素材池并以服务端结果替换临时投影。失败时字段编辑器保留草稿，规范表格不显示未提交内容 |
| 自动同步 | `project-core/page-design-spec-sync.ts` 只创建、更新或删除自动管理的配置项目标；页面规范和手工配置项规范原样保留 |
| 侧边栏投影 | `PageConfigPanel` 将配置项目标投影为蓝底白字字段「规范」入口，将当前页面的非空页面目标投影为顶部常驻的「页面规范」卡片区；入口以消费位置、文档和条目的组合身份切换同一 Markdown 详情气泡，再次点击当前入口关闭，且外部点击不会与入口点击竞争 |
| 创作端与引用页 | 普通页面由设计规范 API 懒加载；引用页接口显式返回页面规范与配置项规范的两类投影，避免把源项目数据写入目标工作区 |
| 浏览端 | `ViewerApp` 从发布设计规范文档按 `target` 分流并传入同一 `PageConfigPanel`；`ViewerDocumentView` 汇总两类条目，配置项目标才显示字段摘要表 |

页面规范只按文档条目顺序显示，不提供按单一页面另行排序。正文为空或目标未完成绑定时，不生成任何侧边栏入口。

## 二、技术选型

### 2.1 表单引擎

采用 **react-jsonschema-form (RJSF)** 作为表单生成引擎：

| 特性             | 说明                     |
| :--------------- | :----------------------- |
| JSON Schema 驱动 | 根据 Schema 自动生成表单 |
| 丰富的控件       | 支持多种数据类型         |
| 自定义控件       | 可扩展 Widget            |
| 实时验证         | 表单填写时校验           |

### 2.2 解析器

自定义解析器处理 Figma 导出格式：

| 功能       | 说明                              |
| :--------- | :-------------------------------- |
| 分隔符识别 | 识别 `=== DEMO CODE ===` 等分隔符 |
| 内容提取   | 提取代码和 Schema 两部分          |
| 格式修复   | 自动修复常见格式问题              |

### 2.3 文档编辑器（配置备注接入）

配置备注以 Markdown 字符串存储在属性级 `$demo.note` 字段中。创作端使用共享 `DocumentEditor` 编辑，使用端使用安全的只读 Markdown renderer 展示；编辑器的 Crepe v7、内容模型和扩展契约统一见[Markdown 文档与编辑器专题](../../../共享能力/Markdown文档/)。

本模块只负责备注与 Schema 的数据流：`onSchemaChange` 持久化包含备注的 Schema，备注不参与 `formData` 或预览运行值。媒体白名单和备注清洗规则仍由配置系统的 renderer 负责。

### 2.4 Radix 组件引用约束

配置与预览界面复用 shadcn/ui 与 Radix 组件承载下拉菜单、弹窗、折叠面板、Tooltip、Select 等交互控件。由于这些控件会在挂载时组合多个 `ref`，依赖解析必须保持一致，避免同一页面中出现不同 ref cleanup 语义。

当前项目在根依赖配置中将 `@radix-ui/react-compose-refs` 统一约束为 `1.0.0`。该版本只负责把节点写入各个 ref，不引入 callback ref cleanup 返回值；这样可以降低 React 18.3 开发模式下 Radix 触发器、弹层与可排序控件组合时出现 `Maximum update depth exceeded` 的风险。

升级 Radix 或 React 时需要重新验证配置化面板、页面树菜单、预览页 Select、Tooltip 与 Dialog 的挂载/卸载行为。如果移除该约束，必须先通过编辑页首屏、页面切换、配置化切换和菜单/弹窗打开关闭流程确认不会重新出现引用循环更新。

## 四、扩展机制

### 4.1 自定义控件

通过 Widget 机制扩展控件，遵循三层映射结构（Layer 1: ui:widget → Layer 2: format → Layer 3: type）：

| 控件         | 文件位置              | 说明                                                          |
| :----------- | :-------------------- | :------------------------------------------------------------ |
| 颜色选择器   | `widgets.tsx`         | 可视化选择颜色，`format: "color"` 触发                        |
| **图片上传** | `widgets.tsx`         | **单图片上传，`format: "image"` 或 `ui:widget: "file"` 触发** |
| 多图片上传   | `ImageListWidget.tsx` | 多图片上传，`ui:widget: "imageList"` 或 `type: "array"` 触发  |
| 富文本编辑器 | `widgets.tsx`         | 富文本编辑，`ui:widget: "richtext"` 触发                      |
| 代码编辑器   | `widgets.tsx`         | 编辑代码片段                                                  |

详细映射规则参见 [03\_表单生成器.md](./03_表单生成器.md) 第五节「控件映射体系」。

### 4.2 控件注册

```typescript
const widgets = {
  color: ColorWidget,
  code: CodeWidget,
}

<Form
  schema={parsedSchema}
  widgets={widgets}
  onChange={handleChange}
/>
```

### 4.3 Markdown 编辑器扩展

配置备注只声明自身的 Markdown 存储和 Schema 回调，不重复实现编辑器插件。图片、附件、配置项引用和只读 renderer 的公共扩展见[编辑器扩展与渲染适配](../../../共享能力/Markdown文档/技术/03_扩展与渲染适配.md)；配置备注的媒体安全和字段级持久化仍由本模块负责。
