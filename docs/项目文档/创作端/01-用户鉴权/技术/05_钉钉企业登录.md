## 一、登录模式

钉钉登录支持两种入口，服务端最终都复用同一套本地用户和 JWT 登录态：

| 入口 | 使用场景 | 身份凭证交换方式 |
| :--- | :--- | :--- |
| 普通浏览器 OAuth | 用户在 Chrome、Edge 等浏览器打开创作端，再点击钉钉登录 | OAuth `authCode` 换用户 access token，再读取当前用户 |
| 钉钉内部 H5 免登 | 用户从钉钉工作台打开网页应用 | `dd.runtime.permission.requestAuthCode` 获取免登 code，再调用旧版内部应用接口 |

普通浏览器不需要把创作端嵌在钉钉里，但用户仍会跳到钉钉授权页完成授权。浏览器 OAuth 与内部 H5 免登是两条独立链路，不能把一种链路拿到的 code 交给另一种接口。

## 二、配置

服务端通过环境变量读取钉钉企业内部应用凭证。完整配置如下：

| 变量 | 说明 |
| :--- | :--- |
| `DINGTALK_LOGIN_ENABLED` | 设置为 `true` 显式启用钉钉登录；完整应用配置也会自动启用 |
| `DINGTALK_CORP_ID` | 企业 CorpId，用于企业身份隔离；不是应用 App ID 或 AgentId |
| `DINGTALK_APP_KEY` | 应用凭证中的 Client ID，历史名称为 AppKey |
| `DINGTALK_APP_SECRET` | 应用凭证中的 Client Secret，历史名称为 AppSecret，只允许服务端使用 |
| `DINGTALK_LOGIN_REDIRECT_URI` | 浏览器 OAuth 回调完整地址，必须与钉钉后台登记值完全一致 |
| `DINGTALK_LOGIN_SCOPE` | OAuth scope，默认 `openid` |
| `DINGTALK_LOGIN_PROMPT` | OAuth 授权提示策略，默认 `consent` |
| `DINGTALK_LOGIN_AUTH_URL` | 可选的旧版手工跳转地址，仅作为浏览器 OAuth 未配置时的兼容回退 |
| `DINGTALK_LOGIN_OAUTH_BASE_URL` | 可选；默认 `https://login.dingtalk.com/oauth2/auth` |
| `DINGTALK_API_BASE_URL` | 可选；默认 `https://api.dingtalk.com` |
| `DINGTALK_OAPI_BASE_URL` | 可选；默认 `https://oapi.dingtalk.com`，内部 H5 免登链路使用 |

浏览器端配置接口只返回脱敏后的启用状态、CorpId 和回调配置，不会返回 AppSecret 或 access token。

## 三、普通浏览器 OAuth 流程

登录页检测到普通浏览器并且配置完整时，按钮跳转到 `GET /api/auth/dingtalk/start`。服务端完成以下工作：

1. 生成不可预测的随机 `state`。
2. 把 `state` 和站内登录后的跳转地址写入 10 分钟有效的 HttpOnly、SameSite=Lax Cookie。
3. 生成钉钉 OAuth 授权地址，带上 `client_id`（应用 Client ID/AppKey）、`redirect_uri`、`scope`、`state` 和 `prompt`。
4. 浏览器跳转到钉钉授权页。官方协议说明见[钉钉 OAuth2.0 鉴权文档](https://open.dingtalk.com/document/connection/oauth2-0-authentication)。

钉钉授权完成后回到 `GET /api/auth/dingtalk/callback`，查询参数通常包含 `authCode` 和 `state`。服务端会：

1. 拒绝缺少授权码、授权失败或 `state` 不匹配的请求。
2. 用 `authCode` 调用 `POST /v1.0/oauth2/userAccessToken`，使用服务端保存的 Client ID 和 Client Secret 换取用户 access token。
3. 带 `x-acs-dingtalk-access-token` 请求头调用 `GET /v1.0/contact/users/me`，读取当前用户的 `unionId`、`openId`、昵称和头像。
4. 按企业 CorpId 加 `unionId` 优先、`dingtalkUserId` 兜底查找本地身份；首次登录则创建密码不可用的本地用户。
5. 使用现有 JWT 签发逻辑，把 HttpOnly 认证 Cookie 写入回调重定向响应。
6. 跳回 state Cookie 中保存的站内地址，默认 `/workbench`，随后清理 OAuth 临时 Cookie。

失败时不会把钉钉原始错误或授权码返回给浏览器，只跳回登录页并显示通用错误提示；服务端日志也不记录授权码和 access token。

## 四、内部 H5 免登流程

在钉钉容器内打开时，登录页优先调用 `dd.runtime.permission.requestAuthCode`。拿到免登 code 后提交 `POST /api/auth/dingtalk/login`，服务端：

1. 使用企业内部应用配置获取应用 access token。
2. 使用免登 code 调用内部应用用户信息接口。
3. 读取钉钉用户 ID、unionId、名称和头像。
4. 按与浏览器 OAuth 相同的身份规则查找或创建本地用户。
5. 写入现有 JWT Cookie。

该链路需要从钉钉客户端或工作台打开应用；普通浏览器不应手工调用这个接口。

## 五、接口契约

| 接口 | 用途 | 关键行为 |
| :--- | :--- | :--- |
| `GET /api/auth/dingtalk/config` | 返回登录页所需的脱敏配置 | 只返回 `enabled`、`browserOAuthEnabled`、`corpId`、`authUrl`、`redirectUri` |
| `GET /api/auth/dingtalk/start` | 启动普通浏览器 OAuth | 生成 state、保存临时 Cookie，并返回 307 到钉钉授权页；配置缺失返回 503 |
| `GET /api/auth/dingtalk/callback` | 接收钉钉 OAuth 回调 | 校验 `authCode`/`code` 和 state，成功后写 JWT 并跳转站内地址，失败回登录页 |
| `POST /api/auth/dingtalk/login` | 接收内部 H5 免登 code | 仅用于钉钉容器免登，成功后返回用户信息并写 JWT |
| `GET /api/auth/dingtalk/binding` | 查看当前账号绑定状态 | 仅展示身份摘要，不返回凭证 |
| `GET /api/auth/me` | 返回当前登录用户 | 返回稳定的本地 `username`，并在已绑定钉钉时额外返回钉钉姓名 `displayName` |

`redirect` 查询参数只接受当前站内的绝对路径，协议相对地址、反斜杠和控制字符会回退到 `/workbench`，避免登录后开放重定向。

## 六、身份存储

本地数据库使用 `user_dingtalk_identities` 保存钉钉身份与本地用户的绑定关系。

关键约束：

- 同一企业内 `unionId` 唯一绑定到一个本地用户。
- 同一企业内 `dingtalkUserId` 唯一绑定到一个本地用户。
- 删除本地用户时，钉钉身份绑定随用户删除。
- 自动创建的本地用户生成随机密码哈希，不向用户展示，也不能用该随机密码登录。

## 七、局域网部署

回调地址必须是钉钉后台登记过的完整 URL，例如：

```text
http://10.130.33.34:4200/api/auth/dingtalk/callback
```

发起登录的浏览器和 author-site 服务都必须能访问这个地址。若钉钉平台不接受局域网 IP 作为回调地址，需要使用内网穿透域名，并让用户从该域名访问登录页和后续页面；不能只把回调地址换成公网地址而继续从局域网地址发起流程。

生产环境建议使用 HTTPS，并让 `DINGTALK_LOGIN_REDIRECT_URI`、钉钉后台登记地址和用户实际访问域名三者保持一致。

## 八、绑定状态与外部授权

设置弹窗的外部账号授权页展示当前账号的钉钉企业身份，包括钉钉名称或 userId、企业 ID 和绑定状态，但不展示敏感凭据。

钉钉登录创建的本地 `username` 是用于唯一匹配的稳定内部标识（通常以 `dt_` 开头），不作为用户界面中的首选称呼。当前用户接口、设置弹窗和管理后台用户列表会优先展示钉钉返回的 `name`（以 `displayName` 返回）；姓名缺失时才回退到本地 `username`。这样既能显示用户熟悉的钉钉姓名，也不会因改名或重名破坏账号绑定。

钉钉企业登录解决“用户是谁”；用户级外部工具授权解决“AI 能否代表该用户访问钉钉文档”。两者使用不同的 token 和生命周期，不能跨用户共享。
